# Stellaris real-game testing framework

Local review draft · 2026-09-09

Source map: [Specify the Stellaris SDK real-game testing framework](https://linear.app/unnamed-system/issue/SDK-405/specify-the-stellaris-sdk-real-game-testing-framework).

This specification consolidates the completed decisions and their amendments. It describes the production framework to build. Historical probes establish bounded feasibility; they do not establish production release qualification. This local draft is the review artifact before publication to the SDK Testing Framework project.

The local review amendment of 2026-09-09 changes the first-release target to Windows x64 / Stellaris 4.4.6. It supersedes the map's earlier macOS-first target. Native Apple Silicon support follows after Stellaris 4.5 and matching cwtools/SDK authoring support are available. No Rosetta 2 adapter is planned.

## Executive Summary

Build a real-game test runner that lets mod authors check their TypeScript-authored behavior inside Stellaris. It replaces the testing package's offline interpreter with controlled game execution, captured results, and evidence that explains both successful checks and failures.

Authors use familiar suites, tests, and hooks. The runner builds the mod once and starts a fresh hidden game for each suite; tests within a suite share its evolving world. Tests can run prepared scripts, inspect resources, advance time, and select valid options on real pending events. Runs preserve the author's control of their computer and isolate normal game data.

The first release targets Windows x64 with Stellaris 4.4.6, matching the SDK's supported authoring version. Native Apple Silicon support follows when Stellaris 4.5 is released with native support and cwtools and the SDK support authoring for it. The same shared adapter contract serves both platforms. Rosetta 2 development, CI qualification, and wider game-control capabilities are outside this release.

A pass requires completed, checked behavior under recorded starting conditions. Incomplete execution, script diagnostics, and cleanup outcomes remain visible separately. The shared design and bounded Windows prototype are established; full Windows capability verification, production implementation, and qualification remain. Early Windows probes must establish the missing event, resource, and ownership mechanisms before dependent integration. Native delivery choices and a measured strict-diagnostics baseline must also be resolved. Release requires all included capabilities, ten consecutive successful qualification runs, failure/recovery checks, measured performance targets, and a tool-backed adapter-authoring Skill.

## Problem Statement

Mod authors need to know whether their TypeScript-authored triggers, effects, and event chains work in Stellaris. An offline interpreter can test only the semantics it reproduces. It cannot establish that the installed game executes vanilla definitions, applies event choices, advances simulation, or produces the expected state.

Manual testing requires repeated setup, game interaction, and interpretation of logs. It is slow to repeat, difficult to isolate, and weak at distinguishing an assertion failure from an action that never completed. It also interrupts the author's use of their computer.

Authors need controlled real-game tests with explicit starting conditions, typed game operations, exact captured results, and retained evidence. A passing result must describe what was checked and completed, while making incomplete execution, diagnostics, and cleanup failures visible.

## Solution

Replace the existing testing package's offline execution model with a standalone real-game runner in `@pdx-ts/sdk-testing`. Authors declare suites, async tests, hooks, fixtures, and prepared scripts in TypeScript. The runner builds the current mod once, captures immutable inputs, starts an isolated hidden Stellaris process for each suite, executes operations through a native adapter, and reports the resulting evidence.

Each non-nested `describe` owns a fresh game and starting fixture. Tests inside that suite run sequentially and share its evolving world. Authors can execute fixed prepared effects and conditions, resolve live country and planet bindings, capture country stockpiles, advance game days, wait for conditions or events, and choose named options on actual pending player events.

The first release qualifies the Windows x64 / Stellaris 4.4.6 combination specified below, using matching SDK authoring inputs. A single adapter factory selects the compatible implementation. Platform and game-build details stay behind the shared adapter contract so later native Apple Silicon support can be added without changing test declarations or runner policy. That extension waits for the Stellaris 4.5 release and matching cwtools and SDK support; it does not require an intermediate Rosetta 2 adapter.

## Implementation Decisions

### 1. Domain and architecture

- A **Run** is one command or callable invocation, its selected suites, captured inputs, attempts, and results. A **Suite** is one non-nested `describe` with a fresh game process, private profile, fixture instance, and world. A **Test** is one async body inside that suite.
- An **Execution process** is the fresh host process that loads configuration and author modules and owns their callbacks and JavaScript state. A separate **Supervisor** owns admission, deadlines, durable evidence, process supervision, and disposal. Blocking author code must not block supervision.
- A **Prepared script** is a fixed recorded effect or condition made available before game execution. An **Invocation** is one dynamic operation, including each repeated call or wait iteration. A **Phase** is a particular fixture, validation, hook, or test-body lifetime.
- A **Locator** is an immutable typed recipe. A **Binding** identifies the particular live object found by successful resolution. An **Observation** is an immutable historical capture with subject, operation, precision, and capture evidence. **Finalization** preserves results and cleanup facts.
- Initially keep authoring, collection, preparation, execution, supervision, protocol, results, reporting, adapter contracts/factory/implementations, and CLI modules inside `@pdx-ts/sdk-testing`. The former interpreter has no compatibility or architecture authority over the replacement.
- Reuse SDK Trigger, Effect, scope/context, event/reference, Fold, PureMod, Rendered mod, and Materialization machinery. Stellaris supplies game semantics. PDXScript remains syntax-only. Use a narrow SDK-owned recording/lowering boundary if internal exports need extension; do not duplicate the recorder or build a second semantic schema.
- Test registration is local to the testing framework. It does not change the SDK's immutable Capability, Item placement, or explicitly declared Feature list. Test-file discovery does not discover mod Features.

The public behavior comes from [Define the author-facing test API and runner integration](https://linear.app/unnamed-system/issue/SDK-420/define-the-author-facing-test-api-and-runner-integration). The [Runner module contracts and prepared-script dispatch](https://linear.app/unnamed-system/document/runner-module-contracts-and-prepared-script-dispatch-596115eda6a6) asset supplies the detailed type and boundary contracts; later coverage and acceptance resolutions supersede its historical open-proof notes.

### 2. Public entry points, configuration, and collection

- Export familiar `describe`, `test`/`it`, `beforeAll`, `beforeEach`, `afterEach`, and `afterAll` registration, prepared-script helpers, fixtures, and assertions from the testing package. Provide `defineConfig`, `runTests`, and `listTests`, plus the standalone `pdx-test run` and `pdx-test list` commands.
- The callable API accepts serializable file/options requests and starts its fresh execution process directly. It does not invoke the CLI or a shell. Configuration callbacks and fixture objects are loaded inside that process. A caller's `AbortSignal` remains local to the API wrapper and sends cancellation over the control channel.
- Configuration uses `pdx-test.config.ts`. Group settings under `build`, `files`, `defaults`, `timeouts`, `failFast`, `diagnostics`, `evidence`, and `installation`. Defaults are recursive `.e2e.ts` discovery under `tests`, the baseline fixture, AI off, fail-fast off, strict diagnostics off, evidence directory `.pdx-test`, and `keepAll` false.
- Apply supplied API/CLI leaves over configuration leaves over defaults. A describe overrides fixture and AI defaults only. Configuration-relative paths resolve from its directory; explicit config and selection paths resolve from invocation working directory. Retain resolved paths.
- Sort normalized file paths, then retain describe/test declaration order. Explicit files select those files; directories recursively select matching test files. `-t` is a regular expression against the combined describe/test name. Skip/focus controls and explicit filters narrow selection. Preserve skipped, focus-excluded, filtered, selected, and later-omitted states separately.
- Selection does not run earlier tests implicitly. A selected test gets suite hooks and its own per-test hooks. Authors must select the whole suite for a sequence spread across tests, or put an independently selectable sequence in one async test.
- Every test must belong to a describe. Reject nested describes, top-level tests, duplicate describe names within a file, and duplicate test names within a describe. The same names may occur in different files; reports include file and suite.
- Await module evaluation, including valid top-level async initialization. Describe callbacks must be synchronous. Freeze registration and prepared declarations after collection; reject later declarations. Each invocation has a fresh module graph, including helpers. Host module state is shared between suites during one healthy invocation; no cross-suite JavaScript-state reset is promised.
- Fixture-typed describe callbacks receive suite-bound registration functions that infer extra bindings. Globally imported registration functions expose the standard player context; lexical nesting does not make them infer a custom fixture type. Suite-bound registration functions reject use under another suite.
- Listing performs collection and selection only. It does not execute hooks/tests, call the build callback, resolve live objects, prepare launch inputs, select an adapter, acquire game ownership, or launch Stellaris. No runnable selected tests produces a clear unsuccessful run by default.
- `runTests` returns a retained `RunResult` for anticipated collection, project configuration, build, environment, fixture, execution, and finalization failures. Malformed programmatic arguments reject before execution. `listTests` returns `CollectionResult`, without claiming game execution.

### 3. Preparation and immutable run inputs

- `defineEffect` records an SDK effect closure once before launch. `defineCondition` records a trigger or contextual trigger declaration. Contextual forms expose declared ambient slots only. Live test bodies may choose scripts, loop, branch, and choose target/context bindings; they cannot record new scripts or substitute newly calculated scalar arguments.
- The prepared catalogue includes every declaration from loaded modules, including declarations used only by skipped tests or unvisited branches. Validate and compile it before launch without executing test bodies to discover operations. Validate known requirements early and dynamically chosen operations when invoked.
- Call the ordinary mod build callback once per run. Accept PureMod, Rendered mod, or an explicit completed-mod directory. Render/capture into immutable, hashed private inputs. Directory input must contain a complete valid mod and descriptor. Refuse inconsistent capture or malformed inputs.
- Capture source-save identity, current-mod bytes, pinned dependencies and their order, DLC/configuration, and support scripts. Each suite receives fresh private copies of that same captured material. Source edits during a run cannot change later suites; a later invocation detects dependency drift.
- Align release qualification with the SDK's supported authoring version: pin the cwtools rules, generated SDK surface, install-derived identifiers, game executable, and fixture inputs for Stellaris 4.4.6. Native bridge compatibility or a successful 4.5 probe does not establish 4.5 authoring support. The unverified-game override cannot upgrade an unsupported authoring combination into a supported release target.
- A supported runner/game combination requires matching verified SDK authoring support and separate adapter qualification. An upstream cwtools update enables SDK integration; it does not itself upgrade the SDK or qualify a new game build. Update the published compatibility matrix only after all affected authoring, native, and production gates pass.
- Keep the generated support mod separate from the normal distributable mod, with explicit load order and a reserved generated namespace. Resolve path/ID collisions through SDK rules. Preserve reference checks, localization duplicate checks, and BOM-prefixed localization output. Never modify author source or normal game data to install test support.

### 4. Fixtures, bindings, and starting conditions

- Provide `baseline` and `defineFixture` with save, requirements, bindings, setup, and validation. Baseline and custom saves must be game-produced. Pin source-save build/hash and ordered dependency content/hashes. Record intentional changes to the current mod separately from pinned fixture dependencies. Required DLC must be available.
- The supplied baseline is a small game-produced save with no required DLC or third-party mods. Record its creation build and validate it on every claimed build. Qualify its exact content and declared bindings; do not assume example resource amounts or other unvalidated state. Suite-created manual saves and autosaves are artifacts, never automatic inputs for another suite.
- Produce and qualify the baseline in Windows Stellaris 4.4.6. The existing Windows spike fixture requires 28 DLCs and uses player ID zero, so it does not satisfy the baseline or nonzero-player acceptance controls. The Windows qualification fixture set must include both the DLC-free baseline and a game-produced nonzero-player case; one fixture need not serve both purposes. Retain exact save, DLC, dependency, and settings provenance for each.
- Unexpected dependency content changes require an explicit fixture-record update; do not silently accept or re-pin them. Disclose setup changes, execution settings, and any declared dependency replacements. A replacement cannot support a claim about the original definition.
- Resolve the actual loaded player as the standard country binding. A custom fixture cannot replace `player` with another object. Supported locators are actual player, unique fixed condition, global event target, and a saved ID declared against that exact source fixture with kind/condition validation. Saved IDs do not create an arbitrary runtime numeric-ID API.
- Declare the kinds of initial and setup-created bindings before launch. Resolve initial bindings, execute setup once, require exactly the declared setup outputs, and validate the complete binding map and starting conditions. Missing, extra, wrong-kind, dead, or foreign-world outputs invalidate the fixture. A fixture with no setup outputs may return void.
- Setup and validation share the fixture-setup deadline. Failed starting conditions are an invalid fixture, not a test assertion mismatch. Missing setup/validation completion is incomplete execution. Hooks and tests start only after successful fixture preparation.
- Tests and hooks may call `game.resolve` on prepared locators. Require exactly one live object of the requested kind. A missing or ambiguous match cannot produce a binding. Do not assume player country zero or predict IDs for created objects.
- Bindings preserve object identity through capital, role, flag, target, or colonization changes. Re-resolving a locator is a new resolution and may find another object. Validate world, object kind, issued token, identity, and lifetime before use. Actual engine removal invalidates a binding; merely requesting destruction does not imply removal. Complete numeric-ID/address reuse must not revive old bindings. Validation advances no game time.
- Effects can create objects and mark them with a unique condition or global event target for later resolution. Finding such a marker does not prove the last invocation created the object. Direct effect-returned binding capture and automatic stale-marker clearing are deferred.

Fixture decisions are held in [Define save fixtures and test-state isolation](https://linear.app/unnamed-system/issue/SDK-414/define-save-fixtures-and-test-state-isolation), as amended by the suite contract. Native identity evidence is indexed by [Verify country and planet locator identity and lifetime](https://linear.app/unnamed-system/issue/SDK-442/verify-country-and-planet-locator-identity-and-lifetime).

### 5. Shared-suite execution and hook behavior

Run suites sequentially, with one owned game at a time. For each suite:

1. Create a private profile and fresh owned process from captured inputs.
2. Establish process/bridge identity, fixture/world/player readiness, paused state, and the suite's AI mode.
3. Resolve initial bindings, complete setup, and validate the starting fixture.
4. Run `beforeAll`.
5. For each selected test, run `beforeEach`, its async body, and eligible `afterEach`.
6. Run eligible `afterAll`, dispose of the game, and finalize evidence before another suite starts.

- Tests share mutations, elapsed game time, bindings, and historical observations within the suite. `beforeEach` supplies no automatic reset. Fixture and AI mode cannot change mid-suite.
- Each hook/body receives a fresh phase-bound game facade. Old callbacks cannot reopen a completed phase, even if they retained a facade. Bindings and observations may cross phases within the same suite/world, but never authorize another suite.
- The first failed required operation or assertion stops the current test's normal actions and omits the remaining tests in its suite. Catching an exception or returning normally cannot clear the durable failure.
- Fixture failure permits no suite hooks or tests. Failed `beforeAll` stops the suite. Failed `beforeEach` skips that body and its `afterEach`; `afterAll` may remain eligible after completed suite preparation. Absent preparation hooks count as completed.
- After hooks use the same typed game/bindings and receive an immutable outcome snapshot. They run only after their corresponding preparation completed and while the channel and native completion state remain trustworthy. Their evidence cannot create a test pass or erase earlier facts. An after-hook failure makes the suite/run unsuccessful and stops that hook; another eligible after hook may still run.
- Cancellation, uncertain action completion, lost world/channel identity, relevant incomplete preparation, or execution-process loss skips affected game hooks with a reason. Runner disposal and evidence collection always run independently of author hooks.
- After an ordinary failed test, invalid fixture, isolated game crash, or operation timeout, a later fresh suite may run only after confirmed disposal, fresh isolation, working shared infrastructure, and a usable execution process. Run-wide fail-fast also stops later suites.
- Execution-process loss, including killing synchronously blocked author code, aborts remaining suites. Do not reload modules to resume: callbacks and shared host state have been lost. Lost ownership, unavailable evidence storage, or unresolved disposal also aborts the run. A new invocation starts a new run.

### 6. Operation and assertion contracts

| Public operation      | Required result                                                                                                   |
| --------------------- | ----------------------------------------------------------------------------------------------------------------- |
| `game.run`            | Execute a fixed prepared effect against typed live target/context bindings; resolve after established completion. |
| `game.evaluate`       | Evaluate a fixed prepared condition and return a captured boolean Observation.                                    |
| `game.resolve`        | Resolve a declared typed Locator to one current-world Binding.                                                    |
| `game.read.resource`  | Return an exact country-stockpile Observation for the requested resource.                                         |
| `game.advance`        | Advance positive whole game days to the exact requested date and finish paused.                                   |
| `game.waitFor`        | Return the successful captured condition Observation within explicit game-day bounds.                             |
| `game.events.fire`    | Complete direct firing without a time advance and return its correlated FiredEvent.                               |
| `game.events.waitFor` | Return one actual matching pending event for the fixture's player within explicit game-day bounds.                |
| `game.events.choose`  | Validate a fired/pending handle and named option, then complete normal engine selection.                          |

- Admit operations through the supervisor after validating active phase/world, failure state, outstanding operation, and deadlines. Reject overlap. Returning with an unfinished operation prevents success; later completion during cleanup does not repair that phase. Each operation is durably identified before dispatch.
- A completed checked action may qualify an action-only smoke test. Empty bodies, unused observations, binding lookup alone, setup alone, or merely reaching the end do not establish a behavioral pass. Ordinary JavaScript assertions may fail a test but cannot manufacture game-observation evidence.
- Framework assertions synchronously obtain bounded durable supervisor acknowledgement before returning or throwing. This acknowledgement cannot depend on the blocked author event loop. Recording/acknowledgement failure is infrastructure failure. The supervisor latches mismatches independently of author exception handling.
- `expectRejected` scopes exactly one logical game operation and the requested structured reason. Only verified refusal without the requested mutation satisfies it. Zero/multiple operations, a different reason, unexpected acceptance, foreign/inactive authority, timeout, or uncertain completion fails. A callback catching the operation's exception does not change the outcome. Unexpected acceptance may have mutated the world and stops the suite.
- Keep successful completion, safe rejection, runner-contract error, and incomplete execution distinct. If an action may have executed but completion or identity is unknown, retain the facts as incomplete; return no successful handle, make no arbitrary choice, and do not retry or resume normal actions.

The guarantee and rejection rules derive from [Define what a passing real-game test guarantees](https://linear.app/unnamed-system/issue/SDK-410/define-what-a-passing-real-game-test-guarantees) and the later public/module contracts.

### 7. Exact observations

- Preserve exact decimals as a signed base-10 coefficient string and a positive power-of-ten denominator named `scale`. The initial resource reader uses scale 100000, preserving increments of 0.00001 units through capture, transport, storage, comparison, and reporting.
- An Observation retains authenticity, run/suite/world, original subject, reader/condition, precision, invocation/capture identity, evidenced game-date brackets, and separate host receipt time. Do not infer an exact engine tick or atomic snapshot from unchanged dates.
- Reusing an Observation later in the same suite compares the original captured value. Attribute the new assertion to the current phase and keep the original capture point. Comparing two observations retains both capture identities. Cross-suite/run or forged observations cannot satisfy framework checks.
- Provide equality, ordering, allowed-set membership, boolean condition assertions, and approximate comparison with a required absolute tolerance. Exact equality is the default. Render enough precision to expose the actual difference.
- Accept finite number literals and exact decimal strings as numeric expectations. Parse a number's decimal representation explicitly; refuse unsafe integer literals with guidance to use a string. Do not silently equate the floating-point result of `0.1 + 0.2` with `0.3`.
- Observations do not implicitly convert to JavaScript numbers. An explicit `toNumber` conversion may lose precision and returns ordinary host data. Failed/unavailable reads create no Observation and never substitute zero. Separate or grouped reads carry no atomic snapshot promise.

### 8. Time, events, and AI

- All ordinary game operations run without implicit time advancement. Use verified native fast-forward; no unpause/re-pause, overnight-mode, OS-input, guessed-address, or implicit-time fallback is allowed. Date change alone is insufficient: establish simulation completion, the requested date, and paused state, without promising internal tick order. `advance` requires positive whole days. Visible events appearing during a fast-forward remain pending and unselected; the requested interval must still reach its exact paused deadline.
- Condition/event waits check immediately, then at positive whole-day increments, default 1. Require nonnegative integral `timeoutDays`; zero checks once. Shorten the last increment to the exact deadline. A completed game-time interval without success is a behavioral failure. A host deadline first means incomplete execution. Each iteration has distinct evidence under the outer wait's unchanged deadline.
- Direct firing returns a tagged pending-choice or completed-only FiredEvent. A pending result must identify the new instance associated with that invocation, including the outer instance in immediate same-definition recursion. An older matching pending event, the last nested event, or a native acceptance acknowledgement is insufficient.
- Hidden choice-free events can return completed-only handles. A visible event without selectable options may still be pending; do not infer completion merely from an empty option list. `choose` accepts FiredEvent or PendingEvent, but rejects completed-only, stale, already-selected, wrong-owner, or currently nonselectable requests with the appropriate reason.
- Named selection uses the normal engine path on the actual live player-owned instance, including current option validity, option effects, and subsequent `after` behavior. Preserve unrelated pending events. Missing/ambiguous post-fire identity is incomplete if mutation may have occurred.
- Direct fire establishes direct-invocation behavior, not natural firing eligibility. Supply required FROM explicitly. Delayed effects, scheduled follow-ups, naturally occurring events, and mean-time-to-happen events require explicit advancement/waits. Multiple matching pending instances are ambiguous. A bounded wait does not promise a random event will appear.
- AI defaults off and is established by readback before supported test execution. Conditionally change it once when needed; repeat requests for the established state are no-ops. Suite AI mode then stays fixed. Fixture load hooks can precede the supported readiness/AI boundary; no AI-before-all-load-hooks claim is made.
- Randomness is inherited from the fixture. There is no deterministic replay, seed-control, automatic retry, trial-count, or statistical guarantee.

See [Define event execution, time, randomness, and AI policy](https://linear.app/unnamed-system/issue/SDK-415/define-event-execution-time-randomness-and-ai-policy) and [Verify recursive fire identity and player-country event coverage](https://linear.app/unnamed-system/issue/SDK-441/verify-recursive-fire-identity-and-player-country-event-coverage).

### 9. First-release capability coverage

Priority describes release scope, not proof status. Every included capability requires native evidence on Windows 4.4.6 and integration through its production runner. The final acceptance decision includes the P1 readers as well as every P0 requirement. Mac 4.5 evidence supplies mechanisms and test cases; it does not qualify Windows implementations or prove that version-specific layouts and scope behavior are unchanged.

| Coverage                                | Included contract                                                                                                                                                                                                                           |
| --------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Prepared effects and boolean conditions | Player/non-player countries and colonized/uncolonized planets. Ordinary SDK scripts, typed vanilla definitions, fixed arguments, and explicit unchecked references use the same execution route.                                            |
| Script contexts                         | Natural ROOT/PREV and ordinary nested navigation; one explicit country FROM, including a distinct country. Navigation inside scripts may reach kinds that have no host Binding API.                                                         |

- Resource keys resolve against the loaded world. A resource's mod origin does not require a different numeric reader. The current 4.4.6 identifier package contains 26 vanilla resource keys; qualify that complete set on Windows. Mac 4.5 native evidence includes two custom resources and their absence in a later fresh world, providing controls to repeat on Windows. For later Apple Silicon support, derive coverage from the selected 4.5 build's inventory rather than assuming the count or keys stay unchanged.
- Type-known target/context/option mismatches fail statically. Runtime checks still enforce identity, kind, lifetime, ownership, context, and operation capability when types are bypassed. Handles cannot be reconstructed from serialized reports.
- Validate the requested operation and relevant live facts. Do not maintain an event-body certification list or trigger/effect semantic whitelist. An SDK method, symbol, or signature match alone does not establish native support. Explicit unchecked references retain their author-asserted status.
- Distinguish implemented-and-verified, implemented-but-unverified, unsupported, and native-incompatible capability states. Never silently skip, emulate, downgrade a requirement, or extend the unverified-game switch into a capability bypass.

### 10. Adapter factory, native dispatch, and protocol

- Only the adapter factory discovers the installation/host, selects the OS/build implementation, and applies compatibility/verification policy. Composition injects its uniform interface. Execution, supervision, results, and reporting do not branch on platform/build or import native implementations. Report supplied identity metadata unchanged.
- Shared policy stays in the runner. Reusable OS/native machinery and game-build operations stay separate behind adapters. Each build assumption has one authoritative home linked to discovery rationale and evidence. Mechanism changes may require operation implementations, not merely offset tables.
- The uniform adapter covers ownership, orphan recovery, installation revalidation, launch, readiness, game operations, evidence collection, disposal, and ownership release. Keep partial-launch ownership/session tokens so failures remain recoverable. The supervisor retains independent deadlines and disposal; the ordinary operation channel cannot be the only cleanup path.
- Keep neutral commands operation-specific: effect invocation, condition evaluation, locator resolution, resource reading, advancement, firing, pending-event inspection, and selection. Author commands contain no native addresses, offsets, console commands, or OS process-control authority.
- Journal run/attempt/suite/world/phase/test/step/invocation identity before dispatch. Child wait operations also carry parent and iteration identity. Native acceptance, script evidence, completion, observations, and assertions remain separate facts.
- Invoke fixed prepared scripts at the verified native engine boundary. Associate generated start/result/end markers with the active invocation in the native execution context. Require consistent script identity, expected markers/result, and native completion. Repeated scripts reuse bytes, never invocation IDs. Log arrival times, nearest markers, or the assumption of one outstanding request are insufficient.
- Generated marker tokens contain generated identity only. Keep author display labels and assertion prose on the host. Preserve SDK scope routing and fixed script arguments; runtime bindings and invocation identities are control metadata, not script scalar substitution.
- Use versioned, length-delimited UTF-8 JSON frames on private control/evidence channels. Check version, length bounds, required fields, source sequence, and identity. Buffer partial frames; partial EOF is missing evidence. Keep raw logs and large assets as referenced files.
- Each record retains source/record identity, sequence, applicable invocation, receipt time, and captured facts. Identical duplicates are harmless; conflicting duplicates fail validation. Stale world/run/phase records cannot establish current completion. Retain raw, partial, and late records. Late completion does not clear a deadline or reopen execution.
- Structured safe rejection reasons cover unsupported operation, missing/ambiguous/wrong-kind object, invalid binding, missing global target, event not pending/not player-owned/without a choice, nonselectable option, and invalid arguments. Inactive phase, overlap, foreign authority, recording failure, timeout, channel loss, and uncertain post-mutation correlation remain distinct contract/infrastructure outcomes.

Prevent unintended handle duplication or inheritance so owner-helper exit closes the last handle and terminates the owned game. Owner-helper loss still requires exit confirmation, retained evidence, and resource reconciliation before another suite. Document the demonstrated prerequisite and add a bounded readiness check where it can be observed reliably. Report a Steam prerequisite failure only when evidence establishes it; a missing game-load marker alone remains a launch/readiness timeout with retained observations. The historical Mac Steam stalls motivate this check but do not establish the Windows cause or required client state.
- Installation lookup precedence is explicit path, nonempty `STELLARIS_PATH`, then platform default. An invalid explicit choice fails. Select exactly one native-compatible adapter; distinguish unsupported host, native incompatibility, ambiguous match, and missing verification. Fix selection for the run and revalidate the installation before each suite; do not silently switch builds.
- Document how authors can obtain the exact supported build when Steam's default build changes. Verify any available 4.4.6 rollback branch on Windows and record its actual branch name, build ID, executable hash, and verification date with the compatibility matrix. Incompatibility guidance names only a verified access path; if no supported build is available through Steam, state that limitation instead of inventing a branch or recommending the unverified override. Do not ship a Windows 4.5 adapter as a gap-filler in this release.
- Refuse missing verification by default. `PDX_TEST_ALLOW_UNVERIFIED_GAME=1` waives only the missing verification record and keeps unverified status visible. Unset, empty, and `0` mean false; other nonempty values are configuration errors. It cannot bypass unsafe interfaces or a missing/ambiguous adapter.
- A separate supervisor holds an OS exclusive lock for machine-wide runner exclusion through cleanup. Journal launch intent and positively identified owned resources, including process creation identity, before creation can leave an orphan. A competing runner refuses promptly instead of waiting. Refuse launch while an ordinary user-owned Stellaris game is running. If another ordinary game appears during a run, detect it where the platform permits, stop the run, and dispose only of the positively identified runner process. Never infer ownership from process name, PID alone, or record age.
- Use private settings, logs, saves, selections, dependencies, and outputs. Command loss causes the surviving supervisor to dispose and preserve evidence. There is no permanent background service or immediate-cleanup promise after supervisor loss. On the next invocation, acquire exclusion and reconcile owned orphan resources before starting fresh suites. Distinguish stale records from surviving owned processes; ambiguous identity/disposal refuses launch with precise recovery instructions. Keep the interrupted run's evidence. Do not resume a shared live world or resend an uncertain action. Bounded readiness polling and rereading existing evidence are permitted.
- Cancellation immediately stops new game-action admission. Apply bounded termination, forced-exit confirmation, and final evidence collection using independent supervision. Cancellation promises neither rollback nor an exact stopping date during native execution. Confirm owned-process exit before treating disposal as complete. Unconfirmed exit prevents another suite/run from claiming isolation.
- Preserve evidence for every run. Keep failed/interrupted profiles. Remove successful disposable profiles only after required evidence is secured; `keepAll` retains them too. Pruning is explicit, never automatic age-based deletion. Failed profile deletion and an unconfirmed live process are separate outcomes; continuation still requires confirmed isolation and evidence safety.

Native Apple Silicon is a later support target. Start that support effort when Stellaris 4.5 is released with native Apple Silicon execution, cwtools has matching rules, and the SDK has integrated and qualified those rules and identifiers. Select and pin the then-supported native Mac game build and independently qualify its adapter and complete public contract. Existing 4.5 beta probes remain historical evidence, not an automatic support claim. Rosetta 2 and Intel Mac adapters are not planned.

[Define supported environments and game-version compatibility](https://linear.app/unnamed-system/issue/SDK-419/define-supported-environments-and-game-version-compatibility) and [Define the runner lifecycle and failure recovery](https://linear.app/unnamed-system/issue/SDK-417/define-the-runner-lifecycle-and-failure-recovery) supply the shared policies, as amended by suite isolation, execution-process ownership, and this local Windows-first decision. ### 13. Results, diagnostics, and evidence

- Preserve behavior (`not-assessed`, `passed`, `failed`) separately from execution (`not-started`, `complete`, `incomplete`). Selection and omission are separate dimensions. Retain multiple failures; do not apply a single verdict precedence that erases facts.
- `RunResult` carries a schema version, run identity, overall success, execution state, collection plan, captured inputs, selected adapter metadata, suites, failures, diagnostics, cleanup/finalization outcomes, and evidence-location outcome. Return unavailable evidence explicitly if storage failed; never invent a path.
- Suite/test/phase records retain process/world identity, starting fixture and AI evidence, ordered hooks/tests, operation trees, acceptance and terminal evidence, exact observations/assertions, timing, deadlines, causes, and omission reasons. Names are display data, separate from identities.
- Reconstruct authoritative results from the append-only supervisor journal and retained bridge/script evidence. A terminal marker cannot replace missing checks. A mismatch followed by a crash remains behavior failed and execution incomplete. Later hook, diagnostic, or cleanup failure does not rewrite established test behavior.
- Overall command success requires runnable selected work, qualifying successful behavior, required completion, successful disposal/finalization, secured evidence, and no run-failing hook/infrastructure error. Report why selected work did not execute. Terminal and JSON reports preserve the same distinctions.
- Script errors remain diagnostics by default. Strict mode counts all script errors collected from the run's isolated game processes, including startup and dependency errors; there is no baseline subtraction or diagnostic allowlist. They fail the run without rewriting test behavior, and completed diagnostic collection is required before strict success. Attribute errors to a specific test only with supporting evidence; otherwise keep suite/run attribution. Do not hide fixture/mod warnings or other unfiltered raw diagnostics.
- A counted script error is a distinct engine-issued error record reporting failure to parse, validate, or execute game script. Count a multiline record once; repeated occurrences remain separate errors. Re-reading the same source record does not add another occurrence. Merely appearing in an error log does not make a workshop, store, or other non-script diagnostic a script error. Define and verify the exact record boundaries and recognized diagnostic families against the pinned Windows build, including explicit `Script Error:` records; do not assume that prefix is the complete classifier. Retain raw records, source identities, classification, and classifier revision. If evidence loss or an unsupported script-diagnostic format prevents complete classification, report that incompleteness and refuse strict success rather than report zero errors.
- Before final publication, freeze the build-specific classifier and measure a DLC-free vanilla startup plus the runner's baseline fixture/support mod through readiness, a completed check, and final collection. Preserve the raw diagnostics and counted totals for each. This is a feasibility measurement, not a baseline to subtract from later runs. If unavoidable vanilla or runner errors prevent the required clean strict success, record the blocker for an explicit decision; do not add an allowlist, reclassify errors to obtain green results, or weaken strict mode silently.
- Retain generated scripts, input hashes and order, resolved configuration, exact adapter/build/bridge identities, raw/partial records, observations, expected/actual comparisons, diagnostics, timings, earlier attempts, omissions, and cleanup outcomes. Reference installed game files and source fixtures by identity rather than copying them into every evidence bundle. Never prune the only surviving evidence copy. Secure final logs after game exit. Free-text diagnostic evidence cannot stand in for correlated completion.

See [Define the test result and diagnostic protocol](https://linear.app/unnamed-system/issue/SDK-416/define-the-test-result-and-diagnostic-protocol) and its suite amendment.

These are fixed release gates on the stated reference machine, not provisional targets or timing guarantees for every author's hardware. Measure early; changing a target requires a deliberate evidence-backed decision. Historical Mac shared-suite measurements were 25.26–27.99 seconds for launch, 0.605–0.779 seconds for disposal, and a 0.195 ms assertion median across 41 calls. Later differently instrumented Mac compatibility runs reached 2.19 seconds for cleanup. These measurements explain the original targets, not Windows performance. The Windows spike used different fixtures, DLCs, and instrumentation and did not qualify these benchmarks. Measure all targets again through the production Windows runner. Fresh-process isolation has a cost per suite. At the 45-second launch limit, twenty sequential suites spend fifteen minutes in launch alone, before test work and disposal. This illustrates the chosen isolation cost; it is not a measured runtime or a total-run bound. In-process save reload is a separate future investigation into engine-state isolation and does not change the first-release fresh-process contract.

## Out of Scope

- Offline simulation, installation-free runtime execution of vanilla definitions, an SDK-owned game state/event scheduler, and compatibility with the retired interpreter API.
- Native Apple Silicon support in the first release. It is a later extension gated on the Stellaris 4.5 release, matching cwtools/SDK authoring support, and independent native qualification.
- Rosetta 2 and Intel Mac adapter development. The planned Mac target runs Stellaris 4.5 natively on Apple Silicon; no intermediate Rosetta adapter is needed.
- CI qualification including self-hosted CI, other platforms/architectures/builds beyond the Windows x64 4.4.6 first-release target, concurrent logged-in accounts, and a privileged cross-user broker.
- Dedicated enforcement of session/account/non-interference conditions, visibility/focus-breach detection, deliberate-window-interference defenses, true headless execution, and general semantic UI selectors.
- Vitest integration as the real-game execution owner, nested suites, implicit file-level suites, parallel game execution, automatic resets between tests, and fixture/AI changes within a suite.
- Replacing fresh suite processes with in-process save reload, or maintaining a Windows 4.5 adapter as an unverified gap-filler while SDK authoring remains on 4.4.6.
- Runtime script-body generation or scalar argument substitution, direct effect-returned bindings, arbitrary runtime numeric-ID lookup, direct save-file editing or construction, deterministic replay/seed control, automatic retries, statistical trials, or atomic multi-read snapshots.
- P2 host scope kinds, other event kinds and non-player direct firing, externally supplied ROOT/PREV, deeper FROM chains, and arbitrary direct numeric-property readers such as fleet power, population, or opinion. These limits do not prohibit normal engine navigation or boolean checks inside supported scripts.
- Event-body semantic certification, trigger/effect emulation or whitelists, mandatory skip/downgrade fallbacks, and capability bypass through the unverified-game override.
- Required model trials, known-port/unseen-build evaluations, model-success thresholds, and fixed model time/cost budgets.
- Implementing or shipping the production framework, publishing the specification, or creating implementation tickets as part of this local drafting step.
