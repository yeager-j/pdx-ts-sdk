Stellaris has one modifier system, but several definitions participate in it.
The names are similar because they describe different parts of the same flow:

| Part              | What it does                                                                                           |
| ----------------- | ------------------------------------------------------------------------------------------------------ |
| Resource block    | Declares a cost, production, upkeep, or logistics transaction and selects an economic category.        |
| Economic category | Groups related transactions and asks Stellaris to generate modifier-key families for them.             |
| Modifier field    | Supplies a number for one modifier key on a technology, building, static modifier, or other source.    |
| Scripted modifier | Registers one custom modifier key and its display metadata for a calculation that reads it explicitly. |
| Static modifier   | Gives a name to a bundle of modifier values so another system can apply and remove the bundle.         |

The most important distinction is between **grouping transactions** and
**supplying modifier values**. An economic category groups transactions. It
does not grant a bonus. A static modifier or ordinary `modifier` field can
supply a bonus, but it does not decide which resource transactions belong to a
category.

An economic category can also declare triggered modifier rows. The triggered
field name selects the transaction family (`cost`, `produces`, `upkeep`, or
`logistics`); each row owns a key, and its `modifierTypes` selects `add` or
`mult`. Select the source category, then the owned row key:

```ts
modifier.economic(expeditions).triggered(shipyardOperations).cost.mult(-0.1);
modifier.economic(expeditions).triggered(shipyardOperations).resource("energy").cost.mult(-0.2);
```

The emitted modifier starts with the selected row key, not the source category:
`<row-key>_cost_mult` and `<row-key>_energy_cost_mult`. The SDK records both
economic-category references, so omitting either owned definition fails the
build. Resource-specific families can expose `add` and `mult`; broad families expose
only `mult`.

## Follow an economic modifier from transaction to value

An economic modifier has four moving parts:

```text
resource transaction selects a category
  -> category generates modifier-key families
  -> content supplies a value for one generated key
  -> Stellaris applies that value to matching transactions
```

The example's survey edict selects the owned `expeditions` category for its
activation cost and energy upkeep:

```pdxscript
resources = {
  category = deep_space_logistics_economic_category_expeditions
  upkeep = {
    energy = 5
  }
}
```

The category asks Stellaris to generate multiplicative cost and upkeep
modifiers. That creates keys such as:

```pdxscript
deep_space_logistics_economic_category_expeditions_energy_upkeep_mult
```

The edict's own modifier field supplies a value for that key:

```pdxscript
modifier = {
  deep_space_logistics_economic_category_expeditions_energy_upkeep_mult = -0.25
}
```

The SDK derives the same generated key from the owned category and resource:

```ts
modifier.economic(expeditions).resource("energy").upkeep.mult(-0.25);
```

The owned category is a content reference, so the SDK derives the key and
records that category reference for the build's missing-definition check. The
resource id remains an open game resource name. The economic category connects
that value to every resource transaction that selects `expeditions`.

## A category generates a family, not one fixed key

[`generateAddModifiers`](/reference/economic-categories/) and
[`generateMultModifiers`](/reference/economic-categories/) choose among four
transaction kinds: `cost`, `produces`, `upkeep`, and `logistics`. Every
generated family can contain resource-specific keys. Multiplier families also
get a broad key without a resource in its name. For example, the
`expeditions` family could include both `expeditions_upkeep_mult` and
`expeditions_energy_upkeep_mult`. There would be no matching broad
`expeditions_upkeep_add` key.

Only generate the operations that consumers need. The declaration creates the
legal family; it still does not create a resource transaction or assign a
value.

Categories can have parents. A transaction in a child category receives the
applicable multiplier families from its ancestors as well as its own category.
Vanilla's economic-category guide states an important exception: additive
modifiers do not inherit into child categories. This prevents one additive
bonus from cascading through a large category tree.

For example, an `expeditions` child could inherit broad multiplier families
from a `field_operations` parent while also generating its own narrower
families. A value for the child would not change other field operations.

## Scripted modifiers are explicit extension points

A [scripted modifier](/reference/scripted-modifiers/) does not generate a
transaction family. It registers one named value that another calculation
must read explicitly.

The example's `expedition_efficiency_mult` shows both halves. Its definition
describes a beneficial, percentage-formatted value in the country modifier
category. The edict's modifier field supplies a number:

```pdxscript
deep_space_logistics_scripted_modifier_expedition_efficiency_mult = 0.20
```

The edict's upkeep calculation then reads that exact key through a script
value:

```pdxscript
mult = modifier:deep_space_logistics_scripted_modifier_expedition_efficiency_mult
```

Without that explicit read, the registered key does nothing. Its name ending
in `_mult` is a convention that describes the intended use; the
scripted-modifier definition itself does not multiply anything.

Use a scripted modifier when you control a formula and need one configurable
value with normal modifier display behavior. Use an economic category when
you want Stellaris's resource system to generate and apply the standard
cost/production/upkeep/logistics families.

## Static modifiers package values; they do not define their meaning

A [static modifier](/reference/static-modifiers/) is a named bundle. Its body
can contain generated economic keys, scripted-modifier keys, ordinary modifier
keys, or a mixture:

```pdxscript
deep_space_logistics_static_modifier_route_disruption = {
  deep_space_logistics_economic_category_expeditions_energy_upkeep_mult = 0.50
  deep_space_logistics_scripted_modifier_expedition_efficiency_mult = -0.10
}
```

The economic category gives the first key its connection to expedition upkeep
transactions. The scripted-modifier declaration and its consumer give the
second key its meaning. The static modifier only packages the two values so an
event, situation, decision, or other caller can apply them together.

Ordinary content fields can supply the same values directly. Do not create a
static modifier when a technology, tradition, building, civic, or other
long-lived definition already owns the modifier block.

<Aside type="caution" title="The receiving scope still matters">
  Modifier values live on game objects and may propagate down the object hierarchy. The economic
  category's `modifierCategory` and a scripted modifier's `category` classify where generated or
  registered values can be read; they do not apply a value to an object. The caller that owns or
  applies a modifier still decides its host. The SDK checks known modifier names and many scoped
  modifier fields, but it does not currently prove the host scope of a static modifier.
</Aside>

## Choose the smallest authoring surface

| Goal                                                               | Use                                                                                                        |
| ------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------- |
| Change an existing economic transaction family                     | An existing generated modifier key in an ordinary modifier field.                                          |
| Create a new group of resource transactions                        | An [economic category](/reference/economic-categories/), then assign that category to each resource block. |
| Expose one custom value to a formula you control                   | A [scripted modifier](/reference/scripted-modifiers/) plus an explicit consumer.                           |
| Apply or remove several modifier values as one named effect        | A [static modifier](/reference/static-modifiers/).                                                         |
| Give a technology, building, tradition, or civic a permanent bonus | That definition's own `modifier` field.                                                                    |

When adding a custom economic category, use the owned recorder seams shown in
the example: `modifier.economic(category).resource(resource)` derives each key
from the declaration. Use `modifier.scripted(item).set(value)` for an owned
scripted modifier. `raw` and `unchecked` remain available for external or
deferred names.

Finally, test the whole path in Stellaris: the resource block, category
inheritance, value source, receiving scope, tooltip, AI budget behavior, and
save/load. Type checking can prove the SDK shape and known names, but it does
not run the game's economic calculation.
