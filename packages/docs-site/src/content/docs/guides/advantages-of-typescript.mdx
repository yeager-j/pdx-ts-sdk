The SDK runs ordinary TypeScript at build time. That gives mod authoring the
same tools as any other program: variables, functions, modules, arrays, loops,
conditionals, arithmetic, and tests.

These tools generate the mod; they do not run inside Stellaris. The game still
receives ordinary PDXScript. [Triggers and effects](/guides/triggers-and-effects/)
explains that boundary in detail.

## Build different variants deliberately

A build-time condition can include content in one output and omit it from
another. [Triggers and effects](/guides/triggers-and-effects/) closes with the
`MOD_DEBUG` example: an environment variable decides whether an event's
`immediate` block records a log line. The same switch can select
development-only events, extra assertions, instrumentation, or balance
profiles.

Treat the input as part of the build, not invisible machine state: document
it, print the selected profile, and pin it in automated builds when
reproducible output matters. Two builds from the same commit can produce
different bytes when their environment differs.

Use [`scope.if`](/guides/triggers-and-effects/#use-scopeif-for-an-in-game-branch)
instead when the decision depends on game state.

## Generate a family with a loop

Related definitions often follow a rule. A technology ladder may scale its
cost, advance its tier, and require the previous technology. TypeScript can
state that rule once:

<PairedExample name="technology-ladder" />

One foundation technology, then five generated upgrades, each requiring the
one before it. The PDXScript tab contains six ordinary technology definitions.
Neither the loop nor the `previous` variable exists in the built mod.

This is more than shorter syntax. The prerequisite chain is constructed from
the same values placed in the Feature, so renaming or reordering the generator
does not leave a second list of string ids to update.

The output order is the SDK's, not the loop's. Emission order is a function of
content — definitions sort by emitted path and id — so the foundation
technology appears last in the file even though the loop creates it first.
Lists inside one definition, such as `prerequisites` or event options, keep
their written order.

## Generate a typed cross-product

Repetition multiplies quickly when every category needs its own variants.
Three empire kinds with four ambitions each require twelve event options in
PDXScript. Keep the differences in typed data and generate the repeated shape:

<PairedExample name="mapped-event-options" />

This example derives the closed `EmpireKind` union from `EMPIRE_KINDS`, keeps
the differences in one typed table, and forms the cross-product with
`flatMap(...map(...))`: one option for every ambition in every empire kind.
Each option receives a stable combined key, the correct visibility Trigger,
localized text, and its reward effect. The PDXScript tab shows all twelve
ordinary option blocks; at game time each empire sees the four whose Trigger
matches it.

The types turn design assumptions into checks. Adding another value to
`EMPIRE_KINDS` makes both records fail typechecking until the new empire kind
has ambitions and a condition. Removing one ambition from a group breaks the
four-entry tuple. The data cannot quietly fall out of step with the generator.

The `as const` preserves the table's literal keys and values while `satisfies`
checks its shape without widening those literals. Named object fields are also
safer to maintain than positional rows such as
`["horizon_corps", "influence", 25]`: readers do not have to remember which
column means resource or amount, and swapping two values of the same primitive
type is less likely to pass unnoticed.

## Extract helpers without inventing a second language

The ladder above computes cost and display name inline. Both are ordinary
rules, so both can move into named functions:

```ts
function scaledCost(level: number): number {
  return 1000 * 2 ** level;
}

function displayName(calibration: string): string {
  return `${calibration} Observatory Arrays`;
}
```

Helpers can live in another module, accept typed SDK values, and have direct
unit tests. Constants and tables can be shared the same way. There is no macro
system or template format to learn alongside TypeScript.

Keep the abstraction at the level of the repeated idea. A helper named
`scaledCost` communicates a rule; a generic function with many unrelated
options can hide the Stellaris definition it was meant to clarify.

## Test script behavior without launching the game

Authored events and triggers are TypeScript values, so a normal Vitest suite
can import them and assert on their shape directly — the cross-product above
can be tested for its twelve options without any harness.

For running script, `@pdx-ts/sdk-testing` provides a small interpreter for
verified trigger and effect semantics. [Testing your mod](/guides/testing-your-mod/)
shows the fixture workflow and carries the caution that the harness is an
unstable, deliberately incomplete API. Its limits matter here: delivery runs
no option selection, so the fixture refuses an event whose options carry
effects. Test such an event as a value, not through delivery.

## Prefer rules over copied boilerplate

TypeScript generation works best when the repeated content has a real
relationship:

- a progression where each item depends on the previous one;
- a fixed shape populated from a data table;
- a shared calculation or naming rule;
- a build profile that deliberately includes or excludes content.

Write unrelated definitions explicitly. The goal is not the fewest lines of
source; it is one clear source of truth for each decision, with ordinary
PDXScript as the inspectable result.
