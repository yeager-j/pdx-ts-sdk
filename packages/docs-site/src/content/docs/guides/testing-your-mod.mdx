:::caution[Unstable API]
`@pdx-ts/sdk-testing` is unfinished. Its public API and modeled semantics will
likely change significantly as the interpreter grows. Expect to update tests
when upgrading the package.
:::

`@pdx-ts/sdk-testing` interprets selected triggers and effects outside
Stellaris. It gives event chains fast unit tests over small, declared fixture
worlds, without launching the game or using the console.

The interpreter is deliberately not a complete Stellaris simulator. It models
only semantics that have been verified and throws when a test reaches anything
else. A passing test says the modeled script logic does what you intended; it
does not prove every game system surrounding that logic.

## Fire an event in a fixture

Projects created by `create-stellaris-mod` include a colocated example test.
The normal workflow is to import an authored event, build the smallest world
state it needs, fire it, and inspect the resulting handles:

```ts
import { fixture } from "@pdx-ts/sdk-testing";
import { describe, expect, it } from "vitest";

import { flags } from "../flags.ts";
import { welcome } from "./example.ts";

describe("the welcome event", () => {
  it("flags the country and pays out the first time", () => {
    const world = fixture({ countries: [{ name: "Player" }] }, { events: [welcome] });
    const player = world.country(0);

    world.fire(welcome, player);

    expect(player.hasFlag(flags.my_mod_welcomed)).toBe(true);
    expect(player.resource("influence")).toBe(50);
  });
});
```

The first argument to `fixture` declares state such as global flags,
countries, owned planets, fleets, situations, archaeological sites,
technologies, resources, and storage limits. It does not silently fill in a
real galaxy. If the behavior depends on a fact, put that fact in the fixture.

The second argument registers every event the world may deliver. `world.fire`
accepts only the exact registered event, a matching scope handle, and—when the
event declares a `FROM` contract—a matching `from` handle. These checks keep a
test from firing an event in a context its definition cannot receive.

Handles read the current fixture state, so the `player` value above sees the
flag and resource changes after delivery. Failed interpretation is
transactional: the fixture does not retain half of an effect sequence when a
later entry throws.

## Advance delayed event chains

An event effect can queue another registered event. Move the fixture clock to
deliver due fires:

```ts
const world = fixture({ countries: [{ name: "Player" }] }, { events: [entry, followup] });

world.fire(entry, world.country(0));
world.advance(30);

expect(world.day).toBe(30);
expect(world.fired.map((record) => record.id)).toEqual([entry.id, followup.id]);
```

`advance(days)` accepts a non-negative safe integer number of days. It delivers
every queued event due in that window, including events queued by another
delivery. The fired log records each event id, day, scope, `FROM`, and whether
the fire came from the harness or an effect.

Advancing the clock does not simulate the rest of the galaxy. In particular,
the harness does not tick situation progress, stages, completion, or
`on_monthly`. Crossing a month boundary while a non-static situation exists
therefore throws. Keep the test within the month, test the weight arithmetic
directly with `evaluateWeightBlock`, or mark fixture progress as static when
the chain genuinely does not depend on it.

For a `random_list`, supply zero-based branch indices instead of accepting a
nondeterministic result:

```ts
world.fire(randomEvent, world.country(0), { arms: [1, 0] });
```

The plan is consumed in execution order, including delayed events in the same
chain. The test fails if it needs an arm you did not supply or if any supplied
choice remains unused.

## Event delivery runs only `immediate`

The fixture can honestly deliver only events whose behavior it implements.
Delivery runs the event's `immediate` block. It does not:

- check an event-level `trigger`;
- choose an option or run option effects;
- run `abortTrigger`, `abortEffect`, or `after`; or
- schedule `meanTimeToHappen` events.

Registering an event with a trigger, abort behavior, an `after` block, or
option effects throws immediately, before a test can record a fire whose real
payoff was skipped. An option with only a name, icon, or gate is allowed
because there are no option effects to omit. `meanTimeToHappen` remains inert:
the fixture will not schedule that event, but a test may fire it explicitly
when it wants to exercise the event's immediate effects.

`fireOnlyOnce` is enforced: delivering the same event a second time in one
fixture throws. The game does not document every detail of how that count is
scoped, so use a fresh fixture when a test needs an independent firing rather
than relying on an invented counting rule.

## `SimScopeName` is narrower than `ScopeName`

The SDK can author events and script for about forty Stellaris scope kinds.
The testing package models five:

```ts
type SimScopeName = "country" | "planet" | "fleet" | "situation" | "archaeological_site";
```

Each simulated scope has concrete state and verified transitions. A
leader-scoped event, for example, is valid SDK content but cannot enter a
fixture today. Registering it throws a diagnostic that lists the modeled
scopes. The harness does not approximate it as a country or provide an empty
leader object, because either choice could make incorrect logic pass.

The same distinction applies within supported scopes. A planet in the fixture
can link to its owner because that relationship is modeled; an arbitrary
generated scope link is not assumed to work merely because the SDK can emit
it.

## Unknown script semantics throw

The interpreter uses a reviewed whitelist for Trigger keys, effect keys,
structural blocks, iterators, scope links, and event fields. The implemented
slice includes common operations such as:

- country and global flags;
- technologies, resources, deposits, and owned planets;
- situation variables, progress, approaches, and targets;
- `AND`, `OR`, `NOT`, `NOR`, and `NAND`;
- runtime `if` branches, `hidden_effect`, and forced `random_list` branches;
- `every_owned_planet`; and
- immediate and delayed event fires with checked scope and `FROM`.

This list is illustrative, not a promise that every related Stellaris key is
modeled. If a Trigger, effect, iterator, link, scripted binding, or event field
is outside the whitelist, the interpreter throws `InterpreterError` with a
coverage summary. It also checks the complete Trigger before evaluating it, so
an unknown branch cannot hide behind short-circuit behavior.

This refusal is the main safety property of the package. A missing simulator
feature is visible work; guessed semantics can produce a green test for a
world Stellaris would never create.

## Evaluate and explain Triggers directly

Use `evaluate` when a test concerns a Trigger rather than a whole event:

```ts
import { evaluate, explain, renderExplanation } from "@pdx-ts/sdk-testing";

expect(evaluate(canReceiveSignal, player)).toBe(false);
console.log(renderExplanation(explain(canReceiveSignal, player)));
```

`explain` returns a tree with the result of each modeled subcondition.
`renderExplanation` turns it into a readable trace:

```text
✗ AND
  ✓ has_global_flag = lattice_awake — set globally
  ✗ has_country_flag = heard_the_hum — absent on country "Player"
```

This is often more useful than one final `false`: it identifies which authored
condition did not match the fixture.

## Add the optional Vitest matchers

The core interpreter has no test-framework dependency. Install its optional
Vitest matchers in a setup file:

```ts
// vitest.setup.ts
import { installMatchers } from "@pdx-ts/sdk-testing/matchers";

installMatchers();
```

Then configure `setupFiles: ["./vitest.setup.ts"]` in `vitest.config.ts`. The
matchers add focused assertions:

```ts
expect(world.fired).toContainEvent(followup, { day: 30 });
expect(canReceiveSignal).toHoldFor(player);
```

`toHoldFor` uses the same explanation tree in its failure message, while
`toContainEvent` prints the fired-event log when no matching delivery exists.
Use ordinary Vitest assertions for fixture state; the handles expose flags,
resources, technologies, deposits, variables, progress, and the other state
the interpreter actually models.
