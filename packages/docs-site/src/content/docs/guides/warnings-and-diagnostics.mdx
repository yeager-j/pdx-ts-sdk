The SDK reports mod problems through two channels:

- It **throws** when it can prove the requested mod is invalid or unsafe to
  emit.
- It returns non-blocking **warning data** on `mod.warnings` when the build can
  continue but needs the author's attention.

Mod authoring and the Fold do not print those diagnostics. Your build script
decides how to display warnings, whether CI rejects selected codes, and how a
thrown error reaches the command line.

## Invalid builds throw

An authoring call may throw immediately when its own input is invalid. For
example, an Asset source must exist and be a regular file, a configuration
prefix must have the required shape, and an explicit localization key must be
valid when it is declared.

Other failures need the complete set of selected Features, so the
[Fold](/guides/the-pipeline/) throws from `mod.compile`. Representative cases
include:

- duplicate content or event ids;
- missing required fields or localization;
- authored references whose targets are not in the build;
- two different values for one localization key;
- an Asset item referenced by GFX but not placed in a Feature;
- duplicate, aliased, reserved, or file-versus-directory output paths;
- output paths that collide with known vanilla files; and
- a vanilla patch whose replacement or winning filename cannot be proved.

These are not warnings because continuing would produce a mod the SDK already
knows is incomplete, ambiguous, or unsafe. Catch an error only when the build
script can add useful context or perform cleanup; do not catch it merely to
continue rendering.

Rendering should normally succeed once the Fold returns a `PureMod`. Writing
or installing can still throw `MaterializationError` when the destination is
unowned, has drifted, contains a conflicting foreign file, is busy, or cannot
be replaced safely. That failure protects files already on disk; deleting the
error and retrying does not resolve the underlying conflict.

## Successful builds can carry warnings

Read warnings from the immutable `PureMod` returned by `mod.compile`:

```ts
const built = mod.compile(features);

for (const warning of built.warnings) {
  console.warn(`warning (${warning.code}): ${warning.message}`);
}

const rendered = render(built);
await write(outDir, rendered);
```

This is the pattern generated by `create-stellaris-mod`. The SDK returns the
data; the project entry point chooses to print it. The install entry point has
its own warning loop because it calls the shared build directly and must not
depend on another command having displayed the warnings.

Warnings do not stop rendering, writing, or installing. Display all of them in
local builds. In CI, decide explicitly which codes should fail the build for
your project instead of treating the absence of an exception as the absence
of diagnostic work.

:::note[One operational notice]
`stellaris.load()` may print a direct notice if its optional parse cache cannot
be written and the loader must reparse on each build. That notice concerns
loader performance, not mod validity, and is not a `ModWarning`.
:::

## `ModWarning` is a discriminated union

Every warning has a stable `code` and a human-readable `message`. The current
codes are:

| Code                      | Meaning                                                                                                                                              |
| ------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| `missing-prefix`          | A complete content id or event namespace does not carry this mod's prefix, so it may collide with vanilla or another mod.                            |
| `loc-quote-replaced`      | Localization text contained `"`; the output format cannot escape it, so the SDK replaced it with `'`.                                                |
| `unstable-desc-key`       | A modifier description has no `descKey`; its generated localization key depends on the description text and changes when that text changes.          |
| `unstable-option-key`     | An event option has no `key`; its generated localization key depends on the option name and changes when that text changes.                          |
| `loc-key-looks-like-text` | A field expects a localization key, but the supplied string contains spaces and looks like displayed prose.                                          |
| `assumed-patch-rule`      | A vanilla patch relies on resolver behavior that is not fully verified; the emitted patch header records the judgment.                               |
| `mismatched-vanilla-ids`  | The build explicitly accepted an installed game version different from the pinned `@pdx-ts/stellaris-ids` version, so some checked ids may be stale. |
| `unverified-asset-path`   | A raw GFX path matches neither an Asset captured by this build nor the available vanilla path inventory.                                             |

Most variants are the flat shape `{ code, message }`. An
`unverified-asset-path` warning also carries structured fields:

```ts
interface UnverifiedAssetPathWarning {
  readonly code: "unverified-asset-path";
  readonly message: string;
  readonly path: string;
  readonly field: string;
  readonly owner: string;
}
```

`path` is the normalized logical path when normalization succeeds, `field` is
the dotted GFX field such as `animation.animationmaskfile`, and `owner` names
the definition that wrote it. These fields let a build report or group the
problem without parsing prose.

Use the `code` discriminant to narrow the union:

```ts
import type { ModWarning } from "@pdx-ts/sdk";

function reportWarning(warning: ModWarning): void {
  if (warning.code === "unverified-asset-path") {
    console.warn(`${warning.owner}.${warning.field}: cannot verify ${warning.path}`);
    return;
  }

  console.warn(`warning (${warning.code}): ${warning.message}`);
}
```

The warnings array and its entries are frozen snapshots. Do not mutate them.
The Fold does not deduplicate warnings, so repeated authored problems can
produce repeated entries. Do not identify a warning by its array index or
depend on categories appearing in one fixed order; use `code` and the
structured fields instead.

## Respond to each warning at its source

Most warnings have a direct authoring fix:

- Add the mod prefix to an exact id or event namespace reported by
  `missing-prefix`.
- Replace a localization double quote yourself when punctuation matters.
- Add `descKey` to a modifier row or `key` to an event option before
  translations depend on the generated localization key.
- Pass displayed text through localization and give a loc-key field the key,
  not the text.
- Align `@pdx-ts/stellaris-ids` with the installed game version instead of
  relying permanently on `acceptGameVersion`.
- For an unverified Asset path, fix the spelling or put the file under the
  scaffolded `assets/` tree. If the path intentionally belongs to DLC or
  another mod, document that dependency and allow the warning deliberately.

An `assumed-patch-rule` warning describes the patch planner's evidence rather
than a typo in the authoring code. Keep it visible and verify the affected
behavior in game, especially after a Stellaris update.

## Make a deliberate CI policy

A strict project may reject every warning:

```ts
if (built.warnings.length > 0) {
  throw new Error(
    `Refusing to publish with warnings:\n${built.warnings
      .map((warning) => `- ${warning.code}: ${warning.message}`)
      .join("\n")}`
  );
}
```

Another project may allow specific external Asset paths while rejecting all
other warnings:

```ts
const allowedExternalPaths = new Set(["gfx/interface/partner_mod/icon.dds"]);
const blocked = built.warnings.filter(
  (warning) => warning.code !== "unverified-asset-path" || !allowedExternalPaths.has(warning.path)
);

if (blocked.length > 0) {
  throw new Error(blocked.map((warning) => warning.message).join("\n"));
}
```

Choose the policy in the project entry point or release command, close to the
decision to write or install. Keep ordinary local builds informative rather
than silent, and make exceptions by code with a reason a maintainer can review.
