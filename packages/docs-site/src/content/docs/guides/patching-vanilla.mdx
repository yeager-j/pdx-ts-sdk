A vanilla patch changes a definition that Stellaris already provides. The SDK
starts from the parsed vanilla object and re-emits a complete replacement.
Whole-object replacement is verified for technologies and buildings. For
megastructures, the SDK has confirmed that the later file wins, but not
whether the winner replaces the earlier object or merges with it. It assumes
replacement, warns you, and records the assumption in the emitted file; test
the patched object in game.

Patching real installed content normally starts from a local Stellaris
install: `stellaris.load()` reads the game files and returns the definitions
and file enumeration needed to build the replacement safely.

## Load vanilla and transform a definition

Create the patch with the `mod.patch<Type>` method for that registry, place it
in a [Feature](/guides/features-and-discovery/), and pass the same vanilla
view to `mod.compile`:

```ts
import { createMod, stellaris } from "@pdx-ts/sdk";

const mod = createMod({
  name: "Crystal Resonance",
  prefix: "crystal_resonance",
  supportedVersion: "v4.4.*",
});

const vanilla = stellaris.load();

const capitalPatch = mod.patchBuilding(vanilla.definition("building", "building_capital"), () => ({
  planetLimit: 2,
}));

const patches = mod.feature("vanilla_patches", [capitalPatch]);
const built = mod.compile([patches], { vanilla });
```

`stellaris.load()` finds the install from an explicit `installPath` option,
then the `STELLARIS_PATH` environment variable, then the platform's Steam
default; a failing explicit path is a loud error, never a silent fall-through.
It keeps a parse cache under `node_modules/.cache/pdx-ts-sdk`, which
`cache: false` disables. `viewFromFiles(files, options)` builds the same kind
of view from file contents you supply, with no install involved — use it in
tests or for controlled inputs.

`vanilla.definition(registry, id)` returns a parsed definition tagged with its
registry. TypeScript therefore rejects a parsed building passed to
`patchTechnology`, and the vanilla view rejects an id it did not load.

The callback returns only the fields you want to change, but its result is not
a partial object sent to Stellaris. The SDK replaces those fields in the
parsed body and carries every untouched entry into the emitted definition.
Fields the typed model does not interpret also pass through. This preserves
the source definition instead of guessing defaults for fields the patch did
not mention.

How much of the parsed body you can read differs by registry. Only parsed
technologies model members today. A parsed building or megastructure is
opaque — its whole body rides through unchanged — so those patch callbacks can
write new values but not read old ones, which is why the example above ignores
its argument.

For technologies, some parsed members are optional because not every vanilla
definition has them. Use `.require(...)` when the transform depends on a
member being present:

```ts
const geneTailoring = mod.patchTechnology(
  vanilla.definition("technology", "tech_gene_tailoring").require("cost", "prerequisites"),
  (technology) => ({
    cost: technology.cost.value * 2,
    prerequisites: [...technology.prerequisites, "tech_gene_seed_purification"],
  })
);
```

A parsed number remembers where it came from. A cost may be written as a
file-local `@variable`. Reading `.value` resolves it and writes the plain
number into your changed field. Values you do not touch stay as variable
references, and the emitted patch file redeclares any file-local variables the
carried body still uses.

A patch can also rewrite vanilla's own display text. The generated patch types
carry the registry's localization slots — `name`, `desc`, and
registry-specific slots such as a megastructure's `details` — and text set
there is emitted to `localisation/replace/` under vanilla's own key: a rename,
not a new key. See [Localization](/concepts/localization/) for how the
replacement layer wins.

## The emitted filename must provably win

Technology, building, and megastructure definitions are last-wins: when an id
appears more than once, the definition in the later-sorting file wins. A patch
in an arbitrary filename can therefore load before vanilla and have no effect.

For each patched registry, the [Fold](/guides/the-pipeline/) examines the
files from the loaded vanilla view and the files produced by the current mod.
It then:

1. Finds every file that defines each patched id.
2. Constructs a new filename after the last defining file.
3. Confirms the candidate name sorts after every one of those files, in the
   same byte order the game uses to sort filenames.
4. Refuses a filename that collides with vanilla or another output from the
   current mod.

Compilation fails if it cannot construct and verify a winning name. It does
not emit a plausible filename and leave the result for an in-game test.

The proof covers vanilla plus the current mod. It cannot account for a
third-party mod that also replaces the same id. Every emitted patch file says
this in its generated header and lists the files it was proven to beat.

## Patchability is explicit per registry

The public patch methods currently are:

- [`mod.patchTechnology`](/reference/technologies/)
- [`mod.patchBuilding`](/reference/buildings/)
- [`mod.patchMegastructure`](/reference/megastructures/)

A content registry having `mod.<type>` does not automatically give it a
`mod.patch<Type>`. Defining a new prefixed object and replacing a vanilla id
are different operations. Replacement requires all of these to be known for
that registry:

- how to parse and preserve a complete vanilla definition;
- whether the first or last duplicate wins;
- whether the winner replaces or merges fields; and
- how to emit a file that wins without replacing an entire vanilla file.

A registry gets a patch method only after a maintainer has reviewed answers to
all four questions. An answer can be a verified fact or a reviewed assumption;
an assumption stays visible through an
[`assumed-patch-rule` warning](/guides/warnings-and-diagnostics/) and the
emitted file header, as with megastructures today. A missing patch method
means at least one requirement is unmet — most often the loader does not parse
that registry yet, or the registry is first-wins and winning would need
before-first emission the SDK does not implement. If you need a registry with
no patch method, request it with in-game evidence of how that registry
resolves duplicates. Do not fake a patch by declaring a new object under a
vanilla id.

## Failures protect the replacement claim

Each loaded vanilla view carries a manifest: the record of which game files it
read. Patches are only comparable when they come from the same one. The Fold
refuses patches when:

- two selected Features patch the same id in the same registry;
- a patch was built from a different vanilla view than the one passed to
  `mod.compile`;
- the target id is not a top-level definition but a swap nested inside one,
  such as a `technology_swap` name — patch the parent definition instead, and
  its swaps ride through unchanged;
- the loaded game version differs from the version of the resolver evidence,
  unless the mod configuration explicitly accepts that game version; or
- a carried expression depends on file-local state the emitted patch cannot
  reproduce safely.

These failures occur before rendering or writing files. Keep the loaded
vanilla view, patch declarations, Feature placement, and `mod.compile` call in
one build flow, so every replacement is checked against the same list of game
files.
