A vanilla patch changes a definition that Stellaris already provides. The SDK
starts from the parsed vanilla object, changes selected fields, and re-emits a
complete replacement. Whole-object replacement is verified for technologies
and buildings. Megastructures currently use an explicit, visible assumption
until an in-game observable can distinguish replacement from merging.

Patching real installed content normally starts from a local Stellaris install.
`stellaris.load()` reads the game files and returns the definitions and file
enumeration needed to build the replacement safely. The exported
`viewFromFiles()` creates a hermetic view for tests and controlled inputs.

## Load vanilla and transform a definition

Create the patch through the matching mod capability method, place it in a
Feature, and pass the same vanilla view to `mod.compile`:

```ts
import { createMod, stellaris } from "@pdx-ts/sdk";

const mod = createMod({
  name: "Crystal Resonance",
  prefix: "crystal_resonance",
  supportedVersion: "v4.4.*",
});

const vanilla = stellaris.load();

const capitalPatch = mod.patchBuilding(
  vanilla.definition("building", "building_capital_1"),
  () => ({
    planetLimit: 2,
  })
);

const patches = mod.feature("vanilla_patches", [capitalPatch]);
const built = mod.compile([patches], { vanilla });
```

`vanilla.definition(registry, id)` returns a parsed definition tagged with its
registry. TypeScript therefore rejects a parsed building passed to
`patchTechnology`, and the vanilla view rejects an id it did not load.

The callback returns only the fields you want to change, but its result is not
a partial object sent to Stellaris. The SDK replaces those fields in the
parsed body and carries every untouched entry into the emitted definition.
Fields the typed model does not interpret also pass through. This preserves
the source definition instead of guessing defaults for fields the patch did
not mention.

Some parsed members are optional because not every vanilla definition has
them. Use `.require(...)` when the transform depends on a member being present:

```ts
const geneTailoring = mod.patchTechnology(
  vanilla.definition("technology", "tech_gene_tailoring").require("cost", "prerequisites"),
  (technology) => ({
    cost: technology.cost.value * 2,
    prerequisites: [...technology.prerequisites, "tech_gene_seed_purification"],
  })
);
```

Parsed numeric values retain their source provenance. For example, a cost may
come from a file-local `@variable`; reading `.value` deliberately bakes the
resolved number into the changed field. Untouched variable references remain
references, and the emitted patch file redeclares the file-local variables its
carried body still uses.

## The emitted filename must provably win

Technology, building, and megastructure definitions are last-wins: when an id
appears more than once, the definition in the later-sorting file wins. A patch
in an arbitrary filename can therefore load before vanilla and have no effect.

For each patched registry, the Fold examines the files from the loaded
vanilla view and the files produced by the current mod. It then:

1. Finds every file that defines each patched id.
2. Constructs a new filename after the last defining file.
3. Checks the candidate with the same byte-order comparator used for logical
   paths.
4. Refuses a filename that collides with vanilla or another output from the
   current mod.

Compilation fails if it cannot construct and verify a winning name. It does
not emit a plausible filename and leave the result for an in-game test.

The proof covers vanilla plus the current mod. It cannot account for a
third-party mod that also replaces the same id. Every emitted patch file says
this in its generated header and lists the files it was proven to beat.

## Patchability is explicit per registry

The public patch methods currently are:

- `mod.patchTechnology`
- `mod.patchBuilding`
- `mod.patchMegastructure`

A content registry having `mod.<type>` does not automatically give it a
`mod.patch<Type>`. Defining a new prefixed object and replacing a vanilla id
are different operations. Replacement requires all of these to be known for
that registry:

- how to parse and preserve a complete vanilla definition;
- whether the first or last duplicate wins;
- whether the winner replaces or merges fields; and
- how to emit a file that wins without replacing an entire vanilla file.

The SDK's reviewed registry overlay grants each `patchX` method separately.
If a registry has no patch method, its resolver or replacement behavior is not
established well enough for this API. An accepted assumption remains visible
through an `assumed-patch-rule` warning and the emitted file header. Use a
dedicated patch-registry addition with new game evidence rather than treating
another content method as permission.

## Failures protect the replacement claim

The Fold also refuses patches when:

- two selected Features patch the same id in the same registry;
- patches come from vanilla views with different manifests;
- the compile-time vanilla manifest differs from the manifest that supplied a
  patch;
- the loaded game version differs from the version of the resolver evidence,
  unless the mod configuration explicitly accepts that game version; or
- a carried expression depends on file-local state the emitted patch cannot
  reproduce safely.

These failures occur before rendering or writing files. Keep the loaded
vanilla view, patch declarations, Feature placement, and `mod.compile` call in
one build flow so the SDK can support every replacement with the same source
enumeration.
