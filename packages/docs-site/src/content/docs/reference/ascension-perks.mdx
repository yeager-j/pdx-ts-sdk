An **ascension perk** is an empire-wide choice made after a country unlocks an
ascension perk slot. Its definition controls which countries see and can select
the perk, what the perk does, and whether some countries receive a conditional
variant. The SDK writes these definitions under `common/ascension_perks/`.

## Availability

`potential` and `possible` are both country-scoped triggers, but they answer
different questions in the perk selection interface:

| Field       | Responsibility                                                                  |
| ----------- | ------------------------------------------------------------------------------- |
| `potential` | Decides whether the perk is a candidate for this country and should be shown.   |
| `possible`  | Decides whether a shown perk can be selected under the country's current state. |

Put structural eligibility in `potential`: empire type, required downloadable
content, mutually exclusive paths, or another condition that should remove the
perk from consideration. Put requirements that the player can satisfy in
`possible`: the number of perks already selected, a technology, or another
progression gate whose failure should explain why selection is blocked.

Vanilla commonly uses a `potential` condition to exclude a perk after the
country already owns it, and a `possible` condition with failure text for its
prerequisite count. The SDK lowers your triggers, but it does not choose or
generate those player-facing failure messages for you.

<Aside type="caution" title="AI weight is not availability">
  `aiWeight` ranks a perk for the AI after the availability rules apply. A zero weight does not
  express player eligibility and does not replace `potential` or `possible`.
</Aside>

## Tradition swaps

`traditionSwap` is a keyed record of conditional ascension-perk variants. The
name comes from the game's shared tradition rules; the field belongs directly
to an ascension perk. Each record key is the variant's full emitted id, so a
mod-owned key must start with the mod prefix.

Each swap field has one responsibility:

| Field            | Responsibility                                                               |
| ---------------- | ---------------------------------------------------------------------------- |
| `trigger`        | Makes this variant eligible for the current country.                         |
| `weight`         | Chooses the highest-weight variant when more than one eligible swap matches. |
| `inheritIcon`    | Reuses the base perk's icon.                                                 |
| `inheritName`    | Reuses the base perk's displayed name, so the swap does not need `name`.     |
| `inheritEffects` | Reuses the base modifier and `onEnabled` effect.                             |

Set all three inheritance flags deliberately. If `inheritEffects` is `false`,
put the complete replacement `modifier` and `onEnabled` behavior on the swap.
If it is `true`, omit those replacement fields and let the base perk supply the
behavior. Avoid overlapping triggers unless the weights express an intentional
choice.

The SDK requires a swap `name` unless `inheritName` is true. A swap that does
not inherit its icon also needs a matching GFX definition and asset. See
[Assets](/concepts/assets/) for authoring GFX definitions and texture files.

## What the perk does

Ascension perks can combine continuing bonuses, conditional bonuses, and a
one-time selection effect:

| Field               | Use                                                                         |
| ------------------- | --------------------------------------------------------------------------- |
| `modifier`          | Applies continuing country modifiers while the perk is active.              |
| `triggeredModifier` | Applies a group of country modifiers only while its `when` trigger is true. |
| `onEnabled`         | Runs country-scoped effects when the perk is selected.                      |
| `customTooltip`     | Shows one localization key instead of the generated root modifier tooltip.  |

Use a modifier for state that should remain active. Use `onEnabled` for a
one-time state change, such as setting a flag or starting another scripted
flow. Make the effect safe against duplicate execution where practical, and do
not use it as a migration hook for countries that selected the perk in an
older save.

Create custom tooltip text with `mod.localization(...)` and pass the returned
`.key`. At the root, `customTooltip` accepts one key and replaces the generated
modifier tooltip. Swap variants accept arrays for both `customTooltip` and
`customTooltipWithModifiers`; the latter adds text while retaining the
generated modifier lines.

<Aside type="caution" title="Root tooltip support is narrower than Vanilla">
  Vanilla uses repeated `custom_tooltip` fields and root-level `custom_tooltip_with_modifiers` in
  some ascension perks. The current `AscensionPerkDef` exposes one root `customTooltip` and does not
  expose a root `customTooltipWithModifiers`. Those broader forms are available only inside
  `traditionSwap`.
</Aside>

## Localization follows perk and swap ids

`mod.ascensionPerk("adaptive_destinies", ...)` mints the full id
`adaptive_destinies_ascension_perk_adaptive_destinies`. Its text members create
this localization family:

| Member | Generated key                                               |
| ------ | ----------------------------------------------------------- |
| `name` | `adaptive_destinies_ascension_perk_adaptive_destinies`      |
| `desc` | `adaptive_destinies_ascension_perk_adaptive_destinies_desc` |

A swap uses its record key as its identity. The advanced example's
`adaptive_destinies_ascension_perk_machine_destinies` key generates:

| Member    | Generated key                                                 |
| --------- | ------------------------------------------------------------- |
| `name`    | `adaptive_destinies_ascension_perk_machine_destinies`         |
| `flavor`  | `adaptive_destinies_ascension_perk_machine_destinies_delayed` |
| `effects` | `adaptive_destinies_ascension_perk_machine_destinies_desc`    |

`flavor` and `effects` are optional. If the swap inherits its name, it does not
need a new `name` key. Keep perk and swap ids stable after release because
scripts, localization, icons, and other definitions can refer to them.

Ascension perks often sit at the end of a tradition category or represent an
ascension path. The perk and the tradition tree remain separate definitions;
connect them through the game's normal references and selection rules. See the
[Traditions deep reference](/reference/traditions/) for complete trees,
prerequisites, and tradition swaps.

## Current limits and testing advice

- Ascension perks have no patch surface. `mod.patchAscensionPerk` does not
  exist.
- The SDK checks field shapes, trigger and effect scopes, localization,
  nested swap ids, references, and emitted paths. It does not simulate perk
  slots, the selection interface, AI choice, swap resolution, modifier behavior,
  or save migration.

Test countries that pass and fail each `potential` and `possible` branch. Test
the first valid perk slot and later slots, every swap trigger, overlapping swap
weights, inherited and replaced icons and effects, selection-time effects,
localization, AI choice, and save/load. See
[Testing your mod](/guides/testing-your-mod/) for the boundary between SDK
checks and live-game verification.
