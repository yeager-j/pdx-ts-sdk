A **megastructure definition** describes one constructible state of a large
space object. It supplies the finished and construction graphics, cost and
build time, placement policy, modifiers, lifecycle effects, and the states
that can upgrade into it. The SDK writes these definitions under
`common/megastructures/`.

localization, build and upkeep resources, planet-level placement rules, a
country modifier, and a completion effect:

## One stage is one definition

A multi-stage megastructure is not one definition with a `stages` array. Each
constructible state is a separate `mod.megastructure(...)` call. The later
state points backward to its allowed predecessors through `upgradeFrom`.

```ts
const frame = mod.megastructure("frame", {
  name: "Stellar Frame",
  entity: "construction_platform_entity",
});

const complete = mod.megastructure("complete", {
  name: "Stellar Array",
  entity: "dyson_sphere_phase_05_entity",
  upgradeFrom: [frame],
});
```

The SDK prefixes both ids and writes the branded reference from `frame` into
the second definition. Put every owned stage in the compiled Feature. A
reference to a stage that the mod did not compile fails during the Fold.

`upgradeFrom` can contain more than one predecessor. It can also form a branch:
two terminal definitions can both name the same previous stage. Vanilla uses
both patterns. For example, one Dyson Sphere stage accepts either its normal
predecessor or a completed Dyson Swarm, while other chains split into
different final outcomes.

Treat the definitions as an upgrade graph. Do not infer the next stage from
source order, logical names, or numeric suffixes; `upgradeFrom` is the edge
that the game reads.

### Hidden and ruined states are still definitions

Vanilla keeps temporary, script-only, ruined, and restored states as separate
ids too. A script-only state commonly uses `potential: always(false)`, hides
its upgrade description with `upgradeDesc: "hide"`, or hides its map and
outliner entries. A restored state points back to the ruined id through
`upgradeFrom`.

Use the same pattern only when the state has a real runtime identity. A name,
description, or art change does not by itself require another stage.

<Aside type="caution" title="An upgrade is not always an in-place linear step">
  Vanilla's Ring World construction deletes an intermediate megastructure and spawns several section
  objects. The current SDK does not expose the `spawn_megastructure` effect used by that
  choreography. Use an ordinary `upgradeFrom` graph when the object upgrades in place; do not claim
  that a scripted multi-object sequence is representable until that effect gap is closed.
</Aside>

## Placement has three layers

Megastructures separate whether an option exists, whether its system is legal,
and whether the selected planet or star is legal:

| Field                  | Immediate scope | Use                                                                  |
| ---------------------- | --------------- | -------------------------------------------------------------------- |
| `potential`            | Country         | Hide or expose the megastructure type for the building empire.       |
| `possible`             | System          | Check ownership, borders, survey state, existing structures, or war. |
| `placementRules`       | Planet          | Validate the exact planet or star selected as the anchor.            |
| `contextMenuPotential` | System          | Control the contextual construction shortcut separately.             |

`possible` receives the building country as `FROM`, so use the callback when a
system rule needs country state:

```ts
possible: (system) =>
  and(
    system.trigger(hasStarFlag("helios_forge_site")),
    system.from.trigger(hasCountryFlag("helios_forge_permit")),
  ),
placementRules: {
  planetPossible: and(isStar(), not(hasAnomaly())),
},
```

Keep checks at the narrowest layer that owns the fact. A border rule belongs
to the system; `isStar()` belongs to the selected planet. This produces better
failure locations and avoids repeating an expensive system search for every
candidate planet.

### Build location can bypass planet placement

`buildType` selects `"inside_gravity_well"`, `"outside_gravity_well"`, or
`"around_planet"`. The default is around a planet. For outside-gravity-well
construction, Stellaris ignores `placementRules`; put the actual legality in
`possible` instead.

`buildOutsideGravityWell` is the deprecated boolean spelling. Some current
vanilla definitions still use it, but new definitions should use `buildType`.

## Resources describe construction and operation

`resources` is a list of economic blocks. A row can set a `category` and any
combination of `cost`, `upkeep`, and `produces`. Each operation stores its
resource amounts under `amounts`:

```ts
resources: [
  {
    category: "megastructures",
    cost: { amounts: { alloys: 10_000, unity: 5_000 } },
    upkeep: { amounts: { energy: 25 } },
    produces: { amounts: { physics_research: 250 } },
  },
],
```

Use separate rows when costs or outputs have different runtime conditions.
Vanilla uses repeated conditional cost blocks for empires whose construction
economy replaces part of an alloy cost with food. The SDK preserves those
rows; it does not combine them into one price.

`buildTime` is the construction duration for this definition. Each later
stage owns its own time and resource blocks. The game does not inherit them
from the stage named in `upgradeFrom`.

## Lifecycle effects run in system scope

The construction hooks are `onBuildQueued`, `onBuildUnqueued`,
`onBuildStart`, `onBuildCancel`, and `onBuildComplete`. The dismantling hooks
follow the same pattern. Their immediate scope is the system, with the
building country available as `FROM`.

Use paired start and cancel effects for temporary state, then make completion
idempotent where practical:

```ts
onBuildStart: (system) => {
  system.setStarFlag("helios_forge_construction");
},
onBuildCancel: (system) => {
  system.removeStarFlag("helios_forge_construction");
},
onBuildComplete: (system) => {
  system.removeStarFlag("helios_forge_construction");
  system.setStarFlag("helios_forge_complete");
},
```

The SDK checks the immediate callback scope. It does not simulate build queues,
upgrade graphs, cancellation, object replacement, or save/load. Test each
entry and exit path in the game, including cancellation and rebuilding.

## Graphics have separate construction and finished hooks

The main graphics fields serve different UI and scene roles:

| Field                      | Role                                                                    |
| -------------------------- | ----------------------------------------------------------------------- |
| `entity`                   | Finished model entity; an empty string is valid for some transient ids. |
| `constructionEntity`       | Model shown while this definition is being built or upgraded.           |
| `constructionScale`        | Separates overlapping construction and finished geometry.               |
| `portrait`                 | Background or portrait sprite used by the construction interface.       |
| `orderIcon`                | Dedicated construction-order icon, with a matching `_selected` sprite.  |
| `placeEntityOnPlanetPlane` | Places the entity on the selected planet's orbital plane.               |
| `entityOffset`             | Moves the entity in that plane.                                         |
| `planeOffset`              | Moves planet-plane rendering to another visual layer.                   |
| `scalesWithPlanet`         | Scales planet-bound art with its anchor.                                |

Each stage can select different finished and construction entities. This is
how a visible model advances from frame to partial shell to complete object.
Planet-bound structures such as orbital rings instead use the planet-plane
fields and can leave `entity` empty while `constructionEntity` supplies the
temporary model.

These names refer to GFX definitions and model entities. The referenced art
must also be present in vanilla, a dependency, or your mod. See
[Assets](/concepts/assets/) for scaffolded asset placement, raw logical paths,
and typed GFX definitions. The SDK can check owned references, but it cannot
prove that a raw vanilla or third-party entity name has suitable geometry.

## Initializers place existing megastructure types

Solar system initializers do not become part of a megastructure definition.
Vanilla initializer effects use a megastructure type id to place ruined Ring
Worlds, Gateways, Orbital Rings, and other story objects at explicit planets
or orbital positions.

Keep the responsibilities separate: define the constructible or ruined state
with `mod.megastructure`, and use a system initializer for starting geometry.
See [Solar Systems](/reference/solar-systems/) for initializer trees and
object placement. Because `spawn_megastructure` is not currently exposed, the
SDK cannot yet author that vanilla initializer effect directly.

## Patch a vanilla megastructure

`mod.patchMegastructure` loads a vanilla definition, changes selected fields,
and emits a complete definition under the same vanilla id. The callback is a
field transform, but the output is not a partial game object: untouched parsed
fields are carried into the replacement.

```ts
import { stellaris } from "@pdx-ts/sdk";

const vanilla = stellaris.load();

const dysonPatch = mod.patchMegastructure(
  vanilla.definition("megastructure", "dyson_sphere_5"),
  () => ({
    buildTime: 1_800,
    resources: [
      {
        category: "megastructures",
        upkeep: { amounts: { energy: 50 } },
        produces: { amounts: { energy: 5_000 } },
      },
    ],
  })
);

const built = mod.compile([mod.feature("patches", [dysonPatch])], { vanilla });
```

The SDK has verified that the later megastructure definition wins, but it has
not verified whether the winner replaces the earlier object or merges with
it. It currently assumes whole-object replacement. Every megastructure patch
therefore produces an `assumed-patch-rule` warning and records that assumption
in the generated patch-file header. Test the complete patched object in game,
especially omitted fields, upgrades, localization, and graphics.

The winning filename is proven only against vanilla and files from the current
mod. Another mod can still load later and replace the same id. See
[Patching vanilla](/guides/patching-vanilla/) for load-order planning,
manifest requirements, and failure cases.

## Recommendations and gotchas

- Keep one owned Feature containing every stage in an upgrade graph.
- Use branded stage references for owned definitions and
  `vanilla.megastructure(...)` for checked vanilla ids in `upgradeFrom`.
  Reserve raw strings for deliberate third-party references.
- Give every buildable entry explicit placement policy and test its failure
  messages in systems with colonies, anomalies, other megastructures, and no
  valid anchor.
- Prefer `buildType` over the deprecated `buildOutsideGravityWell` field.
- Treat temporary, ruined, and restored ids as real states with their own art,
  hooks, and upgrade edges.
- Test both construction art and finished art at several zoom levels and on
  different planet sizes where scaling is enabled.
- Do not assume the SDK simulation harness advances megastructure construction
  or validates placement. Use a fresh game and `-script_debug` for runtime
  behavior.
