A **country ship-of-size limit** defines one shared capacity pool for one or
more ship sizes. Its formula combines a base capacity with an optional maximum
and an optional fraction of the country's current naval capacity. A separate
`mod.addShipOfSizeLimits` contribution applies the policy to the game's shared
ownership-limit list.

The definition writes under `common/country_limits/ship_of_size_limits/`.
The contribution writes a second file under
`common/country_limits/ownership_limits/`.

The order matters. `mod.countryShipOfSizeLimit` mints an owned definition with
a prefixed id, and `mod.addShipOfSizeLimits` then takes that definition and
adds its id to the shared list. The contribution has no id of its own. Put
both items in the compiled [Features](/guides/features-and-discovery/).

The example keeps the hull small to isolate this capacity seam. Before the
Dreadnought can be used in a game, complete its sections, components, graphics,
and design or scripted creation path as described in the
[Ships overview](/concepts/ships/).

## The pool is shared across every listed size

`shipTypes` is one list, not one independent limit per entry. All listed hulls
consume the same calculated capacity. Use one definition when variants should
compete for one pool, as vanilla titan variants do. Use separate definitions
when the capacities must remain independent.

Pass owned ship-size items where possible. Checked vanilla refs are available
through `vanilla.shipSize(...)`; a raw string is the escape hatch for a hull
owned by another mod.

The SDK checks an owned prefixed reference against the compiled content. It
cannot prove that a third-party string exists at game load time.

## Capacity uses a formula, not a fixed ship count

The SDK writes the game's pool formula:

```text
capacity = min(max, base + navalCapFraction × current naval capacity)
```

`base` is capacity, not a ship count. Each hull consumes capacity in
proportion to its `sizeMultiplier`, so one number can allow many small hulls
or a single large one. Vanilla scales its bases to the target hull: the titan
limit sets `base = 80` because the `titan` ship size sets
`size_multiplier = 80`, which is one titan's worth of capacity. The worked
example does the same with a Dreadnought whose `sizeMultiplier` is `60`. Start
from the vanilla limit whose hull accounting matches yours, then verify the
top-bar capacity and construction behavior in game.

`max` and `navalCapFraction` are both optional. A definition with neither is a
flat pool that does not follow naval capacity, which is what five of the seven
vanilla limits use.

`base`, `max`, and `navalCapFraction` accept script values, so a maintained
policy can derive them instead of hard-coding numbers. Vanilla's nomadic
constructor limit derives its base from a static modifier; write that form as
a string, `base: "modifier:nomadic_constructor_limit_add"`. The SDK writes the
string through unchanged and cannot check that the modifier exists.

## `show` controls the tooltip condition

`show` is a required country-scoped trigger. It controls whether the
ship-capacity tooltip appears on the top bar; it is not the pool formula and
does not unlock the hull.

Vanilla limits commonly combine `isScopeValid()` with a technology, origin,
country type, or global-state condition. Match the visibility rule to the game
path that introduces the limited hull. A hidden tooltip can make a working
limit look broken to the player.

The comments in the vanilla `common/country_limits/` files say the trigger
also receives a `FROM`: the federation for a federation design, and the
leading country for a Galactic Community design. The SDK types `show` as a
plain country trigger, so the field declares no `FROM` and `ctx.from` is not
available here (see [Scope and context](/guides/scope-and-context/)). Write
the condition on the country scope, and verify federation and community cases
in the exact design path you use.

## Contributions aggregate and deduplicate

Repeated `mod.addShipOfSizeLimits` calls accumulate into one shared file. Pass
owned limit items, `vanilla.countryShipOfSizeLimit(...)` for a vanilla limit,
or a raw string for another mod's limit. The [Fold](/guides/the-pipeline/)
resolves each id, sorts the final set, and collapses duplicates. It emits the
engine-owned structure:

```txt
default = {
  ship_of_size_limits = { your_limit another_mod_limit }
}
```

This is additive shared output, not an override of `default`. The contribution
takes the mod prefix in its file path, but the `default` wrapper stays the
game's.

If no contribution is present, no ownership-limit file is emitted. The
definition file is still written, but nothing applies it.

## Do not limit hulls used by global designs

Vanilla's own file says not to use ship-of-size limits for ship sizes that can
be used by global designs. [Global ship designs](/reference/global-ship-designs/)
use different selection and ownership paths.

Treat that warning as a system boundary. Do not limit the hull of the Aegis
carrier from the Ships overview merely because the API accepts the reference.
If a special gameplay design needs a cap, first find a current vanilla design
with the same creation and ownership path, then verify the behavior live.

## Current limits and testing advice

- The typed surface only adds. It cannot change a vanilla limit's formula or
  stop one applying: the contribution extends the shared list rather than
  replacing it, and `mod.patchCountryShipOfSizeLimit` does not exist. The game
  says a full overwrite means replacing its own `00_ownership_limits.txt`, or
  `00_ship_of_size_limits.txt` for a formula. That is a raw file copy through
  `mod.assetFile` ([Assets](/concepts/assets/)), which the SDK cannot check.
- The SDK does not simulate capacity consumption, top-bar UI, naval-capacity
  changes, federation/community context, construction rejection, ownership
  transfer, or design-specific exceptions.

Test the base capacity, maximum, naval-capacity scaling, every grouped hull,
the `show` trigger, zero and very high naval capacity, technology and origin
changes, capture and transfer, federation and community paths where relevant,
ship destruction, reinforcement, save/load, and removal of the mod. See
[Testing your mod](/guides/testing-your-mod/) for the boundary between what
the build checks and what only the live game can.
