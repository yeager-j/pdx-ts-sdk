A **component set** groups related component templates into one family. Lasers
of several sizes and tiers can share a set; reactors, drives, sensors, and
combat computers use required sets so every valid design must choose one
member. The SDK writes sets under `common/component_sets/`.

The [Ships overview](/concepts/ships/) defines three sets and connects each
one to a utility, weapon, or strike-craft component.

## Sets group choices; they do not mount them

A component template points to its set with `componentSet`. Sections do not
point to sets. They expose component-slot templates and utility counts, and a
design places a specific component template into each slot.

```ts
const beamSet = mod.componentSet("beam", {
  name: "Aegis Beam",
  desc: "Focused energy weapons fitted to the Aegis class.",
  icon: "GFX_ship_part_laser_1",
});

const beam = mod.weaponComponentTemplate("beam", {
  icon: "GFX_ship_part_laser_1",
  componentSet: beamSet,
  size: "medium",
  type: "instant",
});
```

Use one set when the components are alternatives in one designer family or
upgrade line. Use separate sets when the components have different selection,
targeting, required-slot, or UI roles.

## Required sets create hull obligations

Set `requiredComponentSet: true` when every design of a hull must supply one
component from this family. `isCoreComponentSet` marks a core family such as a
reactor, drive, thruster, or combat computer.

The hull lists required set ids in `shipSize.requiredComponentSet`. A fixed
global design then lists the selected utility component ids in
`requiredComponent`.

<Aside type="caution" title="A required set needs a usable member">
  Declaring a required set does not create a default component. Define compatible utility
  components, their availability rules, and their upgrade path. Then verify that every country and
  hull that can use the size has at least one legal choice.
</Aside>

Because `mod.componentSet` returns the general component-set item type, use an
owned required set's `.id` in `shipSize.requiredComponentSet`. This preserves
rename safety without casting the general item to the generated required-set
subtype.

## Ordinary sets and required sets use the same registry

The same definition shape supports weapon families, strike-craft families,
utility alternatives, and required cores. The flags distinguish their engine
roles:

- `requiredComponentSet` makes the family mandatory for hulls that list it.
- `isCoreComponentSet` identifies a core-equipment family.
- `isSpaceFaunaComponentSet` and `isDefaultSpaceFaunaComponentSet` connect the
  family to the space-fauna equipment system.
- `affectsTargetType` and `affectsTargetFocus` govern whether a selected
  component's targeting fields participate. Both default to enabled in the
  game rules.

Do not set a flag only because a nearby vanilla set uses it. Read the
components in that family and the hulls that require it.

## Localization belongs to the family

The SDK can emit four localization slots from one set:

| Member        | Key pattern         | Typical use                     |
| ------------- | ------------------- | ------------------------------- |
| `name`        | `<id>`              | Family name in the component UI |
| `desc`        | `<id>_DESC`         | General family description      |
| `shipDesc`    | `ship_<id>_DESC`    | Ship-specific description       |
| `stationDesc` | `station_<id>_DESC` | Station-specific description    |

The component template has its own `name`; the set text describes the family,
while the component text identifies the concrete tier or variant.

## Icons and component UI

`icon` and `iconFrame` select the set's component-selection art. Required
families commonly use the core-equipment icon. Ordinary weapon sets use art
that remains meaningful across the sizes and tiers they group.

The generated rule source contains subtype-dependent notes around these
fields. Confirm the UI for both ordinary and required sets instead of assuming
one icon treatment covers both.

## Current limits and testing advice

- Component sets have no patch surface. `mod.patchComponentSet` does not exist.
- The SDK checks the owned set reference from a component template, but it does
  not prove that the family contains a component for every size or country.
- Upgrade relationships live on component templates, not on the set.
- Section compatibility lives on sections and components, not on the set.

Test designer grouping, family text and icons, required-component defaults,
technology unlocks, automatic upgrades, targeting behavior, AI choices, and
every hull family that names the set.
