A **situation type** defines a long-running process owned by an empire. The
running situation has progress, a current stage, an optional approach chosen
by the player or AI, and an optional target such as a planet. It can apply
modifiers, run effects as its state changes, and fire events every month.

This worked example defines a three-stage crystal bloom with two approaches.
A country event selects a planet and starts the situation. Monthly progress
depends on the current approach and stage, random situation events can move
the progress in either direction, and a final event opens when progress
completes:

One example file produces several mod files. `mod.situationType` writes the
definition under `common/situations/`, the namespace writes its events under
`events/`, `mod.on` writes the game-start registration under
`common/on_actions/`, and the authored display text produces localization.

## A situation is a small state machine

Treat one situation as six connected parts:

| Part             | Responsibility                                                                   |
| ---------------- | -------------------------------------------------------------------------------- |
| Situation type   | Declares the progress model, stages, approaches, callbacks, and UI fields.       |
| Start effect     | Creates one running instance and supplies its target (see the events section).   |
| Monthly progress | Calculates the amount added to progress each month.                              |
| Stages           | Divide the progress track into named sections and react to stage entry.          |
| Approaches       | Let the player or AI select a policy that changes progress, costs, or modifiers. |
| Situation events | Present choices and effects in the running situation scope.                      |

Define the type before its start event so that `startSituation` receives the
typed item rather than a copied id. Put the definition, every owned event it
references, the start event, and the on-action contribution in Features passed
to the same `mod.compile` call. The Fold rejects an owned reference whose
definition was left out of the build.

## Model monthly progress explicitly

`monthlyProgress` is required. Its `base` and matching modifier rows are
evaluated by Stellaris in the running situation scope each month:

```ts
monthlyProgress: {
  base: 3,
  modifiers: [
    {
      add: 2,
      desc: "Our observers let the bloom develop naturally.",
      descKey: "observation_progress",
      when: currentSituationApproach(observe),
    },
  ],
},
```

Every modifier row needs `desc`. The SDK registers that explanation as
localization because the game shows it in the progress tooltip. Set a stable
`descKey` when the row will be maintained over time; this keeps its
localization identity separate from edits to the English text.

Use `add` for a flat change and `factor` for a multiplier. Conditions such as
`currentSituationApproach(...)`, `currentStage(...)`, and situation flags let
the calculation follow the rest of the state machine. Keep the calculation in
`monthlyProgress`; use `addSituationProgress` for discrete outcomes such as an
event choice or an approach being selected.

## Choose one stage progress model

Situations support two incompatible ways to size their stages.

In **threshold mode**, omit `totalProgress` and give every stage an `end` value:

```ts
stages: {
  [germination]: {
    name: "Germination",
    end: 40,
    icon: vanilla.spriteType("GFX_situation_stage_1"),
    iconBackground: vanilla.spriteType("GFX_situation_stage_frame_blue"),
  },
  [flowering]: {
    name: "Flowering",
    end: 100,
    icon: vanilla.spriteType("GFX_situation_stage_2"),
    iconBackground: vanilla.spriteType("GFX_situation_stage_frame_blue"),
  },
},
```

In **section-weight mode**, set `totalProgress` and give every stage a
`sectionWeight`. The worked example uses a total of `100` and weights of
`30`, `40`, and `30`. A total or section weight can also be a
situation-scoped weight block — `totalProgress: { base: 100, modifiers: [...] }` —
when its value must be calculated at runtime.

<Callout type="warn" title="Do not mix end and sectionWeight">
  Setting `totalProgress` switches the game to section-weight mode. Every stage must then use
  `sectionWeight`, and no stage may use `end`. The TypeScript type can express both fields because
  it cannot derive one member's legality from the value of another. Stellaris reports the mixed form
  as an error.
</Callout>

Use threshold mode when the boundaries themselves are the clearest model. Use
section-weight mode when each stage should own a share of a separately
calculated total.

## Monodirectional and bidirectional progress

`progressDirection` defaults to `"monodirectional"`. Progress moves toward the
completion edge, and `onProgressComplete` runs when it reaches that edge.

Use `"bidirectional"` when the center has meaningful success and failure
directions:

```ts
progressDirection: "bidirectional",
startValue: -100,
initialProgress: 0,
completeCategory: "positive",
failCategory: "negative",
monthlyProgress: { base: -2 },
```

`startValue` defines the lower bound. `initialProgress` selects the starting
position; if it is below `startValue`, the game raises it to `startValue`.
`completeCategory` and `failCategory` only apply to bidirectional situations.

Reaching an edge does not remove the situation. The game's own documentation
says every situation's completion and failure paths should call
`destroy_situation` — from `onProgressComplete` and `onFail` directly, or
from an event they fire, as the worked example's final event does with
`situation.destroySituation(ctx.self)`. Reserve `permanent: true` for a
situation that must keep running past an edge.

Choose the direction and stage model first, then use only the fields that
belong to that model.

## Give stages stable, ordered identities

`stages` is a record whose keys are the complete stage ids. Each key must use
the mod prefix. The values hold the localized name and description, icons,
progress size, entry effects, conditions, and modifiers. The worked example
declares each key once as a `const` (`germination`, `flowering`, `awakening`)
and reuses it everywhere the stage is named.

Stage declaration order is content: the SDK preserves it in the emitted
`stages = { ... }` container. Keep the record in progress order.

`onFirstEnter` runs only the first time an instance reaches that stage.
`onEnter` also runs when progress leaves and later re-enters the stage, which
is especially important for bidirectional situations. Use the first form for
one-time setup and the second only for repeatable work.

`modifier` runs in country scope. `targetModifier` runs in the situation's
target scope, but the generated stage type accepts any game scope because the
rules do. Keep it consistent with the target passed when the situation
starts — and keep the target a colony or the empire: the game's own
documentation warns that target modifiers silently do nothing for other
target scopes.

## Approaches are selectable policies

`approach` is another record of complete, prefixed ids. Set one entry as the
default. `potential` decides whether an approach belongs in this situation
instance; `allow` decides whether a present approach can be selected now. The
field table below covers the rest. One note on `resources`: the example shows
a one-off `cost`, but most vanilla approaches charge a recurring `upkeep`
instead — a standing policy usually costs monthly.

The worked example keeps **Intervene** visible but locks it until the
**Flowering** stage with `allow: currentStage(flowering)`.

Some fields are checked against the keys declared in the same definition: an
approach's `allow` and `potential`, a stage's `potential`, and the
situation's `abortTrigger`. Other fields do not always carry that
definition-specific identity. Declare ids once as `const` values and reuse
them in progress modifiers, events, and effects so a rename cannot leave a
stale string behind.

Although stages and approaches are both authored as TypeScript records, their
PDXScript forms differ. Stages emit inside one keyed `stages` container.
Approaches emit as repeated sibling `approach = { name = ... }` blocks. Let the
SDK lower these structures; do not shape raw PDXScript around them.

## Declare and preserve the target scope

Many situations track a planet or another object. Declare that contract once
with `targetScope`:

```ts
const crystalBloom = mod.situationType("crystal_bloom", {
  targetScope: "planet",
  // Other fields omitted.
});
```

`targetScope` is a TypeScript-only contract. It does not emit a
`target_scope` field. When owned content starts the situation, the declared
type requires a matching typed scope value. The worked example's start event
passes a saved planet event target to
`country.startSituation({ type: crystalBloom, target: bloomWorld, ... })`;
its `effect` callback knows that `.target(...)` opens a planet because `type`
carries `targetScope: "planet"`. A country target or an untyped bare string
is a TypeScript error.

That inference is local to `startSituation`. In callbacks stored on the type,
such as `onStart`, `onProgressComplete`, stage entry effects, or situation
event effects, use an explicit link when you need the target:

```ts
onProgressComplete: (situation) => {
  situation.target<"planet">((planet) => {
    planet.setPlanetFlag("crystal_bloom_complete");
  });
},
```

The game owns the runtime link. The type argument states what your design
already established; it does not create or validate a target at runtime.

## Wire events around the situation

Use a situation event for UI and effects that run against the active
situation. The worked example's `unstableGrowth` event is one:
`events.situation(2, ...)` with `location: target<"planet">()` and an option
whose effects call `situation.addSituationProgress(-5)`.

`location: target<"planet">()` tells the event window to show the running
situation's target. The generic is an author assertion here; it is not read
from the situation type definition.

`onMonthly.events` fires every listed event each month. `randomEvents` chooses
from weighted rows instead. Omit `event` to make a no-event arm:

```ts
onMonthly: {
  randomEvents: [
    { weight: 8, event: unstableGrowth },
    { weight: 12, event: harmonicInsight },
    { weight: 80 },
  ],
},
```

Only situation events belong in these lists for owned content; the game also
accepts scopeless event ids, which the SDK cannot author. Pass owned event
values instead of copied ids so event kind and build ownership remain
checked.

A situation does not start itself. The worked example attaches a hidden
country event to `onActions.onGameStartCountry`; that event selects a planet,
saves it as a typed event target, checks that the selection succeeded, and
calls `startSituation`. In a real mod,
the entry point can instead be a decision, another event, a special project,
or any legal effect. Read [Events](/concepts/events/) for event bodies and typed
firing, and [On-actions](/concepts/on-actions/) for lifecycle hooks and their
`THIS`/`FROM` contracts.

## Lifecycle callbacks and modifiers

`onStart`, `onProgressComplete`, `onFail`, and `onAbort` all run in
situation scope. `onFail` runs when progress falls to the failure edge, below
`startValue` — vanilla's deficit situations are monodirectional and fail this
way, so the callback is not limited to bidirectional situations.

Use `abortTrigger` for a state that makes the situation invalid, and pair it
with `onAbort` when cleanup is required. `potential` is different in two
ways: it is country-scoped, and the game re-evaluates it while the situation
runs — a running instance is removed the moment `potential` goes false, with
no `onAbort` and no cleanup effects. Keep volatile conditions in
`abortTrigger` and reserve `potential` for conditions that cannot change
during the situation's life.

Top-level `modifier` applies to the owning country. `targetModifier` applies
to a planet target. The corresponding `triggeredModifier` arrays add
situation-scoped conditions. Approaches and stages provide similar modifier
slots for policy-specific and phase-specific effects. Prefer those declarative
modifiers over monthly effects that repeatedly add and remove equivalent
bonuses.

## Localization and identity

The logical name passed to `mod.situationType` mints the top-level id. With the
default id profile, this call:

```ts
mod.situationType("crystal_bloom", definition);
```

mints `crystal_bloom_situation_type_crystal_bloom`. Its `name`, `typeName`, and
`desc` text produce localization owned by that definition. Stage and approach
`name` and `desc` values also produce localization under their record keys.

Stage and approach keys are nested definition ids rather than logical names,
so write the complete prefixed value. Keep the ids stable after release. A
display-text edit should change localization, not the identity that save games,
triggers, and effects refer to.

## Current limitations

- The game rules permit conditional situation pictures (and vanilla reaches
  the same shape through `inline_script`), but the SDK currently accepts only
  a list of fixed sprite references in `picture`.
- The game expects a `<full situation id>_monthly_change_tooltip`
  localization key for the progress tooltip — every vanilla situation has
  one — but the SDK does not generate it. Add it yourself with
  `mod.localization`, spelling the suffix from the full situation id.
- In section-weight mode, the game auto-generates two country modifiers,
  `<id>_max_progress_add` and `<id>_max_progress_mult`, and expects
  `mod_<id>_max_progress_add`/`_mult` localization keys. The generated
  modifier tables cannot know per-situation names, so write those modifiers
  with `unchecked` and add the keys by hand.
- Numeric RGBA stage colors are not represented by the current `color` type;
  use a named color.
- The vendored rules miss two tooltip spellings the game documents (approach
  `custom_tooltip`, stage `custom_tooltip_with_modifiers`). The SDK follows
  the rules; no vanilla situation uses either spelling.
- The SDK types individual fields but cannot prove every valid combination of
  progress direction, stage mode, and completion behavior.
- `targetScope` checks owned `startSituation` calls. Vanilla, third-party, and
  raw situation ids do not carry that authored contract.

## What to test

The simulation harness does not advance situation months, progress, stages,
completion, or `onMonthly`. Use it to test surrounding entry conditions and
event effects, then verify the running situation in Stellaris — see
[Testing your mod](/guides/testing-your-mod/).

For a maintained situation, test every progress edge your situation has
(completion, and failure if it can fail), every stage transition, approach
availability and cost, abort cleanup, that the completion and failure paths
destroy the instance, missing or invalid targets, monthly no-event arms, and
save/load while the situation is active.
