A **building** is a structure constructed on a colony. Its definition controls
where it appears, when construction is allowed, what it costs, which jobs or
modifiers it supplies, and what happens as it moves through its lifecycle. The
SDK writes building definitions under `common/buildings/`.

## Who can build it, and where

These fields decide where a building appears and what kind of building it is.
Keep each rule in the field that answers its question:

| Field          | Responsibility                                                                |
| -------------- | ----------------------------------------------------------------------------- |
| `potential`    | Decides whether the building appears in a colony's construction list.         |
| `allow`        | Decides whether a visible building is enabled or grayed out for construction. |
| `canBuild`     | Marks the definition as directly constructible.                               |
| `ownerType`    | Selects `corporate` branch-office or `subject_holding` ownership.             |
| `buildingSets` | Matches the building to planet-class building sets and can remove mismatches. |
| `capital`      | Marks a capital building.                                                     |
| `capitalTier`  | Gives the tier for a definition that uses the capital subtype.                |

Both `potential` and `allow` are [colony-scoped](/guides/scope-and-context/)
triggers. Use `potential` for a hard list-visibility rule and `allow` for a
condition the player should see and be able to satisfy. A building that fails
`potential` is absent rather than disabled.

`buildingSets` is not an eligibility trigger. It participates in the game's
planet-class building-set matching. Vanilla buildings can belong to more than
one set, such as both `research` and `physics`.

<Callout type="warn" title="Capital fields are a subtype contract">
  `capitalTier` is legal only for the capital building subtype. Do not use `capital: true` as a
  substitute for a colony trigger such as `isCapital()`; one classifies the definition and the other
  tests the current colony.
</Callout>

## Limits

The three direct limit fields run in different scopes:

| Field           | Scope   | Meaning                                    |
| --------------- | ------- | ------------------------------------------ |
| `empireLimit`   | Country | Caps copies across the owning empire.      |
| `planetLimit`   | Planet  | Caps copies on one planet.                 |
| `districtLimit` | Colony  | Connects the cap to colony district state. |

Country, Planet, and Colony are separate scopes in the game rules, so each
block sees a different set of conditions.

Each field accepts either a number or a conditional weight block. A conditional
block states a base value and modifier rows that scale it. No field means no
limit.

In a conditional block, a multiplier of `-1` removes the limit. The rules say
this for all three fields. The empire-limit rules add one warning: do not set a
base below 0, because the engine ignores it. For the planet and district
limits, a modifier-driven cap still applies after a `-1` multiplier has removed
the direct limit.

`baseCapAmount` sets the base count that a cap modifier then adjusts.
`isCappedByModifier: true` opts the building into modifier-driven capping.
Vanilla buildings set `baseCapAmount` on its own and never set
`isCappedByModifier`, so the pair is untested in shipped content. Test it in
game before you depend on it.

Use the smallest scope that states the actual rule. A one-per-world laboratory
needs `planetLimit: 1`; it does not need an empire-wide trigger that counts
buildings manually.

## Lifecycle hooks and state transitions

Building hooks are colony-scoped effect closures:

| Hook         | Runs when the building is… |
| ------------ | -------------------------- |
| `onQueued`   | added to the build queue.  |
| `onUnqueued` | removed from the queue.    |
| `onBuilt`    | completed.                 |
| `onEnabled`  | enabled.                   |
| `onDestroy`  | destroyed.                 |
| `onRepaired` | repaired.                  |

Use these for consequences, such as setting a flag or applying a modifier.
They do not replace the matching trigger fields:

| Trigger                    | Result when it becomes true                               |
| -------------------------- | --------------------------------------------------------- |
| `abortTrigger`             | Cancels ongoing construction.                             |
| `abortConstructionTrigger` | Cancels ongoing construction.                             |
| `ruinedTrigger`            | Changes the completed building to its ruined state.       |
| `destroyTrigger`           | Destroys it, or converts it through a `convertTo` target. |

The two abort triggers are a known ambiguity. The game rules give both the
same description, and no shipped building uses either one, so the SDK cannot
say which the engine reads. Set one, test it in game, and keep the other free.

Keep transition conditions in triggers and one-time work in hooks. For
example, use `destroyTrigger` to express when a building can no longer exist,
then use `onDestroy` only for cleanup caused by that transition.

## Jobs and output

A building can produce resources directly through `resources[].produces`, or
it can add job capacity through a planet modifier. These models have different
game behavior: direct output needs no worker, while a job follows its own
eligibility, assignment, upkeep, production, and swap rules.

The full example below defines a `stormAnalyst` job and adds `200` capacity with
the dynamic modifier key `job_<job-id>_add`. Use
`modifier.job(stormAnalyst).add(200)` to derive that key from the owned job
reference. Job-capacity modifier names are derived from the referenced job id,
including the mod prefix.
See [Jobs](/reference/jobs/) for job eligibility, production, swaps, and
testing advice.

For an end-to-end walkthrough with a custom job economy, see
[Create a job and its building](/tutorials/jobs-and-buildings/).

Vanilla often calls `inline_script` to pick different jobs for regular,
hive-minded, and machine empires. `BuildingDef` has no inline-script field, so
write out the jobs you support instead of copying an `inline_script` line.

## Technology gating and display

These fields are related, but none replaces another:

| Field              | Responsibility                                                      |
| ------------------ | ------------------------------------------------------------------- |
| `prerequisites`    | Names technologies required by the building.                        |
| `showInTech`       | Associates the building with technology entries for unlock display. |
| `showTechUnlockIf` | Country-scoped condition for showing that technology unlock.        |
| `category`         | Places the building in a building category.                         |
| `icon`             | Reuses another building id or names building icon art explicitly.   |
| `positionPriority` | Orders the building in the construction list; lower sorts earlier.  |

Use the reference returned by `mod.technology(...)` for a technology owned by
the same mod, and `vanilla.technology(...)` for a checked Vanilla id. See
[Technologies](/reference/technologies/) for research-tree design and draw
rules.

Most ordinary Vanilla buildings omit `icon`; the game rules infer
`gfx/interface/icons/buildings/<building-id>.dds`. Set `icon` when the building
must reuse different art, as the full example does. An icon reference does not
copy or create the asset.

## Patch a Vanilla building

`mod.patchBuilding` starts from an installed, parsed building and applies a
typed transform. The callback names only changed fields, but the SDK emits a
complete-object replacement and carries untouched and unsupported source
members through.

A parsed building is opaque: nothing about its body is modelled yet. So a
building patch states new values and cannot read old ones, and the callback
below ignores its argument. Parsed technologies expose selected typed members
and `.require(...)`; parsed ascension perk categories expose their member list.

`stellaris.load()` returns the loaded install. This page names it `vanillaView`
because `vanilla` here is the checked-id namespace:

```ts
const vanillaView = stellaris.load();

const capitalPatch = mod.patchBuilding(
  vanillaView.definition("building", "building_capital"),
  () => ({ planetLimit: 2 })
);

const built = mod.compile([mod.feature("building_patches", [capitalPatch])], {
  vanilla: vanillaView,
});
```

For buildings, both behaviors are verified in game: the last file to define an
id wins, and the winning definition replaces the whole object. The compiler
selects an output filename that sorts after every loaded Vanilla file that
defines the same id. It cannot prove the result against another mod that
replaces that id later. Read [Patching vanilla](/guides/patching-vanilla/) for
loading the install, requiring parsed members, and the filename proof.

## Current limits and testing advice

- The SDK checks field shapes, trigger and effect scopes, owned and Vanilla
  references, emitted paths, and localization. It does not simulate colony
  automation, build-list display, limits, job assignment, or lifecycle timing.
- Many shipped buildings nest an `inline_script` call inside their `resources`
  block, most often to swap one cost for another. The SDK's resource block has
  no such member, so a vanilla block built from `category` and `inline_script`
  alone cannot be reproduced. State the costs and output you want instead.
- `aiWeight` is retained for rule compatibility, but the source rules say the
  game no longer uses it unless `economic_plans` is overridden. Prefer the
  current AI resource and weight fields for new content.
- The source rules do not establish a quantity limit for `showInTech`. Treat it
  as a list and test every displayed unlock in game.

Test in game:

- Gates: an eligible and an ineligible colony, every owner type, and every
  building set.
- Limits: each numeric or conditional cap, and cancelling a queued copy.
- Lifecycle: ruin, destruction, repair, and re-enabling.
- Output: direct resources and job-based output.
- Display: technology unlock rows, icon art, and AI construction.
- Patches and upgrades: the patched object, any conversion, then save and load.

See [Testing your mod](/guides/testing-your-mod/) for the boundary between SDK
checks and live-game verification.
