A **section template** is one attachable part of a ship. It declares which
ship sizes accept it, which hull slot it fits, the section model entity, its
named weapon or strike-craft positions, and its utility-slot counts. The SDK
writes section templates under `common/section_templates/`.

The [Ships overview](/concepts/ships/) defines bow, mid, and stern sections
for one complete Aegis design and shows the emitted files.

## A section joins four name systems

One section must make four independent sets of names agree:

| Connection         | Section member             | Where the name is defined                                           |
| ------------------ | -------------------------- | ------------------------------------------------------------------- |
| Compatible hull    | `shipSize`                 | [`mod.shipSize`](/reference/ship-sizes/), or a vanilla hull         |
| Hull attachment    | `fitsOnSlot`               | Key in `shipSize.sectionSlots`                                      |
| Equipment shape    | `componentSlot[].template` | Component-slot templates the game defines                           |
| Equipment position | `componentSlot[].name`     | `globalShipDesign.section[].component[].slot`, or the ship designer |

`shipSize` accepts owned ship-size items and checked vanilla hulls, so a new
section can attach to a shipped ship with `vanilla.shipSize("battleship")`.
The section's own id is minted by `mod.sectionTemplate`; the slot names are
engine keys and stay unprefixed.

```ts
const mid = mod.sectionTemplate("aegis_mid", {
  name: "Aegis Carrier Core",
  shipSize: [hull],
  fitsOnSlot: ["mid"],
  entity: "cruiser_mid_S2HB_entity",
});
```

`name` supplies the text the ship designer shows. The SDK writes it through
[Localization](/concepts/localization/) under the section id. A section on a
player-designable hull needs it, or the designer shows the raw key instead.
The SDK leaves `name` optional for every section and does not check which
hulls are designable.

`compatibleWithAllShipSizes: true` bypasses the explicit compatibility list.
Reserve it for a section whose model, slot name, utility layout, and gameplay
rules really work across every target hull. An explicit `shipSize` list is
safer for ordinary sections.

## Component slots describe sockets, not equipment

Each `componentSlot` row declares one named hardpoint. The mid section above
carries a single strike-craft row:

```ts
componentSlot: [{
  name: "STRIKE_CRAFT_01",
  template: "large_strike_craft",
  locatorname: "strike_craft_locator_01",
  rotation: 90,
}],
```

- `name` is the slot key a fixed design or the ship designer fills.
- `template` is a component-slot-template id such as `small_turret`,
  `medium_turret`, `point_defence_turret`, or `large_strike_craft`.
- `locatorname` is a locator on the section model.
- `rotation`, `position`, `isSideSlot`, and `sectionInstance` adjust specialized
  placement.

The `template` here is not a component set and not a weapon component. It
defines which equipment shape the slot accepts. The actual component is chosen
by the ship designer or by a global design.

  The installed `common/HOW_TO_MAKE_NEW_SHIPS.txt` still illustrates the old
  `slot_size` and `slot_type` members. Current vanilla sections and the SDK use
  `template = <component-slot-template>`. Copy the current definition, not the old sample syntax.
</Callout>

## Utility slots are counts

Utility positions are counts — `smallUtilitySlots`, `mediumUtilitySlots`,
`largeUtilitySlots`, and `auxUtilitySlots` — not `componentSlot` rows.

Stellaris derives names such as `MEDIUM_UTILITY_1` from those counts. A global
design can fill those names through its section `component` rows. Required
components such as reactors and sensors remain separate and belong in
[`globalShipDesign.requiredComponent`](/reference/global-ship-designs/).

Do not add utility counts to compensate for a missing required component set.
One controls ordinary section equipment; the other controls mandatory
hull-level equipment.

## The entity and locators are one graphics contract

The section entity is attached to the locator chosen by the matching hull
slot. Equipment entities are then attached to the locators declared by
`componentSlot`.

For culture-aware ship art, Stellaris normally prefixes the section entity
with the current graphical culture. The base `cruiser_mid_S2HB_entity` can
therefore select a culture-specific entity such as
`mammalian_01_cruiser_mid_S2HB_entity`.

The SDK accepts model-entity and locator references but cannot inspect the
asset graph. Verify that:

- the hull entity contains the section attachment locator
- the section entity exists for each graphical culture
- every equipment locator exists on that entity
- turret and strike-craft art uses the locators expected by its component

## Cost, unlocks, and AI selection

`resources` can add section construction cost or upkeep. `prerequisites`
unlocks the section with technologies. `aiTags` and `aiWeight` control how the
designer or AI classifies and selects it.

Keep these rules aligned with the equipment layout. A carrier section should
have carrier-oriented tags and a weight policy that does not select it before
usable strike craft exist. A torpedo section should gate the technology and
role that make its hardpoints meaningful.

## The two modifier keys have no vanilla example

The rules list two ship-scoped modifier keys for this registry, `modifier` and
`ship_modifier`, so the SDK exposes `modifier` and `shipModifier`. Neither key
has a shipped example: none of the 482 vanilla section templates writes
either one. The only shipped `ship_modifier` use is on ship sizes, which is a
different registry. Prefer `modifier`, and confirm in the running game that
the modifier applies before you build on it.

## Current limits and testing advice

- Section templates have no patch surface. `mod.patchSectionTemplate` does not
  exist.
- The SDK checks reference types and serialization, but not slot completeness,
  model locators, component compatibility, or visual overlap.
- `icon` is present in vanilla section definitions, but the upstream rules
  note that it may be unused. Do not rely on it until you have seen it appear
  in the game's interface.
- A global design places each section by its `slot` value, not by the order of
  the section rows. Moving a row does not correct a wrong `slot`.
- A `resources` block takes one `cost`, `produces`, `upkeep`, and `logistics`
  arm each. Vanilla defense-platform sections write three trigger-gated `cost`
  arms inside one block; that shape cannot be authored yet.

Check the section on every hull and graphical culture, in the 3D ship viewer,
and in automatic and manual designs. Then test AI section selection,
construction cost, component placement, firing origins, damage states, and
save/load.
