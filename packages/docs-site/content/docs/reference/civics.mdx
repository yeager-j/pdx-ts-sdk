A **civic** is a selectable rule that helps define an empire's government and
continuing bonuses. Its definition controls which empires can choose it, what
it costs, whether it can change during a reform, and which modifiers it adds.
The SDK writes civics under `common/governments/civics/`.

Civics and [origins](/reference/origins/) share the game's `civic_or_origin`
registry and the SDK's `mod.civicOrOrigin(...)` method. A civic is the default
subtype: leave `isOrigin` unset.

## Empire-creation requirements are a data model

Four fields participate in empire creation, but they do not all use the same
kind of condition:

| Field        | Type                     | Responsibility                                                   |
| ------------ | ------------------------ | ---------------------------------------------------------------- |
| `playable`   | `Trigger<"no_scope">`    | Allows or blocks the civic for a human player.                   |
| `aiPlayable` | `Trigger<"no_scope">`    | Allows or blocks the civic for generated AI empires.             |
| `potential`  | `GovernmentTriggerBlock` | Classifies the authorities, ethics, civics, and species it fits. |
| `possible`   | `GovernmentTriggerBlock` | States the combination an empire must satisfy to select it.      |

`potential` and `possible` are not ordinary script triggers. They use the
game's government-requirements data shape. Each named domain has `value`,
`or`, `not`, and `nor` clauses, and a clause can include a `text` localization
key for its requirement message.

For a same-domain alternative, put all accepted values in one clause group:

```ts
possible: {
  authority: {
    or: [{ values: ["auth_democratic", "auth_oligarchic"] }],
  },
}
```

Do not replace this object with `or(hasAuthority(...), ...)`; a `Trigger` does
not type-check here. Also do not use two block-level `orGroups` for the two
authorities. Repeated block groups are combined by the requirements model and
would require both groups instead of selecting either value.

A common Vanilla pattern uses `potential` for broad civic families, such as
excluding gestalt or corporate authorities, and `possible` for the detailed
selection requirements shown to the player. Keep both blocks aligned: a
condition that makes every `possible` branch unreachable produces a civic
nobody can select.

<Callout type="warn" title="No-scope gates are not country triggers">
  Empire creation has no country scope for `playable` or `aiPlayable`. A condition such as
  `hasAuthority(...)` is country-scoped and does not belong there. Use the no-scope checks the game
  exposes for this phase, most often downloadable-content checks.
</Callout>

## Modifiers and player-facing effects

`modifier` applies continuing country modifiers while the civic remains valid.
Use `multiplyByHabitabilityEffectModifier` only when the civic's bonus should
be scaled through that separate game rule.

The text fields have different localization behavior:

| Member                       | Result                                               |
| ---------------------------- | ---------------------------------------------------- |
| `name`                       | Creates localization at the civic's full id.         |
| `desc`                       | Creates localization at `<full-id>_desc`.            |
| `description`                | Text shown under **Effects**.                        |
| `negativeDescription`        | Text shown under **Penalties**.                      |
| `customTooltip`              | Repeated text that replaces generated modifier text. |
| `customTooltipWithModifiers` | Repeated text shown with generated modifier text.    |

Each of the latter four names a localization key. Write the display text and
the SDK keys it for you, or pass a `mod.localization(...)` item — or
`external.localization(...)` — to name a key that already exists.

## Reform rules

Civic-only fields control cost and later government reform:

| Field                   | Responsibility                                                   |
| ----------------------- | ---------------------------------------------------------------- |
| `cost`                  | Sets the civic's selection cost; the game rules default it to 1. |
| `pickableAtStart`       | Allows initial selection; the game rules default it to true.     |
| `modification`          | Allows, blocks, or conditions adding and removing the civic.     |
| `alternateCivicVersion` | Points to another civic used as the alternate definition.        |
| `canBuildRulerShip`     | Writes the game's civic-specific ruler-ship marker.              |

Set `modification: false` to prevent adding or removing the civic after empire
creation. Vanilla can still use `alternateCivicVersion` to replace a locked
civic during a government reform. To condition later additions and removals,
provide `add` and `remove` country-scoped triggers instead. The SDK lowers only
the rules you write; it does not make the two conditions logical opposites or
supply a player-facing explanation. The optional
`moddableConditionsCustomTooltip` member takes an existing localization key.

Use the branded value returned by another `mod.civicOrOrigin(...)` call for a
mod-owned `alternateCivicVersion`. Use
`vanilla.civicOrOrigin("civic_...")` for a checked Vanilla id. The game and SDK
share one reference registry for civics and origins, so choose the correct
subtype yourself when a field specifically asks for a civic.

## Conditional `swapType` variants

Each `swapType` row can replace the civic's description, penalty text, and
modifier while its trigger matches. This is useful when one civic needs a
different effect for one authority or another country state without creating
a second selectable civic.

The trigger is unusual because the game evaluates it in two phases. During
empire creation there may be no country scope; during play there is one. Guard
country-only checks with `isScopeValid()` first. The advanced example's
oligarchic branch does that:

`swapType.modifier` is generated for a broad scope union, so its modifier
closure cannot always use the checked country modifier tree. The example uses
`modifier.unchecked(...)` for the exact game modifier key. Keep that escape
hatch local and verify the key against the current game version.

A swap row carries no modifier inheritance flag. Vanilla includes trigger-only
rows as well as rows with replacement modifiers, but the SDK contracts do not
establish how the engine combines an omitted swap modifier with the base one.
Test the base and every matching variant in empire creation and after a
government reform.

## Weights are separate from eligibility

`randomWeight` controls selection during random empire generation. `aiWeight`
controls AI preference where the game consults civic weights. Both are
country-scoped weight blocks with a base and optional conditional modifiers.
They do not replace `playable`, `aiPlayable`, `potential`, or `possible`.

A zero weight is used by Vanilla to exclude a civic from a weighted choice; it
does not express human-player validity in the SDK contract. Keep the gates
explicit even when a weight is zero, and verify the exact selection behavior in
game.

## Icons, ids, and output

`mod.civicOrOrigin("public_stewardship", ...)` mints the full id
`civic_stewardship_civic_or_origin_public_stewardship`. That id is also the
default localization key and remains the value other content references.

The `icon` field is a raw game path, not an asset reference. Both examples
reuse Vanilla civic art so they compile without a custom texture. For released
content, add your own texture under `gfx/interface/icons/governments/civics/`
and pass its logical mod path. The SDK writes the string but does not prove the
texture exists or has the right format. See [Assets](/concepts/assets/).

All civic and origin definitions from one feature stem share
`common/governments/civics/<prefix>_<stem>_civics.txt`; a directly compiled
feature without a stem uses `<prefix>_civics.txt`.

## Current limits and testing advice

- There is no `mod.patchCivicOrOrigin` method. The SDK does not support
  whole-object patches for this registry.
- The SDK checks field shapes, government-requirement references, trigger and
  modifier scopes, owned ids, localization, and emitted paths. It does not
  simulate empire creation, reforms, random generation, AI choice, or swap
  evaluation.
- The SDK can express one `potential` and one `possible` object. Combine all
  requirements into those objects instead of depending on repeated blocks from
  hand-written script.

Test every allowed authority and ethic combination, each exclusion, initial
selection, adding and removing the civic in a reform, every swap both during
empire creation and in play, weights, tooltips, icons, and save/load. See
[Testing your mod](/guides/testing-your-mod/) for the boundary between SDK
checks and live-game verification.
