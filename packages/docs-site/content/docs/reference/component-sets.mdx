A **component set** groups related component templates into one family. Lasers
of several sizes can share one set. Reactors, drives, sensors, and combat
computers use required sets, so every valid design must choose one member. The
SDK writes sets under `common/component_sets/`.

The [Ships overview](/concepts/ships/) defines three sets and connects each
one to a utility, weapon, or strike-craft component.

## Sets group choices; they do not mount them

A [utility](/reference/utility-components/),
[weapon](/reference/weapon-components/), or
[strike-craft](/reference/strike-craft-components/) component template points
to its set with `componentSet`. Sections do not point to sets. They expose
component-slot templates and utility counts, and a design places a specific
component template into each slot. Upgrade rows and section compatibility also
live on the component, not on the set.

A template joins its family by passing the set value, not by naming a slot:

```ts
const beamSet = mod.componentSet("beam", {
  name: "Aegis Beam",
  desc: "Focused energy weapons fitted to the Aegis class.",
  icon: "GFX_ship_part_laser_1",
});

const beam = mod.weaponComponentTemplate("beam", {
  icon: "GFX_ship_part_laser_1",
  componentSet: beamSet,
  size: "medium",
  type: "instant",
});
```

The two ids are independent. The `componentSet` value is the only connection.

Vanilla groups weapons and strike craft by size, not by tier. `RED_LASER` holds
the small, medium, and large lasers of one tier, and each later tier is a
separate set that templates reach through `upgradesTo`. Core utility families
work the other way: `sensor_components` holds `SENSOR_1` through `SENSOR_4` in
one set. Use separate sets when the components have different selection,
targeting, required-slot, or UI roles.

## Required sets create hull obligations

Set `requiredComponentSet: true` when every design of a hull must supply one
component from this family. `isCoreComponentSet` marks a core family such as a
reactor, drive, thruster, or combat computer.

The hull lists required set ids in
[`shipSize.requiredComponentSet`](/reference/ship-sizes/). A fixed
[global ship design](/reference/global-ship-designs/) then lists the selected
utility component ids in `requiredComponent`.

<Callout type="warn" title="A required set needs a usable member">
  Declaring a required set does not create a default component. Define compatible utility
  components, their availability rules, and their upgrade path. Then verify that every country and
  hull that can use the size has at least one legal choice.
</Callout>

When the definition contains `requiredComponentSet: true`, `mod.componentSet`
returns a reference with the required-component subtype. Pass that owned value
directly to `shipSize.requiredComponentSet`; an ordinary set is rejected.

A vanilla required set has no checked path. `vanilla.componentSet` returns the
general set reference, which `shipSize.requiredComponentSet` rejects. Name
vanilla's core families with raw strings instead:
`requiredComponentSet: ["power_core", "combat_computers"]`. Most new hulls need
this, because they must list the families vanilla already defines.

## Flags select the engine role

The same definition shape supports weapon families, strike-craft families,
utility alternatives, and required cores. Two flag pairs carry decisions the
field table cannot express:

- `affectsTargetType` and `affectsTargetFocus` govern whether a selected
  component's targeting fields participate. Switching either off removes that
  targeting dimension from every component in the family.
- `isSpaceFaunaComponentSet` and `isDefaultSpaceFaunaComponentSet` mean
  something only together with the space-fauna equipment system. They are not
  general markers.

Do not set a flag only because a nearby vanilla set uses it. Read the
components in that family and the hulls that require it.

## Localization belongs to the family

The SDK can emit four localization slots from one set:

| Member        | Key pattern         | Typical use                     |
| ------------- | ------------------- | ------------------------------- |
| `name`        | `<id>`              | Family name in the component UI |
| `desc`        | `<id>_DESC`         | General family description      |
| `shipDesc`    | `ship_<id>_DESC`    | Ship-specific description       |
| `stationDesc` | `station_<id>_DESC` | Station-specific description    |

The component template has its own `name`; the set text describes the family,
while the component text identifies the concrete tier or variant.

## Icons and component UI

`icon` and `iconFrame` select the set's component-selection art. Ordinary
weapon sets use art that stays meaningful across the sizes they group.

The game rules require an `icon` and a name on an ordinary set, and make both
optional on a required set. The SDK marks `name`, `icon`, and `iconFrame`
optional on every set, so a set with neither still compiles. Give an ordinary
set both. All 439 vanilla sets declare an icon, and 12 of the 24 vanilla
required sets carry no name text.

## Current limits and testing advice

- Component sets have no patch surface. `mod.patchComponentSet` does not exist,
  so a vanilla set is out of reach of
  [patching vanilla](/guides/patching-vanilla/).
- The SDK checks the owned set reference from a component template, but it does
  not prove that the family contains a component for every size or country.
- A hull cannot name a vanilla required set through a checked reference. Use the
  raw id, as described above.
- Vanilla starbase modules can also auto-equip their components from a set. The
  SDK has no starbase-module registry, so that connection cannot be authored.

In game, [test](/guides/testing-your-mod/) designer grouping, family text and
icons, required-component defaults, technology unlocks, automatic upgrades,
targeting behavior, AI choices, and every hull family that names the set.
