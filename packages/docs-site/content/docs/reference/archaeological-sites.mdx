An **archaeological site type** defines a dig site that a science ship can
excavate one chapter at a time. It supplies the site name and description,
controls who can see and excavate it, lists the ordered chapter events, and
handles failed excavation rolls. The SDK writes these definitions under
`common/archaeological_site_types/`.

The site type is only one part of the story. Each completed chapter fires a
fleet event, and some other effect must first place the site on a planet or
another supported game object. This complete example connects all three
parts: the site type, its three chapter events, and the effect that places it
on a planet.

## A dig site has three connected layers

| Layer                    | Responsibility                                                                    |
| ------------------------ | --------------------------------------------------------------------------------- |
| Archaeological site type | Declares display fields, excavation gates, ordered stages, and lifecycle effects. |
| Fleet events             | Present each completed chapter and apply its rewards or consequences.             |
| Placement effect         | Chooses the object that owns the site and creates either a named or random type.  |

`mod.archaeologicalSiteType` returns a typed site reference. Pass that value
to `createArchaeologicalSite`, and put the site definition and every owned
chapter event it references in [Features](/guides/features-and-discovery/)
passed to the same `mod.compile` call. The [Fold](/guides/the-pipeline/) then
rejects a missing site or event at build time, rather than letting Stellaris
fail on a dangling id at runtime.

A vanilla site type cannot be altered: archaeological sites have no
`mod.patch<Type>` surface, and a vanilla id cannot be re-declared. See
[Patching vanilla](/guides/patching-vanilla/).

## Chapters are ordered stages

The game shows chapters; the field is `stage`. Set `stages` to the exact
number of `stage` entries. Stellaris treats the array order as chapter order:

```ts
stages: 3,
stage: [
  { difficulty: 2, icon: "GFX_archaeology_runes_A1", event: sealedDoor },
  {
    difficulty: { min: 3, max: 4 },
    icon: "GFX_archaeology_runes_A2",
    event: memoryVault,
  },
  { difficulty: 5, icon: "GFX_archaeology_runes_A3", event: lastCustodian },
],
```

Each entry has three jobs:

- `difficulty` sets the chapter's excavation difficulty. A number is fixed;
  `{ min, max }` lets the game choose a value in that interval.
- `icon` is the rune sprite shown for that chapter.
- `event` is the fleet event fired when the chapter completes.

The SDK checks that `event` is a fleet-event reference, but it does not compare
the numeric `stages` field with the array length. Keep them together and change
them in one edit.

<Callout type="warn" title="Do not model chapters as separate site types">
  One site type owns the ordered chapter list. Use a second site type only when the story must move
  to another object or become a separately discovered dig site. In that case, the final chapter
  event can place the next named site.
</Callout>

## Every chapter points to an archaeology fleet event

A stage event runs in fleet scope because the excavating science ship receives
it. Declare the site as its `FROM`, mark it as an archaeology event, and use
that `FROM` for the window location:

```ts
const sealedDoor = events.fleet(1, {
  scopes: { from: "archaeological_site" },
  title: "The Sealed Door",
  desc: "The excavation has reached a door with no visible controls.",
  location: (ctx) => ctx.from,
  archaeology: true,
  isTriggeredOnly: true,
  // Other fields omitted.
  options: [
    {
      name: { english: "Cut through the seal.", key: "cut_the_seal" },
      effects: (fleet) => {
        fleet.owner.effects((country) => {
          country.addResource({ resource: "engineering_research", amount: 250 });
        });
      },
    },
  ],
});
```

The stage completes before this event opens. Use the event for the chapter's
text, choices, rewards, flags, and follow-up event calls. `fleet.owner` opens
the excavating empire when a reward belongs to the country; `ctx.from` opens
the archaeological site when an option must change the dig itself.

Most vanilla chapter events also lock excavation for the duration of the
window: they set `site.setSiteProgressLocked()` in `immediate` through
`ctx.from.effects(...)` and release it with `setSiteProgressLocked(false)` in
`after`. Do the same when the dig must not advance while the player reads.

Keep `isTriggeredOnly: true`. The stage owns the entry point, so the event does
not need a mean-time-to-happen trigger. See [Events](/concepts/events/) for event
options, typed firing, and `FROM` contracts.

## Failed rolls are a separate path

`onRollFailed` runs in fleet scope with the archaeological site as `FROM`.
The worked example gives the current stage one clue:

```ts
onRollFailed: (_fleet, ctx) => {
  ctx.from.effects((site) => {
    site.addStageClues(1);
  });
},
```

This callback does not replace a chapter event. It runs when an excavation
roll fails; the stage event runs only when the chapter finishes.

Vanilla's common failure policy is more involved. It branches on the roll
score, grants zero, one, or two clues, awards scientist experience, and can
select a random archaeology incident. Nearly every vanilla site delegates it
to one checked scripted effect, which the SDK can call directly:

```ts
onRollFailed: (_fleet, ctx) => {
  ctx.from.effects((site) => {
    site.run(standardArchaeologicalSiteOnRollFailed({ RANDOM_EVENTS: "no_events" }));
  });
},
```

`standardArchaeologicalSiteOnRollFailed` comes from
`@pdx-ts/stellaris-ids/effects`; vanilla passes `all_random_events` for sites
that may roll incidents and `no_events` for quiet ones. A fixed clue, a
custom setback, or no progress can also be valid, but each choice changes the
expected length of the dig.

## Separate visibility from excavation permission

The three trigger fields answer different questions:

| Field       | Runtime scope                   | Meaning                                          |
| ----------- | ------------------------------- | ------------------------------------------------ |
| `visible`   | `THIS = country`, `FROM = site` | Can this country see the site?                   |
| `potential` | `THIS = fleet`, `FROM = site`   | Does the excavation action exist for this fleet? |
| `allow`     | `THIS = fleet`, `FROM = site`   | If the action exists, is it enabled now?         |

Omitting `potential` leaves the excavation action present. `allow` and
`visible` are required, so even a broadly accessible site must state its
policy. The example uses vanilla's standard rules: the fleet needs a scientist
leader, and a normal country sees the site when it has enough system intel or
the site planet lies within its borders.

```ts
allow: (ctx) => and(
  exists(leader(ctx.self)),
  leader(leaderClass("scientist")),
),
visible: defaultSiteVisibleTrigger(),
```

`defaultSiteVisibleTrigger` is a checked, version-pinned vanilla scripted
trigger from `@pdx-ts/stellaris-ids/triggers`.

In a maintained mod, use `visible` for discovery, borders, intel, or a
story flag. Use `potential` for a fleet that should never receive the action,
and `allow` for a temporary requirement that the UI should show as disabled.
Creation alone does not make a site visible.

The closure form exposes `FROM` when the rule depends on site state:

```ts
// scientistIsReady and siteIsUnlocked are your own triggers.
allow: (ctx) => and(
  scientistIsReady,
  ctx.from.trigger(siteIsUnlocked),
),
```

Use the closure form whenever the rule reads anything from `ctx` — `ctx.self`
or `ctx.from`, as both `allow` examples above do. A plain Trigger value is
clearer when the rule needs neither.

## Place a named site from an effect

A site definition does not place itself. Call `createArchaeologicalSite` from
the planet, system, or other supported object that should own the site:

```ts
country.randomOwnedPlanet({ limit: not(archaeologicalSite(always())) }, (planet) => {
  planet.preventAnomaly();
  planet.createArchaeologicalSite(silentArchive);
});
```

The example first excludes planets that already link to an archaeological
site. Most vanilla named placements sit in solar-system initializers, on a
body the initializer just created, so they need no guard. Roughly a fifth of
named call sites — those placing onto an existing, possibly occupied body —
call `preventAnomaly` (vanilla's `prevent_anomaly`), clear a conflicting
deposit, or check for an existing site first. The engine's behavior for
creating a named site on an occupied object is not documented, so do not use
the creation effect as the occupancy check.

Vanilla spells the occupancy guard `exists = archaeological_site`. A plain
trigger position cannot express that form today, because `exists()` needs a
scope value that only `ctx` supplies, so the example writes the
scope-transition form `NOT = { archaeological_site = { always = yes } }`
instead. The two express the same check, though vanilla only ever writes the
first.

The caller chooses the location. Common entry points include an anomaly or
event option, a solar-system initializer's `init_effect`, a survey on-action,
or the final event of another dig. If location selection can fail, set story
flags and consume one-time state only after you have selected a valid target.

`maxInstances` does not protect direct named placement. It is checked only
for random site creation, so a one-off story chain must enforce its own
uniqueness. The paired example guards with a global flag: the placing event
requires the flag to be absent and sets it after creation. The example's
`maxInstances: 1` matters only if its weight ever becomes positive.

## Random creation is a selection policy

Pass the literal `"random"` when the game should select a site type:

```ts
planet.createArchaeologicalSite("random");
```

For this path, each candidate's `weight` is evaluated against the current
planet and `maxInstances` limits how many copies random selection may create.
A weight block can gate or favor planet classes, DLC state, flags, and other
planet-scoped conditions. Random does not mean that every type is equally
likely.

Use `weight: 0` for a story site that should be created only by name. Many
vanilla chains do this. Use a positive fixed or conditional weight only when
the type belongs in a random pool.

<Callout type="warn" title="Random creation does not choose the location">
  The calling effect has already selected the planet or other object. The random operation chooses a
  site type for that object. Survey events and scripted placement effects are responsible for
  finding a legal location before they call it.
</Callout>

## Descriptions

Use `desc` for one localized description. The SDK emits both the localization
entry and the raw `desc = <generated key>` pointer that the game reads. Do not
set `desc` and `conditionalDesc` together.

Use `conditionalDesc` when the displayed text changes by site-scoped
conditions. Its scalar form is one piece of display text, or a reference to an
existing key; its array form is an ordered list of `{ trigger, text }`
clauses. The first matching clause is
used, so put specific conditions before a fallback.

## Lifecycle effects

The lifecycle effects run at different scopes:

- `onCreate` runs on the archaeological site when creation succeeds.
- `onVisible` runs on each country when the site becomes visible, with the
  site as `FROM`.
- `onRollFailed` runs on the excavating fleet, with the site as `FROM` — see
  [Failed rolls are a separate path](#failed-rolls-are-a-separate-path).

Use `onCreate` for site-local setup and `onVisible` for a discovery
notification or country state. Half of vanilla's site types fire the stock
discovery notification from `onVisible`, which the SDK writes as
`country.countryEvent({ id: vanilla.event.story.$5, days: 30 })`. Do not put
chapter rewards in these hooks when the stage event is the actual owner.

## What to verify in Stellaris

The SDK verifies references, field types, scopes, emitted files, and
localization. It does not simulate the excavation system. Test at least:

- every chapter event, option, reward, and `FROM` use;
- fixed and interval difficulty values at several scientist skill levels;
- failed rolls and any clue or random-incident branches;
- visibility before and after the intended discovery condition;
- `potential` and `allow` with both legal and illegal fleets;
- placement when no eligible location exists and when a site is already there;
- random weight, planet-class gates, and instance limits, if used;
- save and load during each chapter and after the final event.

See [Testing your mod](/guides/testing-your-mod/) for the SDK's simulation
boundary and the checks that still require the live game.
