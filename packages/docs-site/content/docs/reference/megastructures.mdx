A **megastructure definition** describes one constructible state of a large
space object. It supplies the finished and construction graphics, cost and
build time, placement policy, modifiers, lifecycle effects, and the states
that can upgrade into it. The SDK writes these definitions under
`common/megastructures/`.

This minimal example defines a single-stage star megastructure. It includes
name and description text that the SDK writes to
[Localization](/concepts/localization/), build and upkeep resources,
planet-level placement rules, a country modifier, and a completion effect:

## One stage is one definition

A multi-stage megastructure is not one definition with a `stages` array. Each
constructible state is a separate `mod.megastructure(...)` call. The later
state points backward to its allowed predecessors through `upgradeFrom`.

The SDK prefixes every id and writes the
[typed reference](/guides/references-and-identity/) returned by
`mod.megastructure(...)` into the later definition. Put every owned stage in
the compiled [Feature](/guides/features-and-discovery/); a reference to a stage
that the mod did not compile fails during the [Fold](/guides/the-pipeline/).
Use `vanilla.megastructure(...)` for a vanilla predecessor, and reserve raw
strings for deliberate third-party references.

`upgradeFrom` can contain more than one predecessor. It can also form a branch:
two terminal definitions can both name the same previous stage. Vanilla uses
both patterns. For example, one Dyson Sphere stage accepts either its normal
predecessor or a completed Dyson Swarm, while other chains split into
different final outcomes.

final upgrades:

Treat the definitions as an upgrade graph. Do not infer the next stage from
source order, logical names, or numeric suffixes; `upgradeFrom` is the edge
that the game reads.

### Hidden and ruined states are still definitions

Vanilla keeps temporary, script-only, ruined, and restored states as separate
ids too. A script-only state commonly uses `potential: always(false)`, hides
its upgrade description with `upgradeDesc: "hide"`, or hides its map and
outliner entries. A restored state points back to the ruined id through
`upgradeFrom`.

Use the same pattern only when the state has a real runtime identity. A name,
description, or art change does not by itself require another stage.

<Callout type="warn" title="An upgrade is not always an in-place linear step">
  Vanilla's Ring World construction deletes an intermediate megastructure and spawns several section
  objects. The SDK does not expose the `spawn_megastructure` effect that choreography needs. Use an
  ordinary `upgradeFrom` graph when the object upgrades in place. A scripted multi-object sequence
  like the Ring World's is not authorable with the SDK today.
</Callout>

## Placement checks run at three scopes

Megastructures separate whether an option exists, whether its system is legal,
and whether the selected planet or star is legal:

| Field            | Immediate scope | Use                                                                  |
| ---------------- | --------------- | -------------------------------------------------------------------- |
| `potential`      | Country         | Hide or expose the megastructure type for the building empire.       |
| `possible`       | System          | Check ownership, borders, survey state, existing structures, or war. |
| `placementRules` | Planet          | Validate the exact planet or star selected as the anchor.            |

`possible` receives the building country as `FROM`, so use the callback when a
system rule needs country state:

```ts
possible: (ctx) =>
  and(
    hasStarFlag("helios_forge_site"),
    ctx.from.trigger(hasCountryFlag("helios_forge_permit")),
  ),
placementRules: {
  planetPossible: and(isStar(), not(hasAnomaly())),
},
```

The callback parameter is the script context, not the system itself. Read
`ctx.from` for the country and write a plain system trigger for the immediate
scope. See [Scope and context](/guides/scope-and-context/) for the closure
form.

Keep checks at the narrowest layer that owns the fact. A border rule belongs
to the system; `isStar()` belongs to the selected planet. This produces better
failure locations and avoids repeating an expensive system search for every
candidate planet.

### The build picker has its own fields

`contextMenuPotential` is not a placement layer. It runs in system scope and
decides one thing: whether a fleet that could build the megastructure offers it
in the system right-click menu. The shortcut appears only when the field is
set, and the source rules say the game does not support it for
`buildType: "around_planet"` or `mustSelectShipDesign: true`.

A second family ranks candidate systems in the build tooltip.
`tooltipSystemScore` is a weight block in system scope, and higher scores rank
higher. `tooltipSystemScoreLowThreshold` and `tooltipSystemScoreHighThreshold`
colour the printed score red, yellow, or green. `tooltipShowStarResources` is
the alternative that ranks by the star's deposit output instead of a number;
the rules say the two are mutually exclusive. `tooltipBestSystemsHeader` is the
list header. `tooltipSystemFilter` removes systems from the list entirely; it
takes the country as `FROM`, and the rules recommend it over repeating
`possible`, whose infrastructure checks are unsuitable for ranking.

The generated field table lists all of these fields with no description,
because the source rules record their meaning in a comment style the generator
drops. This section is the only place the site describes them.

### Build location can bypass planet placement

`buildType` selects `"inside_gravity_well"`, `"outside_gravity_well"`, or
`"around_planet"`. The default is around a planet. Outside the gravity well the
game free-places the object between the system's inner and outer radius, so no
planet is selected: vanilla's hyper relay leaves its `placement_rules` block
empty with a comment saying the rules would be ignored. Put the real legality
in `possible`. Vanilla's nomad waystation shows the limit of that rule — it
still writes a `planet_possible` block, but only to carry a failure tooltip.

`buildOutsideGravityWell` is the deprecated boolean spelling. One current
vanilla definition, the hyper relay, still uses it; new definitions should use
`buildType`.

## Resources describe construction and operation

`resources` is a list of economic blocks. A row can set a `category` and at
most one each of `cost`, `upkeep`, and `produces`. Each operation stores its
resource amounts under `amounts`:

```ts
resources: [
  {
    category: "megastructures",
    cost: { amounts: { alloys: 10_000, unity: 5_000 } },
    upkeep: { amounts: { energy: 25 } },
    produces: { amounts: { physics_research: 250 } },
  },
],
```

Vanilla writes conditional pricing in a way the SDK cannot reproduce. It
repeats `cost` inside one `resources` block, each arm carrying its own
trigger; the hyper relay writes four that way, to swap part of an alloy cost
for food in bio-ship empires. A `MegastructureDef` row holds one `cost`, and
the row's `when` condition is typed for no particular scope, so a country
trigger does not compile. Set one price per definition and test it in game.

`buildTime` is the construction duration for this definition. Each later
stage owns its own time and resource blocks. The game does not inherit them
from the stage named in `upgradeFrom`.

## Lifecycle effects run in system scope

The construction hooks are `onBuildQueued`, `onBuildUnqueued`,
`onBuildStart`, `onBuildCancel`, and `onBuildComplete`. Dismantling has three:
`onDismantleStart`, `onDismantleCancel`, and `onDismantleComplete`. All eight
run in system scope, with the building country available as `FROM`.

Use paired start and cancel effects for temporary state, then make completion
idempotent where practical:

```ts
onBuildStart: (system) => {
  system.setStarFlag("helios_forge_construction");
},
onBuildCancel: (system) => {
  system.removeStarFlag("helios_forge_construction");
},
onBuildComplete: (system) => {
  system.removeStarFlag("helios_forge_construction");
  system.setStarFlag("helios_forge_complete");
},
```

The SDK checks the immediate callback scope. It does not simulate build queues,
upgrade graphs, cancellation, object replacement, or save/load. Test each
entry and exit path in the game, including cancellation and rebuilding.

## Graphics fields separate construction art from finished art

The main graphics fields serve different UI and scene roles:

| Field                      | Role                                                                    |
| -------------------------- | ----------------------------------------------------------------------- |
| `entity`                   | Finished model entity; an empty string is valid for some transient ids. |
| `constructionEntity`       | Model shown while this definition is being built or upgraded.           |
| `constructionScale`        | Separates overlapping construction and finished geometry.               |
| `portrait`                 | Background or portrait sprite used by the construction interface.       |
| `orderIcon`                | Dedicated construction-order icon, with a matching `_selected` sprite.  |
| `placeEntityOnPlanetPlane` | Places the entity on the selected planet's orbital plane.               |
| `entityOffset`             | Moves the entity in that plane.                                         |
| `planeOffset`              | Moves planet-plane rendering to another visual layer.                   |
| `scalesWithPlanet`         | Scales planet-bound art with its anchor.                                |

Each stage can select different finished and construction entities. This is
how a visible model advances from frame to partial shell to complete object.
Planet-bound structures such as orbital rings instead use the planet-plane
fields and can leave `entity` empty while `constructionEntity` supplies the
temporary model.

These names refer to GFX definitions and model entities. The referenced art
must also be present in vanilla, a dependency, or your mod. See
[Assets](/concepts/assets/) for scaffolded asset placement, raw logical paths,
and typed GFX definitions. The SDK can check owned references, but it cannot
prove that a raw vanilla or third-party entity name has suitable geometry.

## Initializers place existing megastructure types

Solar system initializers do not become part of a megastructure definition.
Vanilla initializer effects use a megastructure type id to place ruined Ring
Worlds, Gateways, Orbital Rings, and other story objects at explicit planets
or orbital positions.

Keep the responsibilities separate: define the constructible or ruined state
with `mod.megastructure`, and use a system initializer for starting geometry.
See [Solar Systems](/reference/solar-systems/) for initializer trees and
object placement. The same `spawn_megastructure` gap noted above means the SDK
cannot yet author that vanilla initializer effect directly.

## Patch a vanilla megastructure

`mod.patchMegastructure` loads a vanilla definition, changes selected fields,
and emits a complete definition under the same vanilla id. The callback is a
field transform, but the output is not a partial game object: untouched parsed
fields are carried into the replacement. A parsed megastructure is opaque — the
SDK models none of its members — so the callback can write new values but
cannot read old ones, which is why the callback below ignores its argument.

```ts
import { stellaris } from "@pdx-ts/sdk";

const vanillaView = stellaris.load();

const dysonPatch = mod.patchMegastructure(
  vanillaView.definition("megastructure", "dyson_sphere_5"),
  () => ({
    buildTime: 1_800,
    resources: [
      {
        category: "megastructures",
        upkeep: { amounts: { energy: 50 } },
        produces: { amounts: { energy: 5_000 } },
      },
    ],
  })
);

const built = mod.compile([mod.feature("patches", [dysonPatch])], {
  vanilla: vanillaView,
});
```

Compiling a patch needs the same loaded view, passed to `mod.compile` as the
`vanilla` option.

Last-wins ordering is verified for megastructures. Whether the winner replaces
the earlier object or merges with it is not, so the SDK assumes whole-object
replacement. Every megastructure patch therefore produces an
`assumed-patch-rule` warning and records that assumption in the generated
patch-file header. Test the complete patched object in game, especially
omitted fields, upgrades, localization, and graphics.

The winning filename is proven only against vanilla and files from the current
mod. Another mod can still load later and replace the same id. See
[Patching vanilla](/guides/patching-vanilla/) for load-order planning,
manifest requirements, and failure cases.

## Current limits and testing advice

- Conditional pricing is not authorable. A `resources` row holds one `cost`,
  and its `when` condition is typed for no particular scope, so vanilla's
  country-conditional cost arms have no equivalent.
- `MegastructureDef` has no inline-script field. Vanilla builds its three nomad
  arkships entirely from an `inline_script` call, and splices shared `possible`
  fragments, such as the waystation ownership check, into nine more
  definitions. Do not copy one of those calls as if it were a literal member;
  write the result out longhand.
- The source rules never declare `can_prevent_crisis_terraformation`, which the
  game's own README documents, so the SDK cannot author it. No shipped vanilla
  definition uses it today.
- The SDK checks field shapes, trigger and effect scopes, owned and vanilla
  references, emitted paths, and localization. It does not advance construction
  or validate placement.

Give every buildable entry explicit placement policy and test its failure
messages in systems with colonies, anomalies, other megastructures, and no
valid anchor. Test both construction art and finished art at several zoom
levels and on different planet sizes where scaling is enabled. Use a fresh game
and `-script_debug` for runtime behavior. See
[Testing your mod](/guides/testing-your-mod/) for the boundary between SDK
checks and live-game verification.

- [`MegastructureDef`](https://github.com/yeager-j/pdx-ts-sdk/blob/main/packages/sdk/src/generated/megastructure.ts)

  not the loaded install view that patches transform.
