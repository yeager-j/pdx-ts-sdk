title: Scope and context
description: Follow THIS, ROOT, and FROM through triggers, effects, and scope changes.
---

Stellaris evaluates every trigger and effect in a **scope**: a country, planet,
fleet, leader, or another game object. The current scope is `THIS` in
PDXScript. Some script blocks also declare stable `ROOT` and `FROM` scopes.

These are game-time relationships. The TypeScript values you use to author
them are typed descriptions and recorder handles; they are not live game
objects. Read [Triggers and effects](/guides/triggers-and-effects/) first if the
build-time and game-time distinction is not yet familiar.

## The current scope is `THIS`

The first parameter of an effect closure represents the scope where that block
will run:

```ts
immediate: (country) => {
  country.addResource({ resource: "influence", amount: 50 });
};
```

This event's `immediate` block runs in country scope, so the recorder parameter
has country effects. A planet-only effect does not exist on that object.

Triggers carry the same fact in their type. `hasCountryFlag(...)` returns a
`Trigger<"country">`; a planet-only condition returns a
`Trigger<"planet">`. A field or structural effect accepts only a Trigger that
is valid where the game will evaluate it.

```ts
country.if(hasCountryFlag(flags.ready), () => {
  country.addResource({ resource: "influence", amount: 50 });
});
```

The condition and the branch body both use country scope.

## Scope changes are explicit

Scope links open a nested block in another scope. Their callback parameters
show the transition:

```ts
planet.owner.effects((country) => {
  country.addResource({ resource: "influence", amount: 10 });
});
```

`planet.owner.effects(...)` records an `owner = { ... }` block whose `THIS` is
the owning country. The generated type for `owner` determines both where the
link can start and the scope its callback receives.

The generated types carry the landing scope through longer paths too. For
example, a path such as `planet.owner.capitalScope.effects(...)` lands in
colony scope before its callback records effects.

Use the [Scopes & Effects overview](/scopes-and-effects/) to choose a scope-first lookup. Each scope
page keeps legal methods separate from the outgoing properties that navigate to another scope.

Declarative triggers use scope links instead of effect callbacks:

```ts
const ownerIsReady = owner(hasCountryFlag(flags.ready));
```

This describes an `owner = { has_country_flag = ... }` trigger block. The SDK
checks both that the enclosing scope can navigate through `owner` and that the
nested condition is valid in country scope.

## Capture an outer scope deliberately

TypeScript keeps outer variables in lexical scope. The SDK preserves that
relationship in nested effect callbacks:

```ts
immediate: (country) => {
  country.everyOwnedPlanet({ limit: hasOwner() }, (candidate) => {
    country.addResource({ resource: "influence", amount: 10 }); // PREV: the outer country
    candidate.addDeposit("d_minerals_1"); // THIS: the iterated planet
  });
};
```

The callback parameter exists only for a scope push. A captured ancestor proxy
records in the nested block through the game's `PREV` path. Up to four verified
pushes are supported (`PREV` through `PREVPREVPREVPREV`); a replacement or an
unknown scope transition fails rather than guessing a path.

Blocks that keep the same game scope take no parameter:

```ts
immediate: (country) => {
  country.if(hasCountryFlag("ready"), () => {
    country.hiddenEffect.effects(() => country.log("still country scope"));
  });
};
```

Use named context references such as `ctx.root`, `ctx.from`, `ctx.fromfrom`,
and `ctx.prev`, plus saved targets, when the script needs their
absolute game meaning. Captured proxies describe lexical ancestors only; they
do not infer `ROOT` or `FROM`.

## Context keeps stable scopes available

An effect closure's second parameter is its script context:

```ts
immediate: (planet, ctx) => {
  ctx.from.effects((country) => {
    country.addResource({ resource: "influence", amount: 50 });
  });
};
```

This event runs in planet scope and declares a country `FROM`.
`ctx.from.effects(...)` opens that country and records `add_resource` inside a
`from = { ... }` block.

The available context depends on what the field declares:

- `ctx.self` names the block's own `THIS`. It is relative, so it is a value to
  pass, not a reference to open.
- `ctx.root` is the execution's stable `ROOT`, when the field declares it.
- `ctx.from`, `ctx.fromfrom`, `ctx.fromfromfrom`, and
  `ctx.fromfromfromfrom` are the field's declared FROM chain.
- `ctx.prev`, `ctx.prevprev`, `ctx.prevprevprev`, and
  `ctx.prevprevprevprev` are the field's declared PREV chain.

Every declared context member is a typed reference. You can open it with
`.effects(...)`, put a condition on them with `.trigger(...)`, pass them to
fields that expect a scope value, or follow legal links from them. If a field
does not declare one of these scopes, that context member cannot be used and
TypeScript rejects it.

`ctx.self` is deliberately a value, not an openable reference. It serializes
as relative `this`, so opening or navigating from it inside a nested block
would start from that nested `THIS`, not recover the scope where the outer
closure began. Use the outer scope parameter while recording in the same
block, and use stable `root`, `from`, or another absolute reference when
nested script must refer back.

Effect closures are not the only place `ctx` appears. Trigger and weight
fields whose rules declare a `FROM` also accept a one-parameter closure form,
`(ctx) => Trigger`, so a condition can name `ctx.from` or `ctx.self` — for
example `allow: (ctx) => ctx.from.trigger(siteIsUnlocked)` on an
archaeological site. See
[Archaeological sites](/reference/archaeological-sites/) for a worked example.

## Event `FROM` comes from execution `ROOT`

An event fire is the exception to the caution above: the `scopes.from` argument is
checked, not navigated. The value is a **witness** — it proves to the type
checker which scope the called event will see as `FROM` — and nothing is
opened from it.

When one event fires another without an explicit scopes override, the called
event receives the firing execution's `ROOT` as natural `FROM`. It does not
always receive the call site's current `THIS`. At a top-level event effect,
`THIS` and `ROOT` are the same. `ctx.self` can therefore witness the natural
`FROM` expected by the event being fired, even after a nested block changes
`THIS`. `stormWorld` below is a saved event target — a scope stored earlier
under a name; see [Events](/concepts/events/):

```ts
const stormWorld = eventTarget<"planet">("crystal_resonance_storm_world");

immediate: (country, ctx) => {
  stormWorld.effects((planet) => {
    planet.planetEvent({ id: aftershock, scopes: { from: ctx.root } });
  });
};
```

The event-target block changes `THIS` to the saved planet, but the firing
execution's root remains the country. The witness states that the called planet
event receives that country as `FROM`.

Some content fields start with different `THIS` and `ROOT` scopes. A planetary
initializer effect, for example, can run with a planet as `THIS` and a country
as `ROOT`. In such a split-root field, `ctx.self` is not a valid witness for an
event expecting country `FROM`; use `ctx.root` or another explicit absolute
reference:

```ts
initEffect: (planet, ctx) => {
  planet.planetEvent({ id: aftershock, scopes: { from: ctx.root } });
};
```

The type system rejects the unsafe `ctx.self` form at known split-root sites.
If a type assertion bypasses that check, the build throws rather than writing
a misleading event fire.

## Relative and absolute references

The difference is easiest to remember by asking what happens after a nested
scope change:

| Reference           | Meaning inside nested script                  |
| ------------------- | --------------------------------------------- |
| `this` / `ctx.self` | Relative to the block where it is written     |
| `root` / `ctx.root` | The same execution root throughout the script |
| `from` / `ctx.from` | The same declared FROM throughout the script  |
| Saved event target  | The scope captured when the target was saved  |

Use relative navigation when the relationship should move with the current
block. Use an absolute reference when the script must keep naming one known
scope after `THIS` changes.

PDXScript also has deeper FROM and PREV chains. When the rules declare them,
the context map exposes `fromfrom` through `fromfromfromfrom` and `prev`
through `prevprevprevprev`. Captured lexical proxies remain separate: they
still route PREV through nested callbacks and do not claim a field-level
ambient declaration.

## Where scope legality is checked

Scope legality is decided by the generated TypeScript interfaces before the
recorder runs: each closure receives the scope interface its field declares, a
scope link's callback receives its declared landing interface, and every named
context slot exposes only the scope the owning field declares. The recorder
itself only records and serializes; it does not repeat those rules at runtime.

The [scope catalog](/scopes-and-effects/) shows the generated interface, legal methods, event kinds,
and outgoing transitions for every canonical SDK scope.

## Read scope type errors as game rules

The useful part of a scope error is usually the two scopes or the missing
member:

- **“Property does not exist on type …Scope”** means that effect or transition
  is not legal in the current game scope.
- **`Trigger<"planet">` is not assignable to `Trigger<"country">`** means the
  game would evaluate that condition in another scope.
- An unavailable named context member means the field does not declare that
  ambient scope.
- An event-fire witness mismatch means the called event's declared `FROM` does
  not match the witnessed firing scope.

Move the operation to a legal scope, use a typed scope transition, or choose a
condition valid in the current scope. Do not cast the error away: the recorder
intentionally trusts the generated interfaces rather than recreating their
rules after TypeScript has checked them.
