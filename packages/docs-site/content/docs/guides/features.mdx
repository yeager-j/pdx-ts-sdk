A **Feature** is an explicit group of mod items with an optional output file
stem — the middle part of the emitted filename. This complete example places a
technology and the building it unlocks in one named Feature:

<PairedExample name="grouped-feature" />

These items do not enter the build merely because their module was imported or
because their values were exported. They enter when you place them in a
Feature and pass that Feature to `mod.compile`.

## Why Features are explicit

`mod.compile` — [the Fold](/guides/the-pipeline/) — accepts only Features
created by this mod's `createMod` object, not loose items. This gives the Fold
two facts that TypeScript module layout cannot provide:

- **Selection:** which definitions, events, localization,
  [Asset files](/concepts/assets/), and other items belong in this build.
- **Placement:** which authored file stem groups those items in outputs that
  use per-feature files.

This ownership also prevents a Feature created by one mod from being compiled
as part of another mod.

A Feature can hold several kinds of item at once — technologies, events,
[on-action contributions](/concepts/on-actions/),
[patch plans](/guides/patching-vanilla/), localization, and Asset files — so
you do not need one source directory per content kind. The Fold fans them out
to the directories Stellaris expects.

## Feature stems and output filenames

A Feature stem must be lowercase `snake_case` and cannot contain `/`. In
`mod.feature("resonance", items)`, the stem is `resonance`. For registry
content, it contributes to paths such as:

```text
common/technology/my_mod_resonance.txt
```

The registry chooses the directory and extension; the mod prefix and Feature
stem choose the filename.

A directly compiled Feature may pass `undefined` instead of a stem:
`mod.feature(undefined, items)`. The outputs then fall back to their default
filenames — registry content uses the registry's own stem
(`common/technology/my_mod_technology.txt`), events use
`events/<prefix>_events.txt`, and localization drops the stem segment
(`localisation/english/<prefix>_l_english.yml`).

Asset paths and shared outputs such as on-action contributions and patch
plans have their own path rules, so a Feature stem does not directly relocate
them.

## Declare the Features the mod ships

A project declares its module tree the way a Rust crate does with `lib.rs` and
its `mod` lines: `src/features.ts` re-exports each feature module's `feature`,
and the build takes that module as a namespace. The scaffold generates three
files for this:

```ts
// src/mod.ts
import { createModProject } from "@pdx-ts/sdk";

import manifest from "../stellaris-mod.json" with { type: "json" };

export const project = createModProject(manifest, {
  projectRoot: new URL("../", import.meta.url),
});

export const { config, mod } = project;
```

```ts
// src/features.ts
export { feature as example } from "./features/example.ts";
```

```ts
// src/build.ts
import { project } from "#mod";

import * as features from "./features.ts";
import { loadVanilla } from "./vanilla.ts";

export async function buildTheMod() {
  return project.build(features, { vanilla: loadVanilla() });
}
```

Project creation validates the manifest and its source layout but reads no
source files. `project.build(features)` compiles every export of the features
module, captures the optional `assetsDirectory`, and performs one
capability-owned Fold. Every export of `src/features.ts` must be a Feature of
this mod: a string or a helper there is refused by name, and a module with no
exports is refused rather than built as an empty mod. An explicit array is
accepted in the same position.

A module under `src/features/` that no line names is dead code that still
compiles and passes its tests. TypeScript's import graph is the module tree, so
the scaffold's `npm run lint` runs [knip](https://knip.dev) and reports such a
module by path. knip checks that a file is reached, not that it is declared: a
module a declared feature imports for a helper is reached, so if that module
also calls `mod.feature`, `project.build` refuses the build and names the
Feature, because content you wrote would otherwise be dropped. A wrong export
is a type error: `project.build` accepts only Features created by this
project's `mod`.

`src/mod.ts` imports nothing else of the project. Feature modules import `mod`,
so `mod.ts` cannot import `features.ts` back without evaluating them before
`mod` exists; `src/build.ts` is the one module that imports both sides. For a
pipeline with different stages, compose `mod.assetTree` and `mod.compile`
directly. `mod.compile` accepts the same features module or array.

### The private tree under a feature module

A feature module can be one file or the root of its own tree. `mod.feature`
accepts one module namespace, or a shallow array that mixes individual Items
and module namespaces. Every Item-valued export of a namespace is placed, a
nested `export * as` namespace is walked the same way, and every other export
(a string, a function, a plain object) is module API and is left alone. One
Item reached under two names in one namespace is placed once.

```ts
// src/features/resonance.ts
import { mod } from "#mod";

import * as events from "./resonance/events.ts";
import * as technologies from "./resonance/technologies.ts";

export const feature = mod.feature("resonance", [technologies, events]);
```

A bag that holds no Items is refused, and a Feature among them is refused
rather than dropped or placed twice. `mod.feature("empty", [])` stays legal,
because an explicit empty list is a decision. The array is deliberately
shallow: use module exports for deeper organization rather than nested arrays.

### One namespace per Feature

An event namespace is in strict bijection with an event file, and a Feature's
stem names that file, so a namespace belongs to exactly one Feature. Create it
in the feature module that owns it and do not export the handle from a Feature.
The scaffold's ESLint rule `pdx/one-namespace-per-file` reports a second
namespace in one feature module.

## Source layout is not identity

The module path and basename are not used as a Feature stem, content id, event
id, or emitted path. These two source locations can produce the same output:

```text
src/features/resonance.ts
src/features/research/crystal-theory.ts
```

If the moved module still exports the same `mod.feature("resonance", ...)`, with
the same items, its mod output is unchanged. You may need to update relative
imports and the module's line in `src/features.ts`, but the path itself does
not become mod content.

The authored values remain significant:

- Changing a Feature stem changes every filename that contains the stem: the
  registry, event, and localization outputs.
- Moving such an item to a Feature with another stem changes its per-feature
  output file.
- Changing an item's authored logical name changes the id minted for it.
- Changing an event namespace or number changes its event id.

Organize `src/features/` around the concepts people maintain together: an event
chain, research theme, origin, crisis, or another gameplay feature. Let the
Fold map those concepts to Stellaris's output directories. This keeps source
organization useful to the author without making refactors change game-facing
identity by accident.

[References and identity](/guides/references-and-identity/) explains the id
minting rules behind the last two bullets.
