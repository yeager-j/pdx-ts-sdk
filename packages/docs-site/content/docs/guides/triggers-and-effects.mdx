The most important rule is about time:

> Your TypeScript runs once, when you build the mod. Stellaris later evaluates
> the PDXScript files that build produced. The game never runs your TypeScript.

This creates a deliberate difference between the SDK's two script models:

| Model   | What you author                 | At build time (TypeScript)                          | At game time (Stellaris)     |
| ------- | ------------------------------- | --------------------------------------------------- | ---------------------------- |
| Trigger | A declarative condition tree    | The tree is constructed                             | The condition is evaluated   |
| Effect  | A synchronous recording closure | The closure runs once and records PDXScript entries | The recorded entries execute |

The complete example below reuses one country-scoped Trigger in two places. A
technology uses it as `potential`, and an event uses it as the `limit` of an
in-game `if` effect.

## Triggers are trees, not booleans

A leaf builder such as `hasCountryFlag(...)` returns a `Trigger<"country">`.
Calling the builder constructs a value that describes this PDXScript:

```pdxscript
has_country_flag = crystal_resonance_heard_the_hum
```

It does not check the current game state. There is no current country while
Node.js is building the mod.

Leaf builders take the shapes the game rules declare. A flag test takes one
argument. A numeric test takes a comparison operator and a value, such as
`numOwnedPlanets(">=", 3)`, and some argument objects embed the operator as a
tuple, such as `hasCountryResource({ type: "energy", amount: [">=", 100] })`.
The accepted operators are `=`, `>`, `<`, `>=`, `<=`, and `!=`.

Do not write a boolean-returning callback for an in-game condition:

```ts
// Wrong model: this TypeScript would run during the build, not in Stellaris.
const wrongPotential = () => {
  if (heardTheHum && !rejectedTheHum) {
    return true;
  }

  return false;
};

// A Trigger field cannot accept this boolean-returning callback.
```

Build a declarative Trigger instead:

```ts
const resonanceReady = and(
  hasCountryFlag(flags.crystal_resonance_heard_the_hum),
  not(hasCountryFlag(flags.crystal_resonance_rejected_the_hum))
);

const technology = mod.technology("resonance_weapons", {
  // Other fields omitted.
  potential: resonanceReady,
});
```

The paired example above builds exactly this Trigger; its PDXScript tab shows
the `potential` block the game receives.

Ordinary condition fields such as `potential` and `limit` implicitly AND their
direct members, so `and(a, b)` can place both conditions directly in those
fields.

Triggers are ordinary read-only values. You can name one, return one from a
helper, compose it into a larger tree, and reuse it anywhere its scope
permits.

A Trigger cannot be the condition of a plain TypeScript `if`. A Trigger is
typed as callable on purpose: write `if (resonanceReady)` and TypeScript
reports the error it reports for any always-truthy function, instead of
quietly treating the condition tree as `true`. Calling a Trigger throws, with
a message about the build-time and game-time boundary.

Some trigger fields also accept a closure form, `(ctx) => Trigger`, for a
condition that must name the definition's `FROM` or `ROOT` scope. That closure
returns a declarative tree like any other; it is not a boolean callback.
[Scope and context](/guides/scope-and-context/) covers `ctx`.

### Combine conditions explicitly

Use trigger combinators for game-time logic:

| TypeScript                | Game-time meaning              |
| ------------------------- | ------------------------------ |
| `and(a, b)` or `a.and(b)` | Both conditions pass           |
| `or(a, b)`                | At least one condition passes  |
| `not(a)`                  | The condition does not pass    |
| `nor(a, b)`               | Neither condition passes       |
| `nand(a, b)`              | The conditions do not all pass |

The combinators preserve grouping. For example, `not(and(a, b))` remains “not
both,” while `nor(a, b)` means “neither.” This distinction matters because the
immediate children of Stellaris's `NOT` block have NOR semantics. Let the SDK
build the tree instead of trying to recreate the grouping by hand.

Beyond the table, `calcTrueIf({ amount, conditions })` passes when at least
`amount` of its conditions pass — the one combinator with no TypeScript
equivalent — and `hiddenTrigger(...)` hides its conditions from generated
tooltips. The `customTooltip` trigger builders replace a block's generated
tooltip text.

## Effects are build-time recording closures

An effect field receives a scope object in a synchronous closure:

```ts
immediate: (country) => {
  country.addResource({ resource: "influence", amount: 50 });
};
```

The SDK calls this closure once during the build. `country` is a recorder
handle, not a live empire from a running game. Calling
`country.addResource(...)` appends an `add_resource` entry to the event's
`immediate` block.

The exact moment of recording varies — event effects record when the event is
created, and some content effect fields record when the
[Fold](/guides/the-pipeline/) lowers the definition — but every closure runs
during the build. None runs in Stellaris.

This means ordinary TypeScript control flow is still useful, but it controls
the build:

```ts
const includeDebugLog = process.env.MOD_DEBUG === "1";

immediate: (country) => {
  if (includeDebugLog) {
    country.log("debug build");
  }
};
```

One build includes the `log` effect or omits it. Stellaris does not reevaluate
`MOD_DEBUG`. A TypeScript `for` loop works the same way: it can record several
effect entries, but no JavaScript loop is written into the mod.

[See more build-time TypeScript patterns](/guides/advantages-of-typescript/),
including generated technology ladders and data-driven event options.

Effect closures must remain synchronous. Do asynchronous work before creating
the definition, await its result, and then close over that result. The recorder
rejects async closures and scope objects used after their recording closure has
finished.

## Use `scope.if` for an in-game branch

To make Stellaris choose a branch from game state, record its structural `if`
effect:

```ts
immediate: (country) => {
  country
    .if(resonanceReady, (c) => {
      c.addResource({ resource: "influence", amount: 50 });
    })
    .else((c) => c.log("the hum went unheard"));
};
```

The recorder writes:

```pdxscript
if = {
	limit = {
		has_country_flag = crystal_resonance_heard_the_hum
		NOT = {
			has_country_flag = crystal_resonance_rejected_the_hum
		}
	}
	add_resource = {
		influence = 50
	}
}
else = {
	log = "the hum went unheard"
}
```

The build runs both callbacks, so both branches end up in the file. In game,
Stellaris evaluates `limit` and executes only the matching branch.

Continue a chain with `.elseIf(condition, body)` and finish it with
`.else(body)`. Keep the calls chained together: Stellaris associates
`else_if` and `else` with the preceding `if` by position, so the recorder
refuses an unrelated effect inserted between chain links.

### Other structural effects

Structural effects share the model: TypeScript records the shape, Stellaris
runs it. An iterator's `limit` is a Trigger evaluated for each candidate in
game, while its callback records the body during the build:

```ts
country.everyOwnedPlanet({ limit: hasOwner() }, (candidate) => {
  candidate.log("owned world");
});
```

The same family covers in-game randomness and repetition: `randomList` and
`lockedRandomList` pick one weighted arm, `random({ chance })` runs its body
sometimes, `whileLoop({ count })` repeats it, and `hiddenEffect` runs its body
without tooltip text. Reach for these, not `Math.random()` or a TypeScript
loop, when the game must decide at run time.

[List of Effects](/scopes-and-effects/effects/) classifies every current SDK method as an ordinary
effect, structural method, or event-fire method and shows its exact signature and legal scopes.

The Trigger passed to a field or `limit`, and the effects available on a scope
object, are checked against the scope where Stellaris will run that block.
[Scope and context](/guides/scope-and-context/) explains scope changes,
`ctx.self`, `ctx.from`, `ctx.root`, and how to read those type errors.

## Keep the two timelines separate

- Use ordinary TypeScript values, functions, `if`, and loops to decide what the
  build constructs or records.
- Use Trigger builders and combinators to describe conditions Stellaris will
  evaluate.
- Use `scope.if`, `.elseIf`, and `.else` to record an in-game effect branch.
- Use typed scope links and context when script must run in another game scope.
- Remember that every callback has finished before Stellaris starts.
