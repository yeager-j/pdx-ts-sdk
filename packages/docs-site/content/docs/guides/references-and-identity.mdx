Every definition needs a stable game-facing identity, and every reference must
point to the kind of thing its field expects. The SDK keeps those two concerns
connected: definitions mint ids, and the definition values themselves can be
passed into reference fields.

This complete example connects three kinds of reference:

- one authored technology requires another authored technology;
- the same prerequisite list refers to a vanilla technology; and
- a vanilla scripted effect receives an authored technology as its `TECH`
  parameter.

The example also carries a scripted Trigger in `potential` and an event minted
from a namespace and number; both get their own sections below.

PDXScript tab, the Fold has resolved the typed values to their minted ids and
left the vanilla id unchanged.

## A prefix and logical name mint the id

`createMod` binds a prefix to the authoring capability —
`prefix: "luminous_cartography"` in the example above. The prefix is lowercase
`snake_case`. It is the mod's namespace for content ids and contributes to
most SDK-generated output filenames. Most content definitions take a logical
name, also in lowercase `snake_case`, and mint the full id from three parts:

| Part             | Technology example     |
| ---------------- | ---------------------- |
| Mod prefix       | `luminous_cartography` |
| Registry segment | `tech`                 |
| Logical name     | `spectral_surveying`   |

Together they mint `luminous_cartography_tech_spectral_surveying`.

The registry supplies its segment. For example,
`mod.building("spectral_archive", ...)` mints
`luminous_cartography_building_spectral_archive` instead. Three registries
mint a different shape: `mod.spriteType("resonance_icon", ...)` mints
`GFX_luminous_cartography_resonance_icon`, and `mod.pdxmesh` and
`mod.pdxparticle` mint `<prefix>_<name>` with no registry segment.

Use logical names at definition sites. Do not manually repeat the prefix or
registry segment:

```ts
const spectralSurveying = mod.technology("spectral_surveying", {
  // Other fields omitted.
});
```

The resulting `spectralSurveying.id` is the complete minted id. The value also
carries its registry reference type. A Feature accepts only items minted by
the same `createMod` call, so an item from another mod cannot be placed in
this build.

<Callout type="info">
The set of registry segments is the mod's **id profile**. Advanced projects
can replace the whole profile with `createMod(config, { ids: profile })`; a
partial override is rejected, because one build must mint every id the same
way.
</Callout>
Some definitions contain nested ids instead of references to separately
minted items. Those fields require a complete lowercase `snake_case` id that
starts with the mod prefix. The SDK does not silently derive a nested id from
its parent, because Stellaris treats that nested key as its own identity.

An item's source filename is not part of this identity. A Feature stem controls
which output file receives the item, not its id. See
[Features and discovery](/guides/features-and-discovery/) for that distinction.

## Pass authored items as references

When one authored item points to another, pass the item value:

```ts
const observatoryNetworks = mod.technology("observatory_networks", {
  // Other fields omitted.
  prerequisites: [spectralSurveying],
});
```

The `prerequisites` field expects technology references, so a building value
does not typecheck there. The object preserves more information than a copied
string: TypeScript checks the target registry, and the Fold knows this is a
reference to content owned by the current mod.

The referenced item must also enter the build. If `spectralSurveying` is
referenced but its Feature is not passed to `mod.compile`, the Fold rejects the
dangling reference before serialization. This catches a common failure where
an import exists but the definition was left out of the selected Features.

Pass values through helpers and data structures instead of converting them to
strings early. The SDK will lower a reference to its id when it serializes the
field.

## Check vanilla ids through `vanilla`

Use the SDK's `vanilla.*` helpers for content defined by Stellaris:

```ts
// Inside mod.technology(...).
prerequisites: [spectralSurveying, vanilla.technology("tech_lasers_1")];
```

The hard peer dependency `@pdx-ts/stellaris-ids` supplies the literal ids for
the game version the installed package was generated from. A typo such as
`tech_lazers_1` is therefore a TypeScript error. The helper returns a reference
for the requested registry, so a checked vanilla building cannot be passed
where a technology is required.

There is no mode where a missing identifier package silently widens these
helpers to unchecked strings. The package must resolve, and an id must belong
to its pinned set or TypeScript rejects it. Builds that also load a local
Stellaris install must match the identifier package's game version; see
[Patching vanilla](/guides/patching-vanilla/).

Large registries also provide navigable forms that are grouped by their
vanilla source file:

```ts
vanilla.spriteType.eventpictures.GFX_evt_ship_in_orbit;
vanilla.staticModifier.deficit.food_deficit;
```

Those groups are only navigation. The leaf still carries the exact vanilla id.
The checked call form remains available when copying a known id is clearer.

Vanilla events are checked the same way through a navigable trie:
`vanilla.event.crisis.$10` is a typed reference to the country event
`crisis.10`, carrying its scope and kind.

### Raw strings are an explicit external escape hatch

Reference fields still accept raw strings for ids that cannot appear in the
pinned vanilla package, such as content supplied by another mod:

```ts
// Inside mod.technology(...).
prerequisites: ["partner_mod_tech_shared_sensors"];
```

Use this deliberately. TypeScript cannot check the target registry or spelling
of an external string, and the Fold cannot prove that another mod will be
installed. Prefer an authored item for your own content and `vanilla.*` for
Stellaris content.

## Scripted triggers and effects are checked bindings

Vanilla's scripted triggers and effects are definitions in
`common/scripted_triggers` and `common/scripted_effects`. They are not the
same as the Trigger and effect builders the SDK generates from the game's
rules.

Import their pre-bound functions from the identifier package:

```ts
import { giveTechOptionOrProgressEffect } from "@pdx-ts/stellaris-ids/effects";
import { isRegularEmpire } from "@pdx-ts/stellaris-ids/triggers";
```

Each binding carries three facts extracted for the selected game version:

- the definition's exact name;
- its `$PARAM$` names and which are required; and
- the scopes in which its body is legal.

The example uses both. `isRegularEmpire()` typechecks in `potential` because
its inferred scope is `country`, and the effect call below is rejected if
`TECH` is misspelled or missing:

```ts
// Inside the event definition.
immediate: (country) => {
  country.run(giveTechOptionOrProgressEffect({ TECH: observatoryNetworks }));
};
```

A scripted effect binding creates an inert effect call. Use `scope.run(...)`
inside an effect closure to record it. A scripted trigger binding returns an
ordinary Trigger value, so it composes with `and`, `or`, and the other Trigger
builders.

Every parameterless scripted trigger accepts an optional boolean:
`isMachineEmpire(false)` emits `is_machine_empire = no`. The boolean is an
argument in the emitted script, not a build-time test — your TypeScript never
learns whether the empire is a machine empire. A trigger that takes `$PARAM$`s
takes its parameter bag instead of the boolean.

The package ships names, parameters, and inferred scopes — never vanilla
script bodies, localization, or assets. When the scope cannot be determined,
the binding widens rather than guessing a restriction, so a wide scope is not
proof the definition is legal everywhere.

When the inferred scope of a known vanilla definition is wrong for your use,
re-bind it without giving up name checking:
`scriptedTrigger("is_regular_empire", "planet")` checks the name against the
pinned package and asserts only the scope. A misspelled name is still a
TypeScript error in this form. The same applies to
`scriptedEffect(name, scope)`, and
`scriptedTriggerModifier("check_recent_migration", { AMOUNT: 5 })` binds a
vanilla trigger-based modifier row by checked name and parameters.

For a scripted definition supplied by another mod or a newer game version, the
SDK provides the fully unchecked escape hatch:

```ts
import { scriptedEffect, scriptedTrigger } from "@pdx-ts/sdk";

const hasChartedRift = scriptedTrigger.unchecked("has_charted_rift", "country");
const chartRift = scriptedEffect.unchecked("chart_rift", "country");

// Inside the event definition.
immediate: (country) => {
  country.run(chartRift());
};
```

The name, parameters, and claimed scope are all unchecked in that form. An
unchecked scripted effect still creates an inert call and must be passed to
`scope.run(...)`. Prefer the pre-bound imports whenever the definition is
present in the pinned identifier package, and the checked
`scriptedTrigger(name, scope)` form when only the scope needs overriding.

[Triggers and effects](/guides/triggers-and-effects/) explains how Trigger
values and recorded effect calls cross the build-time/game-time boundary.
[Scope and context](/guides/scope-and-context/) explains why a checked binding
may be legal in one callback and rejected in another.

## Events have namespace-and-number identity

The paired example's `mod.namespace("discovery")` shows the other identity
scheme. Events do not use registry segments. A namespace created without a
suffix is the mod prefix; a suffix extends it:

```ts
const rootEvents = mod.namespace(); // luminous_cartography
const discovery = mod.namespace("discovery"); // luminous_cartography_discovery

const patternEmerges = discovery.country(1, {
  // Other fields omitted.
});
// patternEmerges.id is luminous_cartography_discovery.1
```

The local event number is a non-negative safe integer. Keep one namespace in
one Feature stem: the Fold emits a namespace's events together, orders them by
number, and rejects duplicate event ids.

## Exact names are only for meshes and particles

Mint every id by default. Mesh and particle labels are the narrow
exception because opaque `.asset` files can refer to an engine label that must
be preserved verbatim.

Their default behavior still prepends the prefix:

```ts
mod.pdxmesh("survey_ship_mesh", { file: "gfx/models/survey_ship.mesh" });
// luminous_cartography_survey_ship_mesh
```

If an existing `.asset` file requires the complete label in a different
shape, pass `{ prefix: false }`:

```ts
mod.pdxmesh(
  "SurveyShip_luminous_cartography_mesh",
  { file: "gfx/models/survey_ship.mesh" },
  { prefix: false }
);
```

`prefix: false` means “this argument is already the complete id.” It does not
mean “this item is unowned.” The exact name must still contain the mod prefix
as a whole `_`-delimited segment. Only `pdxmesh` and `pdxparticle` support this
option; sprites and ordinary content registries continue to mint their ids.

Use the exact-name form only when an external engine label forces it. The
default mint is simpler, consistent across registries, and harder to collide
with another mod or vanilla content.

## Read reference failures as identity failures

When the compiler rejects a reference, check these facts in order:

1. Did the field receive the correct registry type?
2. Was the authored target placed in a Feature passed to `mod.compile`?
3. Is a vanilla id spelled exactly as it appears in the pinned game version?
4. Is an external raw string intentional, with its dependency documented?
5. For scripted bindings, are the `$PARAM$` names and current scope correct?

Keep authored items as typed values for as long as possible. That lets one
definition site decide identity and lets every reference reuse the decision.
