Use this reference in either direction:

- **Scope first:** open a page under **Scopes** when you know the interface you have and need to
  see its legal generated triggers, effects, event-fire methods, and outgoing scope transitions.
- **Effect first:** open [List of Effects](./effects/) when you know a TypeScript method or
  PDXScript key and need its signature, category, and legal scopes.
- **Trigger first:** open [List of Triggers](./triggers/) when you know a TypeScript builder or
  PDXScript key and need its signature, generated description, and legal scopes.

All three views read the same script-reference records. They describe the current SDK-supported
authoring surface after its reviewed overlays and handwritten structural methods are applied. They
do not claim to list every trigger, effect, or scope behavior available in a live Stellaris build.

## Read the model before the inventory

- [Triggers and effects](/guides/triggers-and-effects/) explains recording and evaluation.
- [Scope and context](/guides/scope-and-context/) explains `THIS`, `ROOT`, `FROM`, and scope changes.
- [Events](/concepts/events/) explains event bodies and typed event references.

## What the reference classifies

**Ordinary effects** are the generated SDK methods that record game effects. Their entries show the
PDXScript key, exact TypeScript signature, and availability.

**Generated triggers** are builder functions that record conditions. Their entries show the
PDXScript key, exact TypeScript signature, generated description, and the scopes where that key is
legal.
Handwritten trigger combinators and typed leaves remain documented in
[Triggers and effects](/guides/triggers-and-effects/).

**Structural and control-flow methods** record branching, iteration, targets, and other script
structure. They are handwritten SDK methods with their own reference records; some have no single
fixed PDXScript key.

**Event-fire methods** record a typed event fire. Each entry keeps two facts separate: the scopes
where the fire call is legal and the scope where the fired event body runs.

Scope-link properties are different. They navigate from one scope interface to another, so each
scope page lists them under **Outgoing scope transitions**, not as effects.

The scope catalog contains one page for every canonical generated SDK scope. Start with
[Country](./scopes/country/) for multiple event kinds, [Storm](./scopes/storm/) for an event key that
does not mechanically match its scope name, or [Army](./scopes/army/) for the explicit no-event-kind
state.
