An **on-action** is a named hook that Stellaris invokes when something happens:
the game starts, a ship enters a system, a colony changes hands, or another
engine-defined transition occurs. Your mod contributes event ids to that hook;
the game calls those events when it reaches the hook.

This complete example attaches one country event to the game-start country
hook and adds weighted choices to the scopeless five-year pulse:

The event definition and the hook contribution are separate mod items. The
Fold writes the event under `events/`, its text under `localisation/`, and the
registration under `common/on_actions/`.

## Attach an event with `mod.on`

Import the generated hook table, choose a hook, and pass one or more event
values. The example's `mod.on(onActions.onGameStartCountry, [firstSignal])`
is the ordinary-list shorthand. Use the object form when the hook needs
`randomEvents`, or both lists:

```ts
mod.on(onActions.onGameStartCountry, {
  events: [firstSignal],
  randomEvents: [{ weight: 80, event: firstSignal }, { weight: 20 }],
});
```

Each present list must contain at least one entry, and the object must contain
at least one list.

`mod.on` returns a contribution; it does not register anything on its own.
Place the returned value in a Feature and include that Feature in
`mod.compile`, as the example's `awakening` Feature does. The hooked event
must be placed in the same build too. A contribution that names an event
omitted from the selected Features fails during the Fold.

Set `isTriggeredOnly: true` on events entered through on-actions. The hook is
their entry point, so they need no other route in — see the caution against
mean-time-to-happen on [Events](/concepts/events/).

## Find hooks through `onActions`

`onActions` is generated from the hook declarations for the supported
Stellaris version. Use editor autocomplete after `onActions.` to browse the
available names, and open a member's definition to read any source
documentation carried with it.

The TypeScript member is camel-cased while its value preserves the exact game
name. Three examples of that mapping:

| TypeScript member                 | Game hook                  |
| --------------------------------- | -------------------------- |
| `onActions.onGameStartCountry`    | `on_game_start_country`    |
| `onActions.onMonthlyPulseCountry` | `on_monthly_pulse_country` |
| `onActions.onEnteringSystem`      | `on_entering_system`       |

`onActions` is the versioned list. Do not copy a hook name into a raw string:
`mod.on` accepts an `OnActionRef`, so a misspelling or a hook absent from the
supported Stellaris version fails in TypeScript.

Some game hooks are scopeless, such as `onActions.onFiveYearPulse`. They accept
checked scopeless references such as `vanilla.event.situation.$2000` in
`randomEvents`. The SDK cannot define a scopeless event body, so ordinary
authored event values still require a scoped hook.

Thirteen hooks the game defines are absent from `onActions` because their
declarations do not map to the SDK's scope model — most declare an
unresolvable `FROM`. They are `on_country_created`, `on_destroying_station`,
`on_fleet_enter_orbit`, `on_fleet_leave_orbit`,
`on_galaxy_map_during_tutorial`, `on_operation_chapter_finished`,
`on_operation_finished`, `on_pop_group_added`, the four `on_resolution_*`
hooks, and `debug_spawn_storm_random_system`. A hook missing from
autocomplete is therefore not proof that the game lacks it.

## The hook decides `THIS` and `FROM`

Each generated hook carries the scope it supplies as `THIS` and, when present,
its `FROM` scope. Every event in the `mod.on` list must declare that exact
contract.

The paired example works because both sides are country-scoped and neither
declares `FROM`:

```ts
const firstSignal = events.country(1, {
  isTriggeredOnly: true,
  // Other fields omitted.
});

mod.on(onActions.onGameStartCountry, [firstSignal]);
```

A planet event cannot be attached to this hook. A country event that declares
`scopes: { from: "country" }` cannot be attached either, because the hook supplies no
`FROM`.

For a hook that supplies both scopes, declare both on the event:

```ts
const arrival = events.ship(2, {
  scopes: { from: "system" },
  isTriggeredOnly: true,
  immediate: (_ship, ctx) => {
    ctx.from.effects((system) => {
      system.log("a ship entered this system");
    });
  },
});

mod.on(onActions.onEnteringSystem, [arrival]);
```

`onEnteringSystem` supplies a ship as `THIS` and a system as `FROM`. The event
method and its `scopes` declaration preserve those two facts through the event
body. A mismatch is a TypeScript error and is checked again during the Fold.

```ts
const badArrival = events.ship(2, {
  scopes: { from: "country" }, // Wrong scope
  isTriggeredOnly: true,
});

// TypeScript error (Type "country" is not assignable to type "system")
//                                     ↓
mod.on(onActions.onEnteringSystem, [badArrival]);
```

Some hooks supply more than two scopes: the rules for `on_entering_system`
also name a country as `FROMFROM`. Its event body exposes that scope as
`ctx.fromfrom`, and the full named contract is checked at registration.

[Scope and context](/guides/scope-and-context/) explains how `THIS`, `ROOT`,
and `FROM` behave inside the event's triggers and effects.

## Hooking is different from firing

Both operations cause the game to run an event, but they enter the game from
different places:

| Hook with `mod.on`                                | Fire from an effect                                  |
| ------------------------------------------------- | ---------------------------------------------------- |
| Adds an event id to an engine-defined hook        | Writes an event-fire effect into authored script     |
| The hook supplies the target scope and `FROM`     | The effect's current scope selects the target        |
| Runs when Stellaris reaches that named transition | Runs when the containing effect executes             |
| Has no per-registration delay                     | Can set `days`, `months`, `years`, or `random` delay |

Use an on-action when the entry point is a lifecycle event that Stellaris
already exposes. Use `countryEvent`, `planetEvent`, and the other typed fire
methods when your own event, content effect, or script flow decides when the
next event runs.

Hooking does not emit a `country_event = { ... }` effect. It emits a list entry
such as:

```pdxscript
on_game_start_country = {
  events = { crystal_resonance_awakening.1 }
}
```

[Events](/concepts/events/#fire-typed-event-references) explains typed event
firing, delays, targets, and explicit `FROM` witnesses.

Stellaris script can also declare a custom on-action name and invoke it with
the `fire_on_action` effect. The SDK supports neither yet: `mod.on` accepts
only the generated hooks, and no typed `fire_on_action` effect exists. Model
the flow with typed event fires instead.

## Contributions merge into one file

Every `mod.on` contribution in the build merges into:

```text
common/on_actions/crystal_resonance_on_actions.txt
```

This path is shared across Features. A Feature stem organizes the source item
but does not create another on-actions file or relocate the contribution.

Several events can be attached in one call:

```ts
mod.on(onActions.onGameStartCountry, [firstSignal, secondSignal]);
```

`mod.on` rejects an empty list. Event order is preserved within that one
`mod.on` call because Stellaris fires the list in order. Hook blocks and
separate contributions are sorted by the Fold, so the order of Features or
calls does not control their serialized position.

The same event cannot be registered twice on the same hook. It can be attached
to different compatible hooks, and one hook can collect events from several
Features. The Fold merges all valid contributions, rejects duplicates, and
writes the shared file only when the build contains at least one on-action.

## Add weighted random events

`randomEvents` emits the game's `random_events` block. Each row has a numeric
`weight` and an optional `event`. Omit `event` to emit the literal `0` no-op
arm:

```ts
mod.on(onActions.onFiveYearPulse, {
  randomEvents: [{ weight: 150 }, { weight: 50, event: vanilla.event.situation.$2000 }],
});
```

This emits:

```pdxscript
on_five_year_pulse = {
  random_events = {
    150 = 0
    50 = situation.2000
  }
}
```

On scoped hooks, authored and checked vanilla references must match the hook's
exact `THIS` and `FROM` contract. An authored event must also be present in a
selected Feature. A raw string remains the explicit escape hatch for an event
owned by another mod.

Rows keep their order within one call. Duplicate weights and repeated event
arms are legal because they carry probability rather than ordinary duplicate
registration. When several Features contribute weighted rows to one hook, the
Fold orders whole contributions by their content, so Feature order does not
change the output. If both lists are present, `events` emits before
`random_events`.
