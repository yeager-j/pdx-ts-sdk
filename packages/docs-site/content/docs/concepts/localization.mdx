The SDK turns author-facing text into the localization keys and files that
Stellaris loads. Use the narrowest authoring surface for each kind of text:

- Put a definition's own text in its generated localization members, such as
  `name` and `desc`. They take English text or a language record.
- Use `mod.localization` when another script field needs a standalone key owned
  by your mod. It adds the mod prefix by default, or can preserve an exact key
  in the ordinary localization layer.
- Use `mod.replaceLocalization` only when you intend to replace an exact key
  that already exists.

## Put definition text on the definition

Generated content methods expose the text slots declared for that content
type. For a building, `name` and `desc` are display text:

```ts
const resonanceArchive = mod.building("resonance_archive", {
  name: "Resonance Archive",
  desc: "A living record of every harmonic signal we have found.",
  // Other fields omitted.
});
```

The SDK mints the building id and applies the registry's localization patterns:

| Member | Generated key                                       |
| ------ | --------------------------------------------------- |
| `name` | `crystal_resonance_building_resonance_archive`      |
| `desc` | `crystal_resonance_building_resonance_archive_desc` |

The text does not appear in the building's PDXScript body. The game-facing
definition uses its id, while the [Fold](/guides/the-pipeline/) registers the
matching localization entries in the same Feature's language file.

Each registry reference page lists its localization slots as `$`-patterns,
such as `$_desc` in the [building field tables](/reference/buildings/). In
those tables `$` means the definition id, and for a nested entry's slots it
means that entry's own key.

### Translate a slot in place

Every text position takes the same value: a bare string, which is the English
shorthand, or a language record. Write the record where the definition is, and
the Fold emits one entry per language under the same generated key:

```ts
const resonanceArchive = mod.building("resonance_archive", {
  name: { english: "Resonance Archive", french: "Archive de résonance" },
  desc: "A living record of every harmonic signal we have found.",
});
```

`english` is required and the other names must be supported Stellaris
languages, exactly as in `mod.localization`. A language file is written only
for the languages some entry supplies, so the `desc` above stays in the
English file alone.

This is the same value everywhere text is authored: event `title`, `desc`, and
option names, a modifier row's `desc`, and the rename slots of a content patch.

### Pin a key that would otherwise hash its text

Most slots key off the definition id, so their keys are stable whatever the
text says. Two positions have no id to key off — a modifier row's `desc` and an
event option's `name` — and their keys end in a hash of the English text. Edit
that text and the key changes, orphaning any translation shipped against the
old one; the build reports it as `unstable-desc-key` or `unstable-option-key`.

Add `key` to the record to pin that part of the key instead:

```ts
options: [
  {
    name: { english: "Trace it to the source.", key: "trace_source" },
  },
];
```

`key` is only for those anonymous positions. On a slot whose key comes from the
definition id, it would name a key nothing reads, so the build refuses it.

## Fields that name a key

Some PDXScript fields hold a localization key rather than owning the text
themselves — a `customTooltip`, a conditional `desc`. They take the same
display text every other slot takes, and the SDK keys it for you from the
definition id and the field, so nothing has to be named twice:

```ts
const resonanceArchive = mod.building("resonance_archive", {
  customTooltip: "Stores discoveries made through resonance research.",
});
```

That emits `custom_tooltip = crystal_resonance_building_resonance_archive_custom_tooltip`
and writes the English under it. The key is built from the id and the field
path, so editing the words never moves it. Where the field repeats, each entry
counts from `0` in the order you wrote them.

To point one of these fields at a key that already exists, pass a reference
rather than text. That is the only meaning a bare string does _not_ have here.

## Create a standalone key with `mod.localization`

`mod.localization` mints a key of your own, and what it returns is a reference
you can hand straight to any field that names one:

```ts
const archiveTooltip = mod.localization("archive_tooltip", {
  english: "Stores discoveries made through resonance research.",
  french: "Conserve les découvertes issues de la recherche en résonance.",
});

// The same building as before, showing only the tooltip field.
const resonanceArchive = mod.building("resonance_archive", {
  customTooltip: archiveTooltip,
});
```

`mod.localization` adds the mod prefix to the name you pass, so this item owns
the complete key `crystal_resonance_archive_tooltip`, still readable as
`.key`. Reach for it when several fields share one entry, or when the text is
placed in a Feature of its own.

### Name a key this mod does not define

Vanilla's keys, and another mod's, come from `external.localization`:

```ts
import { external } from "@pdx-ts/sdk";

const resonanceArchive = mod.building("resonance_archive", {
  customTooltip: external.localization("BUILDING_RESEARCH_LAB_1_DESC"),
});
```

Only the key's syntax is checked: this build has no record of what vanilla
defines, so a misspelling reaches the game, where an unresolved key shows as
itself.

Recorded script reads a bare string the other way round. A key inside a trigger
or effect — `customTooltip("...")` — has no owning definition to key text
against, so a string there is still the key, and a reference works as well.

A string is shorthand for English-only text:

```ts
const label = mod.localization("archive_label", "Resonance Archive");
```

For translations, pass a language record with `english` plus any supported
Stellaris languages: `braz_por`, `french`, `german`, `japanese`, `korean`,
`polish`, `russian`, `simp_chinese`, and `spanish`. The SDK exports the list
as `LOCALIZATION_LANGUAGES`. English is required, and TypeScript rejects
unknown language names. The Fold emits only the language files that have
text.

Calling `mod.localization` does not emit anything on its own. The returned
value is a mod item: place it in a [Feature](/guides/features-and-discovery/)
and include that Feature in `mod.compile`, just like content and events. The
Feature's stem selects the localization filename.

### Preserve an exact key in ordinary localization

Some game-defined key patterns decide the complete key spelling. A technology
with `gateway: "crystal_resonance_orbital"`, for example, needs the exact key
`gateway_crystal_resonance_orbital`:

```ts
const gatewayDescription = mod.localization(
  "gateway_crystal_resonance_orbital",
  "Orbital Resonance path: Researching this technology leads to further advancements.",
  { prefix: false }
);
```

`prefix: false` changes only the emitted key. The item still belongs to the
creating mod, still goes in a Feature, and still writes to ordinary
`localisation/<language>/`. Its `.key` type is the exact supplied string.

Use this option only when Stellaris decides the full key pattern. The SDK checks
the key's syntax and duplicate registrations, but it cannot prevent the exact
key from colliding with Vanilla or another mod. Include the mod prefix within
the key where the game-defined pattern permits it, as the gateway value above
does.

## Replace an exact existing key deliberately

The paired example's `mod.replaceLocalization("crisis.2010.a", ...)` call
preserves the key exactly and writes it under the game's replacement layer.
The key is not prefixed or normalized — it must start with an ASCII letter,
digit, or `_`, and contain only ASCII letters, digits, `_`, `.`, `-`, or `'`.

Each language entry goes to
`localisation/replace/<language>/<prefix>_<feature stem>_l_<language>.yml`.
In the example, the `resonance` Feature makes the English file:

```text
localisation/replace/english/crystal_resonance_resonance_l_english.yml
```

Use this for a free-standing key that a typed content patch cannot reach, such
as existing event option text. The SDK cannot prove that the key exists in
Stellaris or another mod. A typo therefore creates an unused entry instead of
replacing anything.

Do not use `replaceLocalization` only because a new mod-owned key needs exact
spelling. Use `mod.localization(key, text, { prefix: false })` for that case so
the entry remains in ordinary localization.

A replacement language record is partial: include only the languages whose text
should change. Languages omitted from the record keep Vanilla's existing text,
so replacing only the French text does not emit an English replacement:

```ts
const frenchOnly = mod.replaceLocalization("crisis.2010.a", {
  french: "Réexaminez le signal.",
});
```

A bare string remains shorthand for replacing English only. A language record
must supply at least one language.

Ordinary localization and replacement localization are separate layers. Even
if they name the same key, the Fold keeps both files because the replacement
layer is the deliberate winner in game.

## Duplicate keys fail before files are written

The Fold checks localization keys across every selected Feature. Two entries in
the same layer and language may share a key only when their text is identical.
Identical registrations collapse to one deterministic file; different text
throws an error such as:

```text
Duplicate localization key "crystal_resonance_archive_tooltip" for english
```

The check includes text generated from content definitions, event text,
standalone localization, and localization contributed by patches. You do not
need to coordinate filenames to get this protection: the key is checked
globally before the Feature-owned files are resolved.

Keep every key and displayed value on one source line. For a line break that
Stellaris should display, write `\\n` in the TypeScript string — the escaped
backslash plus `n` — so the emitted file holds the two characters `\n`, which
is how the game's own localization spells one. A literal line break or NUL
byte is rejected because it could turn the rest of the file into unintended
entries. Since the game's format has no quote escape, the Fold replaces a
double quote in displayed text with a single quote and records a warning.

## What the emitted `.yml` files look like

The SDK's API and this documentation use the American spelling
**localization**. Stellaris requires the British spelling in its directory
names, so rendered paths use **`localisation/`** and
**`localisation/replace/`**. Do not rename those directories after the build.

Every emitted `.yml` file also starts with a UTF-8 byte order mark (BOM), then
the language header and sorted entries:

```pdxloc
l_english:
 crystal_resonance_archive_tooltip:0 "Stores discoveries made through resonance research."
```

The BOM is not visible in the PDXScript tab of the example above, but it is
present in the rendered file. Stellaris silently ignores localization files
without it, so the renderer adds it automatically.

Displayed text passes through to the game unchanged, so Stellaris markup works
as usual: scope properties such as `[Root.GetName]`, colour codes such as
`§Y...§!`, icon tags such as `£energy£`, and `$VARIABLE$` slots. The SDK does
not check these; the game interprets them at display time. Text that must vary
by game-state trigger is scripted localization (`mod.scriptedLoc`, emitted
under `common/scripted_loc`) — a content registry, not a localization entry.
